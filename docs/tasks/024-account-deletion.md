# 024: アカウント削除と退会

## 目的
**利用者が自分のアカウントを消せるようにする。**

人間の要望。

1. **確認を2段階以上にする**
2. **相手のデータも消える**
3. **同じ Google アカウントで、まっさらな状態から登録し直せる**

## 他のサービスがどうしているか（調べた）

**業界の答えは1つではない。3つの型がある。**

| サービス | 片方が消したとき |
|---|---|
| **CoupleStars** | **共有物は残る側に残す。**消えた側の個人特定情報だけ落とす |
| **Candle** | **共有物ごと消える。**相手のアクセスにも影響する |
| **OurCouple** | **自分が作った分だけ消える。**相手の分は残り、**相手に通知が行く** |
| Between | 別れたあとも共有データを保持したい人向けの案内がある（保持寄り） |

**人間が選んだのは Candle 型である。**

**futary はその型が合う。**理由は設計側にある。

- **`anniversary` と `meetup` は「ふたりのもの」と 021 で明記した。**
  作った人のものではない
- **`meetupDays`・付き合って〇日目・投稿数・写真の枚数は、ペアの属性である。**
  片方を抜いて成立しない
- **OurCouple 型（自分の分だけ消す）を採ると、カレンダーとホームが
  意味の通らない状態で残る**

**CoupleStars 型（残す側に残す）を採らない理由は別にある。**
**消したい側が、自分の写真を相手の端末に残したまま去ることになる。**
**「消した」と言えなくなる。**

## この判断の重さを、先に書いておく

**片方が押すと、相手の思い出が予告なく消える。**
**そして通知は作らないと決めてある**（ADR-008）。**相手は次に開いたとき、
何も無くなっていることで知る。**

**これは人間が選んだ形である。**変えたくなったら下の「先送りにしたもの」を見る。

---

## 1. 削除の順序（途中で止まっても読めない形にする）

**D1 にインタラクティブなトランザクションは無い**（`architecture.md` 4節）。
**途中で止まる前提で組む。**

### 訂正: 「最初に読めなくする」は、誰も守っていなかった

**当初「`couple_members` を最初に消す」と書いた。取り消す**（R の指摘）。

**`resolveCoupleContext` は `couple_members` から `couple_id` を解決する。**
**最初に消すと、2回目のリクエストが `NEEDS_ONBOARDING` に落ちて、
削除の手続きそのものに到達できない。**
**「読めなくする」と「途中から再実行できる」が、同じ1行に乗っていた。両立しない。**

**そのうえで、前提の方が間違っていた。**

**「途中で止まっても読めない形にする」と書いたが、誰から守るのかを書いていない。**
**ペアの2人は、もともと両方のデータを読める。**
**途中で残っていても、新しく誰かに見えるわけではない。守る相手がいない。**

**守る相手のいない要件のために、再実行できる性質を捨てていた。**

**再実行できることを優先する。`couple_members` は後ろに置く。**

```
1. reactions        （posts と user を参照）
2. posts
3. events
4. invites / invite_failures
5. couple_members   ← ここまで来れば、あとは couple_id が要らない
6. couples
7. user を消す（session と account は ON DELETE cascade で落ちる）
```

**5 まではどこで止まっても `couple_id` が引けるので、もう一度押せば続きから進む。**

**`resolveCoupleContext` には触らない。**
R は「`couples` に削除中の印を立てて `resolveCoupleContext` が弾く」案も挙げたが、
**採らない。**削除の手続きだけを通す例外が要り、
**認可の要に穴を1つ開けることになる**（005 がまさにそれを潰した）。
**守る相手のいない要件のために、認可の中心を触らない。**

### 途中で止まったまま戻ってこなかったら

**残る。**それは受け入れる。

- **半分消えた状態が読めることは、開示ではない。**
  読めるのは元から読めた2人だけである
- **もう一度押せば続きから進む。**そこまでを担保する
- **相手側から見ると中途半端な状態になる。**それは「消えていない」ことの
  見え方であって、**新しい害ではない**

- **2〜8 は何度実行しても同じ結果になる形にする**（`WHERE couple_id = ?`）。
  **途中で落ちたら、もう一度走らせれば続きから進む**
- **順序を変えない。**`posts` より先に `reactions` を消さないと FK で落ちる。
  `user` は最後（`posts.author_id` などから参照されている）
- **`session` と `account` は `user` を消せば自動で落ちる**（cascade。実測で確認済み）。
  **他のテーブルに cascade は無い**

### R2 の消し漏れは「消えていない」と同じ

**D1 が消えても R2 のオブジェクトが残ると、鍵を持っている人には見え続ける。**
`post.delete` は R2 の失敗を握りつぶす設計だが（007）、**ここでは握りつぶさない。**

#### 行から鍵を集めない。接頭辞で消す（R の指摘）

**当初の順序では `posts` を先に消していた。`image_key` の一覧が失われる。**

**接頭辞で消す。D1 の行に依存しない。**

| 接頭辞 | |
|---|---|
| `couples/{coupleId}/posts/` | ペアの投稿画像 |
| `users/{userId}/profile/` | **プロフィール画像。2人分**（`r2-signed-url.ts` の `userImageKeyFor`） |

**プロフィール画像を落とすところだった。**`couples/` の下だけを見ていた。

**接頭辞で消すと、削除の順序から独立する。**
`posts` の前でも後でも同じ結果になり、**再実行しても同じである。**

**論理削除で残っていた過去の画像も、この機会に片付く**（`post.delete` は
`image_key` を残す設計。007）。

- **失敗したら、失敗したことを残す。**黙って成功にしない
- **署名付き URL の有効期限は最長1時間**（6節）。
  **既に発行済みの URL は、消しても1時間は生きる。**これは受け入れる

## 2. まっさらな状態から登録し直せる

**`user` の行を消す。**残すと、同じ Google アカウントで入り直したときに
**前の利用者として復帰する。**

- `account`（Google との紐付け）は `user` の cascade で落ちる
- **`invite_failures` は `user` を参照している。`user` より先に消す**
- 消したあと、**同じ Google アカウントは「初めての利用者」として登録される**

### T9 と同じ観点で後始末する

**削除の直後、クライアントに前の状態が残らないこと**（`architecture.md` 5節）。

- **サインアウトする。**セッションはサーバ側で消えているが、**画面が知らない**
- **識別が変わるので、キーに閲覧者を含めている問い合わせは自然に切り替わる。**
  **ただし「利用者ごとに違う値を持つキャッシュ」の一覧に漏れがあると、そこだけ残る**
- **削除 → 同じ Google アカウントで再登録、を通しで見る。**
  **新しい利用者IDになるので、キーは衝突しない**

## 3. 確認を2段階以上にする

**「取り消せない」と「相手のデータも消える」を、別々の段階で見せる。**

1. **1段階目。**何が消えるかを列挙する（投稿・写真・カレンダー・記念日・統計）
2. **2段階目。相手のデータも消えること、相手に事前に知らせないことを明記する。**
   **ここで初めて「削除する」が押せる**

**2段階目に、具体的に何が消えるかを書く**（R の指摘）。

- **相手が書いた投稿も消える**
- **相手が押したリアクションも消える**
- **相手のプロフィール画像も消える**
- **相手には事前に知らせない。次に開いたとき、ペアが無くなっている**

**「あなたのアカウントを削除します」では足りない。
消えるのは相手の分も含めた全部である。**

- **既定で押せる状態にしない。**020 の「押しても何も起きない、にしない」の逆で、
  **ここは押しにくくする**
- **文言に「アカウントを削除」だけを書かない。**
  **「ふたりのデータを削除」である**

## テストで証明すること
- **`couple_members` を消した時点で、両方の利用者がどの手続きからもペアのデータを
  読めない**（残りの行が残っている状態で）
- **途中で止めて再実行しても、同じ結果になる**（各段で1回止めて再開する）
- **`user` を消すと `session` と `account` が落ちる**（cascade）
- **`user` より先に `invite_failures` を消さないと落ちる**（順序の証明）
- **削除後、同じ Google アカウントで登録すると、前のペアに戻らない**
- `security-requirements.md` 3節の認可テストが緑

## 確認観点
- 2段階目に**相手のデータも消えることが書いてあるか**
- **押し間違えない形になっているか**
- 削除後に**同じアカウントで入り直して、まっさらか**
- **相手側の画面が、次に開いたときどう見えるか**（何も無い状態になる）

## 先送りにしたもの（採らなかった案）

**猶予期間を置き、相手が次に開いたときに知らせる形。**

「相手の思い出が予告なく消える」への手当てとしては、これが正しい。
**通知が無くても、次に開いたときに画面で知らせられる**（ADR-008 に反しない）。

**採らなかったのは、実装が重いからである。**

- 猶予後の実削除を誰が走らせるか。**Cron Triggers は 021 で「無料枠で使えるか
  未確認」のまま先送りしている**
- Cron を使わないなら**「誰かが開いたときに回収する」形になるが、
  誰も開かないペアは残り続ける**
- 猶予中に同じアカウントで登録し直したいとき、**そこで即時削除に切り替える**必要がある

**「予告なく消える」を受け入れたのは、人間の選択である。**
**変える判断が出たら、ここから始める。**
