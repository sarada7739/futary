# 025: 招待コードの再発行

## 目的
**ペアを作ったあとに、招待コードをもう一度出せるようにする。**

人間の要望（「念のため」）。

## サーバ側は既にある

`invite.issue` は**呼ばれるたびに前のコードを無効にする**（004 の監査 Medium 指摘由来。
同時に有効なコードは1件だけ）。**再発行の手続きを新しく作る必要は無い。**

**足りないのは画面である。**いまコードを見られるのは
`(onboarding)/invite.tsx` だけで、**ペアが成立すると二度と通らない。**

## 1. 置き場所

**マイページに置く。**

- **ペアが1人のときだけ出す。**2人揃っていたら**出さない**
- **出さない理由を書く。**「相手が参加済みです」。**押せないボタンを置かない**（020）

### 満員のペアで発行できないことを確かめる

**`invite.issue` が、既に2人いるペアで呼ばれたときどうなるかを先に確かめる。**

- 拒んでいるなら、**その拒み方をテストで固定する**（いま無いなら足す）
- 拒んでいないなら、**サーバ側で拒む。**画面で出さないだけにしない
  （**UI 側の制御に依存しない**。`security-requirements.md` の T5 と同じ考え方）

**「画面に出さないから安全」は、この製品では採っていない。**

## 2. 前のコードが無効になることを、押す前に伝える

**再発行すると前のコードが使えなくなる。**
**相手に既にコードを渡していたら、それが通らなくなる。**

- **押す前に書く。**押したあとに気づく形にしない
- 「念のため」で押した人が、**相手に渡したコードを無効にしてしまう**のがいちばん惜しい

## 3. T9 の対象である

**招待コードは「利用者ごとに違う値を持つキャッシュ」である**
（`architecture.md` 5節。#178 で `PENDING_INVITE_QUERY_KEY` を対象に入れた）。

**マイページから発行する経路でも、キーに閲覧者を含める。**
**画面が増えるとき、そこが漏れる。**

## テストで証明すること
- **2人揃っているペアでは発行できない**（サーバ側。画面ではなく）
- **再発行すると前のコードが使えなくなる**（004 の既存の性質。**変えていないこと**）
- **発行した本人以外が、そのコードを引けない**
- 新しい経路のキャッシュキーに閲覧者が含まれる（T9）

## 確認観点
- **相手が参加済みのとき、再発行の導線が出ていないか**
- **前のコードが無効になることが、押す前に読めるか**
- 発行したコードが**その場で読めるか**（コピーできるか）
