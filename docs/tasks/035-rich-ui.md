## 目的

**人間がモックアップ2枚（ホーム・サインイン）を出した。「可能な範囲で」寄せる。**
**そして「この2画面だけでなく、全画面に反映」との指示。**

**完全一致は目標ではない。**寄せられるところを寄せ、**寄せないと決めたものを結果に書く**
（`conventions.md` 6節「検証の範囲から外したものは、結果に書く」）。

## 0-2. 画面を1つずつ作り込まない（この指示のいちばん大事なところ）

**モックに写っているのは2画面だが、そこに写っているのは画面ではなく「素材」である。**

- 淡いグラデーションの地
- **白いカード + やわらかい影 + 大きめの角丸**
- **ピル型**（バナー・ボタン・バッジ）
- 光のボケ
- **主役の要素を、はっきり大きく**

**この語彙をトークンと `packages/ui` の部品に落とす。全画面は、それを使うだけにする。**

**14画面を1つずつ寄せない。**

| | |
|---|---|
| 1つずつ寄せる | **一貫しない。**そして**次に画面が増えたとき、また作り込みが要る** |
| **部品を寄せる** | **全画面が一度に変わる。**次の画面も最初からそう見える |

**`packages/ui` のコンポーネントは `style` を受け取らない**（`architecture.md` 7節）。
**つまり見た目はもともと部品側にある。そこを直せば全画面に効く、という作りになっている。**

### 対象（14画面）

```
(tabs)      index  calendar  timeline  memory  stats  list  mood  profile  delete-account
(auth)      sign-in
(onboarding) index  create  invite  join
（モーダル） compose
```

**個別に作り込むのは、モックに写っている2つ（ホーム・サインイン）だけ。**
**残り12画面は「部品を使っているので、そう見える」状態を目指す。**
**そこに個別の細工を足さない。**

### 途中で一度止まる

**部品（トークンと `packages/ui`）ができた時点で、一度人間に見せる。**

**14画面を触ってから方向が違うと分かるのが、いちばん高い。**
**部品の段階なら、やり直しが1回で済む。**

### 背景の光のボケ
- **コードで作らない。画像を1枚敷く**

- 敷けないなら敷かない。**無くても他が効く**

### 機能パネル（`feature-panel.tsx`）— 020 の判断を覆す
- **白いカード**（`surface` 地 + `radius` + `shadow.card`）にする
- **「COMING SOON」を薄く重ねる**

**020 で「枠線も背景も持たない」と決めた。**理由は
**「薄い枠は『押せそうな箱』に見える」**だった。

**モックは枠線ではない。白い面と影である。**
**020 が嫌ったものと別物なので、判断を覆す。**

**押せる／押せないの差を濃さで見せる、という 020 の考え方は残す。**

### 「次フェーズ」→「COMING SOON」
- **「次フェーズ」は開発の都合の言葉である。利用者の言葉ではない**
- **これは字種の趣味ではなく、文言の質の話である**

### ボトムタブ
- **浮かせる。**画面下端に貼り付けず、左右と下に余白を取ったピル型にする
- 中央の **＋ は大きな丸**（いまの FAB を活かす）。**光彩を足す**
- **ラベルは日本語のまま。**モックは英字だが、**`requirements.md` 6節「言語: 日本語のみ」を、
  見た目のために変えない。**アイコンと短い日本語で既に読める

**浮かせると、下のコンテンツが隠れる。**
**各画面のスクロールの下パディングを、タブバーの高さ＋余白ぶん足すこと。**
**「隠れていないか」を全画面で見ること。**

### トークンを足すときは A に上げる

**`packages/ui` のコンポーネントは `style` を受け取らない**（`architecture.md` 7節）。
**必要ならコンポーネント側にプロパティを足す。**呼ぶ側から `style` を渡す形にしない。

**新しいトークン（グラデーションの色・影の段階・角丸の大きい方）は、
`architecture.md` 7節に書く。書くのは A。**
**B は「足したいトークンと、その値と、なぜその値か」を挙げて A に上げる。**

**トークンを勝手に増やさない。**増やした先が散ると、**次に触る人がどれを使うか決められない。**

- **スマホ幅とPC幅の両方**

# 視覚仕様（2026-09-05。人間の「リッチ感がなく、前よりひどい」を受けて A が起こした）

**部品の段階を人間が見て、否定的な評価だった。**
**モックと現状を同じ物差しで実測し、数値に落とした。**

**数値はここに書いてあるものを使う。**「感覚で寄せる」をしない。

## なぜ「前よりひどい」に見えるのか（診断）

1. **視覚的な重さが上下逆。**画面最上部に唯一の濃色ブロック（`brand-ink` ベタのバナー）があり、
   **主役のカードは白くて薄い。**目が最初にデモ告知に吸われる
2. **文字階層が潰れている。**最大24px / 最小12px で**比が2倍しかない。**
   モックは日数72pt に対しラベル11pt で**6倍以上。**
   **全部が太字で全部が同じくらい、はカタログの見え方**
3. **箱の中身が小さい。**172pt のカードに 56pt のアバターと1行の文字。
   **白い面積が余って「空箱」に見える**
4. **深さがない。**`shadow.card`（0.04）は画面上でほぼ見えず、**カードが地に貼り付いている**
5. **パネルの隙間が4pt。**8枚の独立した面ではなく**「1枚の表」に見える**
6. **下の 195pt（画面の24%）が無地。**モックは 79pt しか空かず、**地にボケがあるので「空」に見えない**

### 文言を短くする（A の判断）

**11pt で27文字は入らない。**

```
これはデモです。ログインすると自分のふたりの記録を残せます   （27文字。入らない）
→ これはデモです。ログインで記録を残せます                （19文字）
```

**2行に折るのは禁止。**「収まっていない」が、この画面でいちばん安く見える。

**デスクトップでは全幅に伸ばさない。`layout.maxWidth`(640) の列の中に入れる。**
**いまの全幅の茶帯は、デスクトップで最も悪く見える。**

### 「今日どうだった？」は2行のままにする（A の判断）

**文言もフォントサイズも変えない。この1枚だけ2行を許す。**

- **文言はプロダクトの一番尖った機能の名前である**（`requirements.md` 5節）。
  **見た目のために機能の名前を削らない**
- **1枚だけサイズを変えると、次に長いラベルが出たときにまた1枚だけ変えることになる**
- **`FeaturePanel` は元から `LABEL_LINES = 2` で高さを取っている。折り返しは設計内である**

**7枚が1行になれば「入りきっていない」感は消える。1枚だけ長いのは、名前が長いからである。**

### アイコンを線画にしない（A の判断）

仕様の元案は「塗りでなく線（線幅1.75）」だった。**やらない。**

**`packages/ui/assets/` のアイコンは PNG である。線の太さは変えられない。**
差し替えは**新しい素材を作ること**になり、035 の範囲外。

**`tintColor` で色だけ変える。結果に「やらなかった」と書く。**
