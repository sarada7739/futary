## 1. いちばん大事な設計判断: 色は静的な定数ではなくなる

**今、`colors` は `packages/ui/src/tokens.ts` の `as const` な定数で、
`apps/app` の 21 ファイル・約 90 箇所から直接 import されている。**
**`shadow.glow` は `colors.primary` を参照し、`gradients` は `colors` から組み立てている。**

**定数のままでは切り替えられない。**画面の見た目に関わるトークンを、
**React のコンテキストから取る形に変える。**

### 分ける: モードで変わるもの・変わらないもの

| 変わらない（静的 export のまま） | **変わる（`useTheme()` から取る）** |
|---|---|
| `radius` `space` `layout` `fontFamily` | **`colors` `shadow` `gradients`** |

### 静的な `colors` の export を消す（ここが留め金）

**`@futary/ui` から `colors` `shadow` `gradients` の静的 export を消す。**
**残すと、直し忘れた画面がピンクのまま何事もなく動く。**
**消せば、型チェックが直し忘れを全部挙げる**（`conventions.md` 6節
「留め金は、閉じた集合の側に打つ」。閉じた集合は「`@futary/ui` の export」である）。

**「全部の画面を目で見て確かめる」を留め金にしない。**

### `useTheme()`

```ts
// packages/ui
export type Appearance = "pink" | "white";
export const APPEARANCE_VALUES = ["pink", "white"] as const;

export function useTheme(): {
  appearance: Appearance;
  colors: Colors;        // 今の colors と同じキー
  shadow: Shadow;        // card / fab / glow
  gradients: Gradients;  // screen / card
};
export function useAppearance(): {
  appearance: Appearance;
  setAppearance: (a: Appearance) => void;
};
```

- **キーの集合は両モードで同一。**ホワイトだけに存在する色・ピンクだけに存在する色を作らない。
  **型で `Record<ColorToken, string>` を両方に要求する**
- `AppearanceProvider` はルートに1つ。**Provider が無いとき（画面結合テストの多く）は
  `pink` で動く**（`guest-mode.ts` と同じ理由・同じ形）
- **`packages/ui` の部品も `useTheme()` を使う。**`Screen` `Card` `Button` `Text` `Avatar` `Badge`
- **画面ファイルは `const { colors } = useTheme()` に置き換えるだけ。**見た目の判断を画面に書かない

### `+html.tsx`

`<meta name="theme-color" content="#F5868D">` に `colors.primary` のリテラルが書いてある
（`@futary/ui` を import できない理由はそこのコメント）。
**ホワイトのときは `#1D1D1F` にする。**保存値を読む inline script で `<meta>` を書き換えるか、
起動後に JS から書き換えるか。**起動後でよい**（theme-color はブラウザの外枠の色で、
一瞬ピンクでも実害は無い）。**やらないなら理由を結果に書く。**

**`<body>` の背景色がピンクで固定されていれば、それは inline script で先に直す。**
**ホワイトを選んだ人が、起動のたびに一瞬ピンクを見るのは避ける**（保存先が
`localStorage` なので同期で読める。下記 2節）。

## 2. 保存先は端末。サーバに置かない

| | |
|---|---|
| サーバ（`couple_members` に列を足す） | マイグレーション・API・テストが要る。**ゲストは保存できない。**起動時に通信を待つ間、どちらの色で描くか決められない |
| **端末（Web は `localStorage`）** | **見た目は個人の・端末の好みである。**記念日（`primaryDate`）は「ふたりの共有データ」だったが、これは違う。相手に反映させない。**ゲストでも使える。同期で読めるので起動時に一瞬もぶれない** |

**端末に置く。**キーは `futary.appearance`。値は `"pink"` か `"white"`。
**それ以外の値・未設定は `pink`**（未知の値で壊れない）。

- **`localStorage` に置いてよい。**`security-requirements.md` 2節が禁じているのは**秘密**である。
  これは秘密ではない。**`expo-secure-store` を使わない**（秘密ではないものを秘密の箱に入れない）
- **ネイティブ（iOS）はまだ配布していない**（`requirements.md` 5節）。
  **`Platform.OS !== "web"` ではメモリに持つだけでよい。**インターフェースは同じにしておく。
  **`@react-native-async-storage` を足さない**（依存を増やさない。使う日が来たらそのとき）
- **同じ端末の別ブラウザ・別端末では別々の設定になる。**それでよい。結果に1行書く

**ADR-014 に記録した**（`docs/decisions.md`）。

## 3. ホワイトのパレット（**数値は B が決める**）

**人間の指示: 「詳細な数値の決定は B（Fable）に任せてよい」。**

**A が決めるのは、どのトークンが何の役割か・どちらの方向へ振るか、だけである。**
**下の表の値は A の参考値であり、B はこれに縛られない。**Apple の Web サイト・
iOS 設定アプリの値を A が見て置いたものだが、**画面に出して、モックと並べて、B が決める。**
**決めた値と理由を B が結果に書き、A が `architecture.md` 7節へ写す。**

**縛るのは2つだけ:**
- **役割ごとに1トークン。**キーの集合はピンクと同一（1節）
- **ホワイトの `border` は、地の上で見える濃さにする。**ホワイトでは枠線が唯一の輪郭
  （035 で `border` が薄すぎて `secondary` の枠を変えた教訓）

| `surface` | `#FFFFFF` | **`#FFFFFF`** | 地と同じ。**カードは影ではなく枠線で浮く** |

### 影・発光・グラデーション（方向だけ A が決める。値は B）

| トークン | ピンク | **ホワイト** |
|---|---|---|
| `shadow.card` | 0.08 / 24 / y8 | **無し**（不透明度 0）。**代わりに `Card` が `border` 1px の枠線を持つ** |
| `shadow.fab` | 0.15 / 6 / y3 | **残す。**黒い FAB も白地の上で浮いている必要がある。濃さは B が見て決める |
| `shadow.glow` | `primary` 0.25 / 10 | **無し**（不透明度 0）。**発光はピンクの語彙。ホワイトには無い** |
| `gradients.screen` | `bg` → `surface-tint` | **`bg` → `bg`**（平ら） |
| `gradients.card` | `surface-tint` → `primary-subtle` | **`surface` → `surface`**（平ら） |
| 光のボケ（`Screen` の画像） | 敷く | **敷かない** |

**「無し」を値で表す（不透明度 0）か、部品側で分岐するか。**
**値で表せるものは値で表す。**`Screen` のボケだけは画像の有無なので `appearance` で分岐する。

### `Card` の枠線

**ピンクでは影だけ・ホワイトでは枠線だけ、ではなく、両方とも `border` 1px を持たせてよい。**
ピンクの `border`（`#F2E0DC`）は地とほぼ同色で、影の上に乗っても見た目はほぼ変わらない。
**部品の分岐を1つ減らせる。**ただし**ピンクで見え方が変わっていないことを画面で確かめる**
（変わるなら分岐する）。

## 4. 切り替え UI（マイページ）

- **カード「見た目」を1つ足す。**記念日カードの上、プロフィールカードの下
- **選択肢は2つ。「ピンク」「ホワイト」。**`primaryDate` の選択（「ホーム上部の表示」）と
  **同じ部品・同じ見た目**（選ばれている方が `primary`、他方が `secondary`。
  `flexWrap` で並べる。新しい部品を作らない）
- **押した瞬間に全画面が変わる。保存ボタンは無い**（端末の設定なので通信が無い。
  記念日の「保存」と同じ列に置かない）
- **ゲストにも出す。**ログイン不要の設定である。
  今のマイページは未ログイン時に「Google アカウントでログインしてください」を出して
  設定カードを出していない。**「見た目」だけはその上に出す**
- 一言添える: **「この端末だけの設定です」**（相手には反映されないことを、聞かれる前に言う）
- `testID`: `profile-appearance-pink` / `profile-appearance-white`

## B との合意（2026-09-13。着手前に B が挙げ、A が判断した）

| B の提案 | A の判断 |
|---|---|
| CSP の所在は `scripts/build-public.mjs` が生成する `_headers`。**Expo Router の唯一の inline script を sha256 で固定**しており、distinct な inline script が2種類以上になるとビルドが止まる | 了解。停止条件の「A は所在を確かめていない」はこれで解消 |
| `+html.tsx` に inline script は足さない。`<body>` に背景色の固定は無く、Provider が `localStorage` を同期で読むので初回レンダーから白で描ける。theme-color の `<meta>` は起動後に JS で書き換える | **方針は了解。ただし「一瞬ピンクが出る経路が無い」はまだ確かめられていない。**`app.json` は `web.output: "static"` で、**各ルートの HTML はビルド時に prerender される。**そのとき `localStorage` は無いので、**prerender された HTML はピンクで描かれている可能性がある**（hydration までの最初の描画）。**書き出した `dist` の HTML に `#FEF6F3` や `gradients.screen` の値が入っているかを見ること。**入っていれば、白を選んだ端末で hydration 前の一瞬がピンクになる。**測ってから決める**: 見えないなら結果に「見えない」と書いて終わり。見えるなら、**2つ目の inline script を `build-public.mjs` でハッシュに足すのは「緩める」ではない**（`'unsafe-inline'` にしなければよい）ので、そのときは足してよい。**測る前に足さない** |
| T3〜T5（レンダリングを伴うテスト）は `apps/app/test` に置く。`packages/ui` には jsdom・testing-library・react-native-web が無く、足すと「入れる依存: 無し」に反する。既に `screen.test.tsx` が同じ理由でそこにある。T1・T2（純粋な値）は `packages/ui` | 了解。**8節の表の「どこで」を B の案で読み替える** |
| `Card` の枠線: ピンク側に 1px を足すと内容が 1px 内側へ動き「1ピクセルも変えない」に反する。最初から `Card` 内で分岐する | 了解。**3節の「両方に持たせてよい」は撤回。**分岐する。理由は B の言うとおり |
