# 021: 予定の持ち主と、ふたりの予定

## 目的

人間が 018 の実機確認で出した要望。

1. **予定は設定者以外が編集・削除できない**
2. ただし「**ふたりの予定**」にチェックが入っていれば、もう1人も編集できる
3. ~~チェックの入った予定は、**翌日「会った日」に変わる**~~ → **公開後へ回す**

## 1. ペアの内側で権限が分かれるのは、これが初めてである

いままでの認可は「**`couple_id` で絞れば、ペアの2人は同じものを見て、同じものに触れる**」
だった（`security-requirements.md` 3節）。**その前提が変わる。**

`plan` にだけ、**行ごとの持ち主**ができる。

| `kind` | 誰が編集・削除できるか |
|---|---|
| `anniversary` | **どちらでも。**ふたりの記念日である |
| `meetup` | **どちらでも。**ふたりが会った事実である |
| `plan` | **設定者だけ。**ただし `is_shared` が立っていればどちらでも |

**`anniversary` と `meetup` は変えない。**個人のものではないため。

### 2段階にしない

**`SELECT` で持ち主を確かめてから `UPDATE` する形にしない**
（`security-requirements.md` 3節）。**1文の `WHERE` で表す。**

```sql
WHERE id = ?  AND couple_id = ?
  AND (kind <> 'plan' OR is_shared = 1 OR created_by = ?)
```

`event.update` と `event.delete` の**両方**に要る。
**片方だけに書くと、消せてしまう。**

### 認可テストに項目7を足す

`security-requirements.md` 3節に足す。**ペア内の書き込み権限は新しい種類**であり、
既存の6件はどれも「他のペアに触れないこと」か「未認証」の話で、**これを守っていない。**

### `kind` の変更が権限を奪う（security-auditor が発見）

**`WHERE` は更新前の行で評価される。**同じ `UPDATE` の中で `kind` 自体も
変えられるため、次が通る。

1. 記念日・会った日（**どちらでも編集できる**）を、設定者でない側が編集する
2. その編集で `kind` を `plan`、`is_shared` を 0 にする
3. `created_by` は元の設定者のまま
4. **以後その行は「設定者だけが編集できる `plan`」になる**

**021 以前は全 `kind` が「どちらでも編集できる」だったので、`kind` の変更は
無害だった。持ち主の概念を入れたことで、`kind` の変更が権限を奪う手段になった。**

#### これは攻撃より先に事故である

**締め出されるのは、まず編集した本人である。**自分が編集した行に、その直後から
触れなくなる。**設定者は直せるので回復不能ではないが、締め出された側は自力で
戻せない。**「相手に頼んで直してもらう」しか無い。

**ふたり専用のアプリで、片方が片方に頼まないと戻せない状態を作らない。**

#### 更新後の状態でも実行者が編集できることを要求する

`WHERE` に1つ足す。**読み足さない。**新しい `kind` と `is_shared` は入力にあり、
`created_by` は行にある。**同じ1文で表せる。**

#### 「自分を締め出す」だけでは足りなかった（R の指摘）

**当初この2行だけにしていた。誤りだった。**

```sql
  AND (kind     <> 'plan' OR is_shared     = 1 OR created_by = ?)   -- 更新前
  AND (:newKind <> 'plan' OR :newIsShared  = 1 OR created_by = ?)   -- 更新後
```

**`created_by` は更新で変わらない。**だから2行目は
**「更新後も実行者が編集できること」しか要求していない。**
**設定者本人は素通りする。**自分が作った記念日・会った日を非共有の `plan` に
変えられ、**相手は以後その行に触れられない。**

**監査の原文は「片方の判断だけで」だった。**私が塞いだのは
「設定者でない側が」の分だけである。**指摘の半分だった。**

**`meetup` で実害が具体的である。**自分が作った「会った日」を非共有 `plan` に
変えると **`meetupDays` が減る。ホーム最上部の主役の数字である。**
相手は戻せない。

#### `anniversary` と `meetup` は、ふたりのものから片方のものへ移せない

**この表は 021 が自分で書いたものである。**

> `anniversary` | **どちらでも。**ふたりの記念日である
> `meetup` | **どちらでも。**ふたりが会った事実である

**行がこの区分から片側の操作だけで出られてはいけない。**3行目を足す。

```sql
WHERE id = ?  AND couple_id = ?
  AND (kind     <> 'plan' OR is_shared     = 1 OR created_by = ?)   -- 更新前の権限
  AND (:newKind <> 'plan' OR :newIsShared  = 1 OR created_by = ?)   -- 自分を締め出さない
  AND NOT (kind <> 'plan' AND :newKind = 'plan')                     -- 区分をまたいで狭めない
```

**3行とも同じ1文で表せる。**新しい `kind` と `is_shared` は入力にあり、
`kind` と `created_by` は行にある。**読み足しは要らない。**

| 誰が何をする | 結果 |
|---|---|
| **設定者が**、記念日・会った日を「非共有の予定」にする | **拒む**（R の指摘。**当初これが通っていた**） |
| 設定者でない側が、記念日・会った日を「非共有の予定」にする | **拒む** |
| どちらかが、記念日・会った日を「**共有の**予定」にする | **拒む**（下記。**当初は通していた**） |
| 設定者でない側が、共有の予定の共有を外す | **拒む**。**共有を外せるのは持ち主だけになる** |
| 設定者が、自分の予定の共有を外す | **通る** |
| どちらかが、`plan` を記念日・会った日にする | **通る**（権限が広がる方向） |

#### 2回に分ければ着けた（R の指摘）

**当初この行には `AND :newIsShared = 0` が付いていた。**
「非共有の `plan` にする更新」だけを止める形である。**2回に分ければ迂回できた。**

| | 当初の条件に引っかかるか | |
|---|---|---|
| step1 | `meetup` → **共有**の `plan` | **引っかからない**（`:newIsShared = 1` のため） |
| step2 | 共有の `plan` → 非共有（持ち主が） | **引っかからない**（`kind` が既に `plan` のため） |
| 結果 | | **1回で止めた終着点に、2回で着く** |

**条件を「この操作が安全か」で書いていた。「この状態遷移が許されるか」で書く。**
1つの更新だけを見ると防げていても、**行が通れる経路をつなぐと着く。**

**`:newIsShared` を条件から外す。`anniversary`・`meetup` は `plan` になれない。**

#### 区分をまたぐ変換は、広がる向きだけ許す

| 向き | |
|---|---|
| `plan` → `anniversary`・`meetup` | **通る。**持ち主のあるものが、ふたりのものになる（広がる） |
| `anniversary` ↔ `meetup` | **通る。**どちらも「ふたりのもの」で、区分をまたがない |
| `anniversary`・`meetup` → `plan` | **拒む。**共有で作っても、次の更新で狭められる |
| `plan` の共有/非共有 | **持ち主が決めてよい。**変えない |

**「記念日を共有の予定にする」は当初通していたが、閉じた。**
**失うものは小さい**（その用途はほぼ無く、消して作り直せる）。
**残せば、2回で抜けられる。**

**`plan` は「持ち主のあるもの」、`anniversary`・`meetup` は「ふたりのもの」である。**
**区分そのものが権限を表しているので、区分をまたぐ変換だけを見ればよい。**

**「消してから作り直す」は塞がない。**削除は目に見える操作であり、
記念日・会った日はどちらでも消せる。**問題だったのは、編集の見た目で
権限が片側へ移ることだった。**

**「共有を外せるのは持ち主だけ」は副作用だが、望ましい方である。**
持ち主でない側が共有を一方的に解除できる方がおかしい。

#### `event.delete` には要らない

**削除は状態を変えない。**更新後の状態が無いので、条件も無い。

#### 公開後に入れる 3 には適用しない

**共有の予定を翌日 `meetup` に変える処理は、利用者ではなく仕組みが動かす。**
しかも `plan` → `meetup` は**権限が広がる方向**である。
**この条件は利用者の更新にだけ掛ける。**

#### 画面で先に止める

021 は「**押せてから断られる形にしない**」と決めている。
**設定者でない側が編集するとき、結果が「非共有の `plan`」になる選択を出さない。**
実際には、`kind` に `plan` を選んだ時点で**「ふたりの予定」を立てたまま固定する。**

**返るのは `NOT_FOUND` のまま**（上記の判断と同じ）。ここでも到達するのは
競合したときだけになる。**ただし理由は違う。**上は「見えているのに見つからない」
だったが、こちらは**「その更新を受け付けない」**である。
**画面で出さない限り、利用者はこの差に触れない。**

### `event.list` が `canEdit` を返す（R の指摘）

**確認観点の「編集できないことが画面から分かるか」を、いまの契約では満たせない。**
`event.list` が返しているのは 018 で足した `createdByName` **だけ**で、
`created_by` は返していない。

**名前で突き合わせる形は採れない。019 でふたりが同じ名前を設定できるようにした。**
同じ名前のペアで、相手の予定が編集できてしまう。

**`createdById` を返してクライアントに判定させる形は採らない。**

上の `WHERE` は `kind` と `is_shared` と id の**3つの組み合わせ**である。
id を返すと、**この式が画面側にもう一度書かれる。**
`daysTogether` を判別可能な union にしたときと同じ理由である
（**クライアントに解釈を持たせない**。`architecture.md` 5節）。
ずれれば、**押せるのに断られるか、押せないのに権限があるか**のどちらかが起きる。

**サーバが `canEdit`（boolean）を計算して返す。規則は SQL の1箇所のままにする。**

#### 2つが一致していることをテストで固定する

`canEdit` は SQL とは別の言語で書かれる。**別々に書けば、別々にずれる。**

**`(kind × is_shared × 設定者かどうか)` の全組み合わせについて、
`event.list` が返す `canEdit` と、`event.update` が実際に成功するかどうかが
一致することを突き合わせる。**

**「両方に同じことを書いた」ではなく「両方が同じ答えを出す」を固定する。**
`event.delete` も同じ規則なので、同じ表で見る。

**作れない組み合わせを「一致した」と数えない**（R の指摘）。
`is_shared` は `plan` にしか立たない（入力スキーマと CHECK の両方で拒む）。
**`anniversary × is_shared=1` は作れない。**表から落ちていること自体は正しいが、
**落ちたぶんを「一致」として数えると、網の目が実際より細かく見える。**

表に要るのは3つ。

| | |
|---|---|
| 網羅 | `kind` 3値 × `is_shared` 2値 × 設定者かどうか 2値 に**漏れが無いこと** |
| 除外 | **作れない組み合わせが、作れないものとして除かれていること**（数に入れない） |
| 対象 | **`event.update` と `event.delete` の両方**が同じ表を通ること |

3つ目は 021 が上で書いていることそのものである。
**片方だけに書くと、消せてしまう。**

### 権限が無いときは `NOT_FOUND` を返す（R の指摘）

021 で3つ目の場合が増える。**同じペアの、相手の非共有 `plan`。**
利用者は**その予定を画面で見ている。**隠すべき情報が何も無いのに、
他ペアのIDを叩いたときと同じ返事をすることになる。

**それでも `NOT_FOUND` のままにする。**

- 1文の `WHERE` では「0件だった理由」を区別できない。
  区別しに行くと2段階になり、**それは上で禁じたことそのものである**
- **画面は `canEdit` で押せなくする。**通常の操作でここに到達しない
- 残るのは**競合したときだけ**である（相手がいま共有を外した、いま消した）。
  そのとき「見つかりません」と出るのは、**実際に見つからなかったのと同じである**

**理由は「区別できないから」ではない。**あとで `FORBIDDEN` を返したくなったときのために
書いておく。**書き込みが 0 件で終わったあとに読んで分類する形は、2段階にはあたらない。**
認可は `UPDATE` の1文で既に済んでおり、**そのあと理由を調べても、決定は動かない。**
禁じているのは**「確かめてから書く」であって「書けなかったあとに調べる」ではない。**

## 2. 「ふたりの予定」

`events` に `is_shared`（INTEGER、既定 0）を足す。

### 3 を外したことで、チェックの意味が半分になる

**当初「ふたりの予定」は2つのことを意味していた。**

1. **相手も編集・削除できる**
2. 翌日「会った日」に変わる

**3 を回したので、いま意味するのは 1 だけである。**

- **列と名前（`is_shared`・「ふたりの予定」）は変えない。**3 が入ったときに
  意味が増えるだけで、**列を作り直さずに済む**
- **画面の説明文には、いまできることだけを書く。**
  「相手も編集できます」。**「翌日『会った日』になります」とは書かない**
- **動かない機能の説明を先に書かない。**020 の「準備中です」を避けたのと同じ形である。
  **書いてあるのに起きないのは、書いていないより悪い**

- **`kind = 'plan'` のときだけ立てられる。**入力スキーマで拒否し、**CHECK でも表す**
  （シードが入力スキーマを通らない書き込み口になる。014 と同じ理由）

```sql
CHECK (is_shared = 0 OR kind = 'plan')
```

## 3. 翌日「会った日」に変える（**公開後。このタスクではやらない**）

> **以下は設計として残すだけで、いまは実装しない**（上記「3 は公開後へ回す」）。
> 着手するときは、**下の「同じ日に共有の予定が2件あるとき」を先に決める。**

### 同じ日に共有の予定が2件あるとき（未決定・R の指摘）

`plan` に一意制約は無い（018。**`meetup` 以外は同じ日に何件でも作れる**）。
**同じ日に「ふたりの予定」を2件登録できる。**「昼に映画」「夜にごはん」——
**自然な使い方である。**

その日が過ぎると、**変換が2件とも `meetup` にしようとして
`events_meetup_unique` に当たる。**既存の `meetup` が無いので、
下に書いた回避条件には引っかからない。**2件が互いに衝突する。**

**残す1件をどう選ぶかまで決めないと、B が 0008 の重複解消と同じ形を自分で発明する。**
**3 に着手するときに A が決める。**いま決めても、そのときには前提が動いている。

### 読み取り経路で書き換えない

`event.list` や `stats.get` の中で変換する形は**採らない。**

- **デモは読み取り専用である。**`readProcedure` の中で書き込むと、
  **未認証の閲覧者がデータを変える**ことになる（T5）
- D1 にトランザクションが無く、**同時に読まれると二重に走る**
- 「見せ方だけ変える」形にすると、**`meetupDays` の数え方にも同じ判定が要る。**
  「何を会った日とみなすか」が2箇所に分かれる

### Cron Triggers で1日1回動かす

**先に確認すること。**

- **Cloudflare Workers の無料枠で Cron Triggers が使えるか。**
  使えなければ設計を変える。**使えるはずだ、で進めない**
- ローカルでの動かし方（`wrangler dev --test-scheduled` 等）

**016 でデプロイするまで動かない。**それでよい。

### 変換の規則

- 対象は **`kind = 'plan'` かつ `is_shared = 1` かつ `date` が今日より前**のもの
- **過ぎたものを全部拾う。**「昨日の分だけ」にしない。
  実行が飛んでも次の回で追いつく（**冪等にする**）
- **同じ日に既に `meetup` があるときは、変換しない。予定はそのまま残す**
  - 018 の部分 UNIQUE に当たる
  - **消さない。**その日に会った記録は既にあり、目的は達成されている。
    **人間が入れたものを、こちらの都合で消さない**
- 変換したら `is_shared` を 0 に戻す（`meetup` に `is_shared` は立てられないため）

### 取り消しの導線

**会えなかった予定が「会った日」になるのを、利用者が止められること。**

新しい操作は作らない。**既にあるもので足りる。**

- 予定を**削除する**
- 「ふたりの予定」の**チェックを外す**
- 変換されたあとに「会った日」を**削除する**

ただし**変換されたことに気づけないと、上の3つ目に辿り着けない。**
`meetupDays` はホームの主役の数字である。**気づかないうちに増える。**

**カレンダーで、変換された「会った日」がそれと分かる必要は無い**
（会った事実として同じもの）。
ただし**確認観点として、実際に触って違和感が無いかを見る。**

## テストで証明すること
- **設定者でない側が、共有でない `plan` を更新・削除できない**（両方）
- `is_shared = 1` の `plan` は**どちらでも**更新・削除できる
- `anniversary` と `meetup` は**どちらでも**更新・削除できる（変えていないこと）
- `is_shared` を `plan` 以外に立てられない（入力・CHECK の両方）
- **`canEdit` と、`event.update` が実際に成功するかどうかが一致する**
  （`kind × is_shared × 設定者かどうか` の全組み合わせ。`event.delete` も同じ表で見る）
- **設定者でない側が、記念日・会った日を「非共有の `plan`」に変えられない**
  （`security-requirements.md` 3節の項目8）
- **設定者も、記念日・会った日を「非共有の `plan`」に変えられない**
  （**R の指摘。当初これが通っていた。設定者を主語にしたテストが1件も無かった**）
- **記念日・会った日を「共有の `plan`」にも変えられない**
  （**2回に分けると非共有 `plan` に着けるため。R の指摘**）
- **`plan` を記念日・会った日に変えるのは、どちらでもできる**（広がる向き）
- **記念日 ↔ 会った日 は、どちらでもできる**（区分をまたがない）
- **設定者でない側が、共有の `plan` の共有を外せない**（同上）
- **設定者は、自分の `plan` の共有を外せる**（変えていないこと）
- **`plan` を記念日・会った日に変えるのは、どちらでもできる**（権限が広がる方向）
- `security-requirements.md` 3節の認可テストが緑（件数と内容は出典側を見る）

## 付随: CI に `drizzle-kit generate` の空回しチェックを入れる

**021 の要望とは関係ない。**B が 021 の `generate` で
**親表 `couples` を作り直す差分**を踏んだため、ここで塞ぐ。
0009 のスナップショットに `check()` が1つ欠けていたのが原因で、
**気づかず適用すれば `FOREIGN KEY constraint failed` になる形だった。**

設計と理由は `architecture.md` 4節。**要点だけ。**

- クリーンな作業ツリーで `db:generate` を走らせ、**何も出ないことを確かめる**
- **`git diff --exit-code` は使わない。**`generate` が作るのは
  **新しい `.sql` と新しいスナップショット**で、**どちらも未追跡**である。
  `git status --porcelain` のように**未追跡を見るもの**にする
- **ステップ名に何を見ているかを書く。**`generate` は列の追加と改名を
  区別できないとき対話で聞いてくる。CI に TTY は無いので、そこに当たると
  **「ずれています」ではなく対話の待ち受けが出る**
- `schema-integrity.test.ts` は**これを見ていない**（DB の実体↔期待値であり、
  **スナップショット↔スキーマファイルは通す**）

**独立した PR にしてよい。**021 本体を止めるものではない。
