# 027: 行きたい場所・食べたいものリスト

## 目的

**ふたりで「行きたい」「食べたい」を貯めて、行ったらチェックする。**

人間が `requirements.md` 5節「スコープ外」から次フェーズへ上げるものとして選んだ。

**ホームの「リスト」パネルは既に置いてある**（020。`iconPanelList`・`onPress` 無しで
「次フェーズ」表示）。**027 はそのパネルに `onPress` を付ける作業である。**

## 1. 分類を持たない（A の判断）

`requirements.md` は「行きたい場所・**食べたいもの**リスト」と書いている。
**2つに分けない。1本のリストにする。**

**「カフェ」は場所でもあり食べ物でもある。**
分類させると、**入れる前に迷う。迷わせる分類は、書かれない。**

- 投稿が「本文か画像」だけで種別を持たないのと同じ
- 画面の入力欄のプレースホルダで示す: **「行きたい場所、食べたいもの…」**
- **`kind` 列を作らない。**後から足したくなったら、そのとき足す

## 2. 達成したものを消さない

**チェックを付けたら、リストの下に移る。消えない。**

**このアプリは「時間が経つほど価値が増す」ものである**（`requirements.md` 1節）。
**行った場所が消える設計は、その逆を向く。**

- 未達成が上、達成済みが下。**それぞれ新しい順**
- チェックは**外せる**（間違えて付けたときに戻せる）
- **消したいときは削除する。**削除は論理削除（`requirements.md` 6節）

## 3. `toggle` にしない。`setDone({ id, done })` にする

**現在の状態をサーバに推測させない。クライアントが目標の状態を送る。**

`toggle` だと、二重発火で**行ったり来たり**する。
`setDone` なら**同じ要求が2回届いても結果が同じ**になる
（`conventions.md`「副作用を伴うボタンは二重発火を防ぐ」の、サーバ側の担保）。

**画面側の二重発火防止もやる。**サーバが冪等であることは、
**画面が2回送っていい理由にはならない。**

## 4. 権限はペアで共有。作成者に限定しない

**リストはふたりの共有物である。**どちらが入れたものでも、
**もう1人がチェックでき、削除できる。**

**021（予定の持ち主）はここには持ち込まない。**
021 は**人間が「予定」について出した個別の要望**であって、既定ではない。
既定は `security-requirements.md` 3節の
**「`couple_id` で絞れば、ペアの2人は同じものを見て、同じものに触れる」**である。

**`created_by` は列としては持つが、レスポンスには出さない**（`event.list` と同じ。
**028 で `createdByName`〈表示名〉は出すことにした。ID は引き続き出さない。**
`architecture.md` 5節。**出さないものを画面が使えないようにする**）。

## 5. ページングを入れない。代わりに上限を持つ

**リストは「全部見えること」が価値である。**タイムラインと違う。

- **1回で全件返す**
- **1ペアあたり 200 件を上限とし、サーバ側で拒む**（未削除・達成済みを含む）
- 上限に当たったら `LIMIT_REACHED`。画面は**押す前に**残り枠を出さない。
  **当たってから伝えれば足りる**（200 に当たる利用者はまず居ない）

**上限が無いと「全件返す」が壊れる。**片方だけ決めない。

### 訂正: この上限は「行の総数」の上限ではない（B の指摘。2026-09-01）

**`deleted_at IS NULL` で数えるため、上限がかかるのは「いま並んでいる行数」である。**
追加と削除を繰り返せば、**行そのものは無制限に増える。**

**それでよい。**この上限が守っているのは
**「1回で全件返す」が壊れないこと**であって、ストレージではない。
**触れるのはペアの2人だけで、増やして困るのは本人である。**

**何から守るのかを書く**（`conventions.md` 8節）。
**「上限」と書いただけでは、何の上限か読めない。**

## 6. データモデル

```
wishes
  id          TEXT    PK
  couple_id   TEXT    NOT NULL -> couples.id
  title       TEXT    NOT NULL              -- 1〜100文字。trim 後に空なら拒否
  created_by  TEXT    NOT NULL -> user.id   -- レスポンスには出さない
  created_at  INTEGER NOT NULL
  done_at     INTEGER                       -- 達成したら非NULL
  deleted_at  INTEGER                       -- 論理削除
  INDEX (couple_id, created_at DESC)
```

- **`kind` を持たない**（1節）
- **`done_by` を持たない。**画面に出さない列を足さない
- ~~**`note` を持たない。**title に書けば足りる~~
  → **028 で覆した**（人間の要望「メモ欄を追加して、自由入力できる」）。
  `note` を足し、あわせて `wish.update` を足した
- **CHECK を持たない。**書ける条件が無い（`done_at >= created_at` は
  時計のずれで壊れる。`architecture.md`「CHECK には必ず名前を付ける」は
  **付けるときの話**であって、無理に作る理由ではない）
- マイグレーションは `0016_wishes.sql`。**他表から FK 参照されない**ため、
  `architecture.md` 4節「子テーブルを持つ親テーブル」の問題は起きない

  **訂正（B の指摘。2026-09-01）: これは「参照される側」の話しか書いていない。**
  **`wishes` は `couples` と `user` を参照する側になる。D1 は FK を常に強制する。**
  **024 の `me.delete` に `wishes` の削除文を足さないと、
  wish を1件でも持つペアはアカウント削除が恒久的に失敗する。**
  B が `security-auditor` の監査で発見（High。実装で解消済み）。
  **元の書き方は「FK の心配は無い」と読める。**`architecture.md` 4節
  「表を足したら、消す手順にも足す」を参照
- **`schema-integrity.test.ts` にケースを足す**（`architecture.md` 4節）

## 7. 読むクエリには必ず `deleted_at IS NULL` を含める

**`posts` と同じ規則が、この表にも要る**（`architecture.md` 4節）。

**`posts` の節に「`wishes` も同じ」を書き足すのは A がやる。**
B は実装で守り、**それを固定するテストを書く。**

## 8. 契約（oRPC）

```
wish.list    () -> { items: [{ id, title, doneAt, createdAt }] }
                   未達成が先、達成済みが後。それぞれ createdAt の新しい順
wish.create  ({ title })          -> 作った1件
wish.setDone ({ id, done })       -> 更新後の1件
wish.delete  ({ id })             -> { id }
```

- **すべて `couple_id` スコープ。**他ペアの `id` を渡しても `NOT_FOUND`
  （`FORBIDDEN` にしない。**存在を教えない**）
- **ゲストは書き込みを全てサーバ側で拒む**（014 の方針。UI 側は体験のためだけ）

## 9. T9 の対象である

**`wish.list` は利用者ごとに違う値を返す。**
**キャッシュキーに閲覧者識別子（`viewerKey`）を含める**
（`architecture.md` 5節。`viewer-key-coverage.test.ts` の走査対象に入る）。

**画面が増えるとき、そこが漏れる**（025 で同じことを書いた）。

## 10. デモに入れる

**「リスト」パネルが押せるようになる。**空のリストがデモで最初に出るのは弱い。

- `packages/db/seed/demo.ts` に**決定的に**組み立てて入れる（乱数を使わない）
- **達成済みと未達成の両方**を入れる。並び順が見えるようにする
- **実在の店名を入れない**（014 で写真1枚を落としたのと同じ理由。
  `docs/sample/README.md`）

## 11. 画面

**`(tabs)/list.tsx`。ボトムタブには出さない。**

- **`(tabs)` の中に置く。**ボトムタブを消さない（`architecture.md` 3節）。
  `memory.tsx`・`stats.tsx` と同じ扱い
- ホームの「リスト」パネルから `router.push("/list")`
- **入力はモーダルにしない。**画面上部に1行の入力欄と追加ボタンを置く。
  **1行しか入れないものにモーダルは重い**
- 3状態（読み込み中 / 空 / エラー）をすべて持つ（016 で全画面に入れた規則）
- 空のとき: **「まだ何もありません」で終わらせない。**何を入れる場所かを書く

## テストで証明すること
- **他ペアの `id` を渡すと `NOT_FOUND`**（`setDone`・`delete` の両方）
- **ゲストは `create`・`setDone`・`delete` のいずれも通らない**
- **`setDone` が冪等である**（同じ `done` を2回送っても結果が変わらない）
- **削除した行が `wish.list` に出ない**（`deleted_at IS NULL`）
- **201 件目が `LIMIT_REACHED` で拒まれる**
- **並び順**（未達成が先、達成済みが後、それぞれ新しい順）
- **`title` が trim 後に空なら拒む**
- キャッシュキーに閲覧者が含まれる（T9）
- `schema-integrity.test.ts` に `wishes` のケースがある

## 確認観点
- 入れたものが**すぐ見えるか**
- チェックを付けたとき、**消えずに下へ移るか**
- **チェックを外せるか**
- ゲストで開いたとき、**入力欄が押せる形で置かれていないか**
  （押してからサーバに拒まれる形にしない。014 の導線に合わせる）
