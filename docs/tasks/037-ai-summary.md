# 037: AIまとめ

## 目的

**その月の投稿を、LLM に短くまとめさせる。**

人間の指示。**ホームの「AIまとめ」パネルは 020 で置いてある**（`iconPanelAi`・COMING SOON）。
**027・029 と同じで、そこに `onPress` を付ける作業である。**

**「AIまとめを使用する」にチェックを入れた人だけ使える。**
**OpenAI のキーを使う予定だが、Claude API のキーでも動くようにする。**

## 0. 前提が1つ変わる

`requirements.md` 5節は、これを**「LLM API コストが無料運用と衝突する」**として
スコープ外に置いていた。

**その理由は消えていない。**費用は運営（＝人間）が持つ。
**だから歯止めを設計に入れる**（5節）。

**そしてオプトインの理由は費用ではない。**下記。

## 1. オプトインの意味は「外部へ送ること」への同意

**AIまとめは、投稿本文を OpenAI か Anthropic に送る。**

ADR-012 で**「運営は全部読める。対策していない」**と決めた。
**それは運営の話である。外部の第三者へ渡すのは別の話である。**

**チェックが要るのは、費用のためではなく、そこへの同意のためである。**

### 2人とも同意していないと使えない

**投稿はふたりのものである。**

**片方の同意で、相手の投稿を外部へ出さない。**

- `couple_members` に **`ai_opt_in`** を持たせる（**個人ごと**）
- **2人とも 1 のときだけ**生成できる
- **1人のペアでは使えない**（相手がまだ居ないので同意が取れない）
- **相手が同意していないとき、画面にそう出す。**「相手の同意を待っています」

**ADR-012 の「身内だけ」と同じ論法である。前提が揃っていないなら、動かさない。**

## 2. キーは運営が持つ。利用者に入れさせない

**`wrangler secret`。**ローカルは `.dev.vars`。

**利用者に自分の API キーを入れさせない。**

**ADR-012 で「運営は全部読める」と決めている。**
**利用者のキーを預かると、運営がそれを読めることになる。**
**自分のデータを読まれるのと、自分の課金に使えるキーを読まれるのは、重さが違う。**

## 3. プロバイダを切り替えられるようにする

| 環境変数 | 中身 |
|---|---|
| `AI_PROVIDER` | `openai` または `anthropic` |
| `OPENAI_API_KEY` | OpenAI のキー |
| `ANTHROPIC_API_KEY` | Anthropic のキー |

- **`AI_PROVIDER` が指すプロバイダのキーが無ければ、起動時に落とす**
  （`BETTER_AUTH_SECRET` と同じ fail-closed。`architecture.md` 8節）
- **`apps/api/src/lib/ai.ts` に窓口を1つ作る。**
  手続きからはプロバイダが見えない形にする
- **両方のキーを同時に読まない。**`AI_PROVIDER` で決まる方だけ

**モデル名も環境変数にしない。**`lib/ai.ts` の中に、プロバイダごとの既定を書く。
**環境変数を増やすほど、本番とローカルがずれる経路が増える。**

## 4. 月次と週次の両方を作る（2026-09-06。人間の指示で追加）

~~まず月次だけ。週次を足すかは、月次が使われてから決める。~~

**人間から「週間も欲しい」との要望。足す。**

**私が「週の投稿は少なすぎる」としたのは見立てであって、実測ではない。**
**使う人が要ると言っているなら、そちらが正しい。**

### 期間を1つの表で持つ

**`month` 列をやめ、`period_kind` と `period_key` にする**（6節）。

| `period_kind` | `period_key` | 例 |
|---|---|---|
| `month` | `YYYY-MM` | `2026-08` |
| `week` | `YYYY-Www` | `2026-W36` |

**まだ本番に出ていない。いま変える方が安い。**

### 週の定義

**ISO 8601（月曜始まり）。JST で計算する。**

**`packages/date` に置く**（`architecture.md` 5節「日付計算は `packages/date` に置く」）。
**手続きの中で週を計算しない。**

### 投稿の下限は週も3件のまま

**期間で基準を変えない。**変えると**週だけ薄いまとめが出る。**

**3件に満たない週は生成できない。それでよい。**

### 歯止めを2段にする

**週次を足すと、生成の回数が跳ねる**（月3 + 週5×3 = 18回/月）。

| | |
|---|---|
| **期間ごと** | **3回まで**（作り直しの余地） |
| **1ペア・1暦月の合計** | **10回まで** |

**片方だけでは止まらない。**期間ごとだけだと総量が跳ね、総量だけだと1つの期間で使い切れる。

## 5. 費用の歯止め（設計に入れる）

| | |
|---|---|
| **生成の回数** | **1ペア・1ヶ月あたり3回まで。**作り直しの余地は残す |
| **入力の長さ** | **その月の投稿本文の合計を 8000 文字で切る。**超えたら**古い方から落とす** |
| **画像を送らない** | **本文だけ。**画像は外部へ出さない |
| **生成した結果は保存する** | 開くたびに叩かない |
| **投稿が3件未満の月は生成しない** | まとめる中身が無い |

**「押すたびに課金される」形にしない。**

## 6. データモデル

```
couple_members
  ...
  ai_opt_in  INTEGER NOT NULL DEFAULT 0   -- 037。個人ごとの同意

ai_summaries                              -- 037
  couple_id   TEXT    NOT NULL -> couples.id
  period_kind TEXT    NOT NULL            -- 'month' | 'week'
  period_key  TEXT    NOT NULL            -- 'YYYY-MM' | 'YYYY-Www'（JST・ISO 8601）
  body        TEXT    NOT NULL
  provider    TEXT    NOT NULL            -- 'openai' | 'anthropic'
  model       TEXT    NOT NULL
  generated_count INTEGER NOT NULL DEFAULT 1  -- 期間ごと3回
  created_at  INTEGER NOT NULL
  updated_at  INTEGER NOT NULL
  PRIMARY KEY (couple_id, period_kind, period_key)
  CONSTRAINT ai_summaries_provider_check CHECK (provider IN ('openai','anthropic'))
  CONSTRAINT ai_summaries_period_kind_check CHECK (period_kind IN ('month','week'))
```

- **`provider` と `model` を残す。**あとで「どのモデルが書いたか」が分からなくなる
- **CHECK に名前を付ける**（`architecture.md` 4節）
- `couple_members` は**他表から FK 参照されない**ので `ALTER TABLE ADD COLUMN` が通る
  （**実測してから書くこと**）

### `me.delete` に `ai_summaries` の削除文を足す

**4回目である**（027 `wishes` / 029 `moods` / 031 `post_images` / 037 `ai_summaries`）。

**`ai_summaries` は `couples` を参照する側。D1 は FK を常に強制する。**
**足さないと、まとめを1件でも持つペアはアカウント削除が恒久的に失敗する。**

**032 で入れた「残ってよい行以外は0件」の走査に、これは自動で映る。**
**映ることを確かめること。**

## 7. 契約

```
me.get              -> ... aiOptIn: boolean, partnerAiOptIn: boolean を足す
me.setAiOptIn       { optIn: boolean } -> { aiOptIn }
                    自分の分だけ。user_id を引数に取らない（029 と同じ）
aiSummary.get       { periodKind, periodKey } -> { body, provider, model, updatedAt, generatedCount } | null
aiSummary.generate  { periodKind, periodKey } -> 生成して保存し、同じ形を返す

                    投稿が3件未満なら INVALID_INPUT
                    その期間の4回目は LIMIT_REACHED
                    その暦月の11回目も LIMIT_REACHED
```

- **未来の期間は拒む。**今月・今週も**終わっていないので拒む**
- **T9 の対象。**`aiSummary.get` のキャッシュキーに `viewerKey` を含める

## 8. 出力を信用しない

**投稿本文は利用者が書く。それが LLM への入力に入る。**

**LLM の出力は、表示するだけにする。**

- **リンクにしない。**出力の中の URL を押せる形にしない
- **マークダウンを解釈しない。**素のテキストとして出す
- **出力から何かを実行しない**

**プロンプトインジェクションで書き換えられても、表示が変になるだけで済む形にする。**

**入力に入れるのは本文と、投稿ごとの匿名の記号（A / B）だけ。**
**利用者名・メールアドレス・画像・ID を入れない。**

記号は **`couple_members.slot` から機械的に決まる**（slot 1 が A、2 が B）。
**個人を特定しない。**「どちらが書いたか」がまとまりに出るために要る（人間の指摘）。

**本文の中に名前が書かれていれば、A が誰かは分かる。だが本文はもともと送っている。
記号そのものは情報を増やしていない。**

**R が挙げたもう1案（注入数27を厳密に固定する）は採らない。**

## 直し方（A の判断: R の言う「安い方」を採る）

**`orpc` という識別子への参照を全部集め、そのそれぞれが
「認識できる使われ方で終わっているか」を見る。**

**穴は「`orpc` からどうやって辿ったか」の形にあって、辿った先の型ではない**（R の見立て）。
**`orpc` 識別子そのものを起点にすれば、辿り方の全部が視界に入る。**

**`ts.createProgram` + TypeChecker にはしない。**遅くなるうえ、
**型で追う必要があるのは、いま壊れている理由ではない。**

### 識別子の名前を `import` 文から取る

```ts

```

**`lib/orpc` から入ってきた識別子の名前を `import` 文から取り、その識別子への参照を集める。**
**別名にされても外れない。**

### 守る範囲を書く（範囲の外を明示する）

**それが起きたら、そのとき考える。**
**いま無理に広げない。ただし「守っていない範囲」として書く**

## 1. 名前空間 import — 入口の形を1つに決める


`isOrpcQueryCall` にも一致しない。**2枚とも外れる。**

**穴は無くなったのではなく、使用箇所から import 箇所へ移った。**
**`import` 行1本で、そのファイルの網が全部消える。**

### 判断: `ts.isNamespaceImport` を追わない。入口を1つに固定する

**「`lib/orpc` を import する行は、名前付き import でなければならない」を、
別の検査として固定する。**

- **`import * as ...` も `import 既定 ...` も赤**
- **別名（`import { orpc as x }`）は許す。**名前は `import` 文から取れる

**入口の形を1つに決めれば、中で何を追うかの話に戻せる**（R の言葉）。
**`isNamespaceImport` を足すのは、同じ追いかけっこの延長である。**

## 2. 短縮記法の誤検知 — 許す（変数を1段だけ辿る）

```ts
const queryKey = [...orpc.stats.get.queryOptions().queryKey, viewerKey];
```

**「viewerKey が確認できません」と言われた人が、有るものを探すことになる。**
**これが一番悪い壊れ方である。**

- **短縮記法のとき、同じスコープの変数宣言を1段だけ辿る**
- **辿れなければ赤**（fail-closed のまま）
- **1段だけ。**それ以上は追わない

**片方を緩めても、もう片方の網は緩まない。**
