# 014: ゲストデモモード

## 目的
未ログインでアプリの中身が見える状態を作る。
面接官がログインの壁で離脱するのが最大の損失であり、このタスクは
「動くプロダクトのURL」という評価軸そのものを支える。

## 変更対象ファイル
- （新規）`packages/db/migrations/xxxx_event_checks.sql` — `events` に CHECK を2本
- （新規）`packages/db/seed/demo.ts` — デモペアのシードデータ投入
- （新規）`apps/app/components/demo-banner.tsx`
- `apps/app/app/(auth)/sign-in.tsx` — 「ゲストではじめる」を有効化
- `apps/app/` 各画面 — 書き込み系UIの抑制
- `apps/api/wrangler.toml` — `DEMO_COUPLE_ID`

## 実装内容

### サーバ側（005 で既に土台がある）
- 005 の認可ミドルウェアが未認証時に `couple_id = DEMO_COUPLE_ID` / `mode = 'readonly'` を設定済み
- `writeProcedure` が `readonly` を `FORBIDDEN` にすることを**改めてテストで確認する**
- **UI側の制御に依存しない。** サーバ側の拒否が唯一の防御線

### シードデータ
- デモ用の couple（`is_demo = 1`）と、架空の2人のユーザーを作る
- 過去1年半にわたる投稿を30〜50件（画像付きを含む）
- リアクションを散らす

### `events` に CHECK を足すマイグレーション

シードが**入力スキーマを通らない2つ目の書き込み口**になるため、
`architecture.md` 5節のとおり CHECK を2本足す。**このタスクの作業である。**

```sql
CHECK (repeat_yearly = 0 OR kind = 'anniversary')
CHECK (time IS NULL OR kind <> 'anniversary')
```

#### 生成された SQL に `CREATE INDEX` が2本入っていることを目視で確認する

**SQLite に `ALTER TABLE ... ADD CONSTRAINT` は無い。**
drizzle-kit は**新テーブルを作って全行コピーし、旧テーブルを DROP して改名**する
（0006 の `reactions.kind` がその形だった）。

**`DROP TABLE events` で、表定義の外にある索引2本が消える。**

```
events_couple_date_idx    (couple_id, date)                      -- 0007
events_meetup_unique      (couple_id, date) WHERE kind='meetup'  -- 0008
```

再作成の `CREATE INDEX` が生成物に入っていなければ、
**018 で入れたばかりの一意化が黙って消える。**

テストは全マイグレーションを適用してから走るので、
「同じ日に2件目の `meetup` を作ると1件のまま」が失敗して気づける。**安全網は効く。**
それでも**生成物を読まずに通さない。**

#### 適用の前に、CHECK に違反する既存行を数える

`INSERT INTO __new_events SELECT ... FROM events` は、
**1行でも CHECK に違反すれば失敗する。**0008 で重複を先に潰したのと同じ構造である。

```sql
SELECT COUNT(*) FROM events WHERE repeat_yearly = 1 AND kind <> 'anniversary';
```

- `time` の方は 0008 で追加した列であり、その時点で既に検証があったため
  **違反する行は存在しえない**
- 上の行が作れたのは **PR #96 で検証を入れる前に API を直接叩いた場合だけ**で、
  011 の UI は常に `kind === "anniversary"` を送る。**おそらくゼロ**

**見つかった場合、0008 と同じ「消す」は採らない。人間が入れた本物の予定である。**
`UPDATE events SET repeat_yearly = 0 WHERE ...` にする。

**0008 もまだリモート未適用**（L73）なので、0008 と 0009 が一緒に走る。
片方だけ通って片方が落ちる形になるため、**この確認は 0008 の適用前に済ませる。**

#### シードは何度でも実行できること

**最低2回走る。**014 のローカルと、016 の本番である。
016 で一度で成功する保証も無い。

018 で `meetup` に部分 UNIQUE を入れたため、**2回目は UNIQUE 違反で途中で落ちる。**
投稿は入ったがイベントは入っていない、という**半分だけ入った状態**が残る。

**投入の前にデモペアの既存行を消す。**

- 消すのは **`is_demo = 1` の couple に属する行だけ。**他のペアに触れない
- 外部キーの順に、**`couple_id` を持つ全ての表**を消す
  （`reactions` → `posts` → `events` → `invites` → `couple_members` → `couples` → `user`）。
  **表が増えたときにここへ足す**
- **デモの couple と架空の2人の user の id は、シード内の定数として宣言する。**
  `crypto.randomUUID()` で作らない。実行のたびに id が変わると、
  `wrangler.toml` の `DEMO_COUPLE_ID` が古い id を指したまま**ゲストデモが
  `FORBIDDEN` になる**（005 の項目6が正しく効いて拒否される）。
  R2 の鍵 `couples/{coupleId}/...` も変わり、**上書きにならず孤児が溜まる。**
  再実行のたびに `wrangler.toml` を書き換えて再デプロイする運用は現実的でない
- **R2 の画像は消さなくてよい。**孤児が残るが、鍵は `couples/{coupleId}/...` で
  同じ `coupleId` を使い回せば上書きになる（`architecture.md` 6節）

#### イベントの件数は種類ごとに指定する

**「合わせて20件」では統計カードの主役の数字が作れない**（R の指摘）。

`meetupDays` は `kind='meetup'` の件数そのものであり、**シードの件数が
そのままホーム最上部に出る。**20件を3種類に割ると7件前後になり、
**「1年半で7日しか会っていない」**と読める。改名で数字の意味が確定したぶん、
少なさが目立つ。

| 種類 | 件数 | 備考 |
|---|---|---|
| `meetup` | **80〜100件** | 1年半（約547日）で週1〜2回。`daysTogether` と並べて自然に見える数 |
| `plan` | 5〜8件 | **未来の日付を含める。**カレンダーに予定が入る様子が見える |
| `anniversary` | 3〜5件 | 付き合った日・誕生日など |

#### 日付に乱数を使わない

**`meetup` の日付は決定的に決める。**一定間隔で刻むか、日付の集合を作って
重複を除く。**乱数で散らさない。**

1年半に8件をランダムに置くと同じ日に当たる確率は約5%である。
**低いが、落ちるときと落ちないときがある。**ローカルで通り、016 の本番投入で落ちる。
`memory.get` で `ORDER BY RANDOM()` を使わないと決めたのと同じ理由（013）。

#### 018 で足した項目をデモで見せる

人間が実機で求めた3件は、**デモで見えなければ意味が無い。**
面接官が触るのはデモの方である。

- **`created_by` を2人に振り分ける。**全部を同じユーザーで作ると、
  カレンダーに同じ名前だけが並び、「どちらが設定したか分かる」が伝わらない
- **`time` は有りと無しを混ぜる。**全部に入れると任意項目だと分からず、
  全部空だと機能があることが分からない

#### DB の制約を通ること

シードは**入力スキーマを通らない2つ目の書き込み口**である。
018 で `events` に CHECK を足した（`architecture.md` 5節）ので、
**`repeat_yearly = 1` の `meetup` や、時間付きの `anniversary` を書くと落ちる。**

**落ちるのが正しい。**契約経由では作れないデータをシードだけが作れる状態にしない。
- **1ヶ月前・半年前・1年前の日付に必ず投稿を置く**（013 の思い出しがデモで確実に出るように）
  - **これも乱数に頼らない。**「1ヶ月前」は `packages/date` の `monthsBefore` で
    求めた日付そのものに置く（存在しない日は月末に寄る。`architecture.md` 5節）
- 「付き合って○日目」がそれらしい数字になるよう `anniversary_date` を設定する

### シードデータの内容についての制約（`docs/security-requirements.md` 1節）
- **実在の人物の写真を使わない**
- **実際の出来事・実際の会話を書かない**
- 画像はフリー素材または生成画像を使い、出典を `packages/db/seed/README.md` に記録する

#### 使う素材は決めてある

`docs/sample/` に配置済み。**出自はすべて AI 生成で、`docs/sample/README.md` に記録済み。**
`packages/db/seed/README.md` からその記録を参照すること（旧 L3）。

| 用途 | 素材 |
|---|---|
| デモペアのアバター | `プロフィール画像/woman1.jpg`（女性）・`man1.jpg`（男性） |
| 投稿の写真 | `風景/` の**5枚**（`eHaCqEMx.jpg` は**使わない**。架空のブランド看板が写り込んでいる） |

**デモペアは男女である。**投稿写真4枚に写っている男女のカップルと揃っている（L55）。

- 投稿30〜50件に対して写真は5枚しかない。**同じ写真を何度も使い回さない。**
  写真付きは5〜8件程度に絞り、残りは本文のみにする。
  実際の利用でも全投稿に写真が付くわけではないので、その方が自然に見える
- **シードに圧縮のコードを書かない。圧縮済みの画像をコミットする。**
  原本のままだと1枚1MB前後あり、デモの表示が重くなるので圧縮は要る。
  ただし圧縮の実装を書くと、**長辺1600px / 品質0.8 という同じ規則が
  `apps/app/lib/image.ts` と2箇所になる**（L63 の日付計算と同じ形）。
  シードは Node、クライアントは `expo-image-manipulator` で、実装を共有できない。

  **一度だけ圧縮した結果を `packages/db/seed/assets/` に置く。**
  シードはそれを R2 へ入れるだけにする。**規則を持つ場所を1つに保つ**

### クライアント側
- ログイン画面の「ゲストではじめる」からデモに入れる
- 画面上部に常時バナーを出す:「これはデモです。ログインすると自分のふたりの記録を残せます」
- 投稿・リアクション・イベント登録のUIを、押せない状態にするか、押すとログインを促す
- FAB はログイン導線に差し替える

## 確認観点
- 未認証で書き込み系の手続きがすべて `FORBIDDEN` になるか（サーバ側で確認する）
- 未認証で**デモペア以外**のデータが一切取得できないか
- デモのシードデータに実在人物・実際の出来事が含まれていないか
- 同じ写真が何度も出てこないか
- デモから抜けて通常ログインできるか
