# 032: 削除の網を、表の名前ではなく「残っていないこと」で張る

## 目的

**`me.delete` の網から `post_images` と `reactions` が漏れている。**

R が 031 のレビューで報告した。**いま実害は無い**（どちらも手で書いた削除文が
正しく動いている）。**次の表で漏れる。**

## 1. いまの網

`apps/api/test/me.test.ts` の
**「`couple_id` 列を持つ全ての表で、`me.delete` 後にそのペアの行が0件になる」**
は、027 で `wishes` を落として High を出したあとに入れたものである。

**よくできている。**`sqlite_master` の `CREATE TABLE` 文字列から `couple_id` を
拾い、**消す前に行が実在することも要求している**（空振りの緑を防いでいる）。

**`couple_id` を持たない表が映らない。**

| 表 | 持っている列 | 網に映るか |
|---|---|---|
| `posts` `events` `invites` `couple_members` `wishes` `moods` | `couple_id` | **映る** |
| **`reactions`** | `post_id` | **映らない** |
| **`post_images`**（031） | `post_id` | **映らない** |

**2つが既にその位置にいる。**

## 2. 「`post_id` も見る」にしない

**列の名前を並べる形にすると、3つ目の名前が出たときにまた漏れる。**

`couple_id` → `post_id` と足していくのは、**手で維持する一覧に戻ることである。**
027 でそこから離れたのに、戻ることになる。

## 3. 「全表が0件」に変える

**ペアを1つだけ作った状態で `me.delete` したあと、残ってよい表以外は全部0件。**

**join の経路を辿らなくてよい。**テストのDBにはそのペアのデータしか無いのだから、
**「0件」だけを見れば足りる。**

- **何ホップ先の表でも映る。**`post_images` も、将来の3ホップ目も
- **列の名前に依存しない**

### 免除は「表」ではなく「残ってよい行の条件」で書く

**表ごと免除を作らない。**（R が 032 のレビューで指摘。**重要である**）

`session` と `account` に残るのは**相手の分だけ**である。
**表の名前だけで免除すると、自分の `session` が消えていなくても鳴らない。**
**ログアウトされていないことを見逃す**——T8 と再認証（024）に直結する。

| 表 | 残ってよい行 | 理由 |
|---|---|---|
| `user` | **自分以外** | 相手のアカウントは消さない（024） |
| `session` `account` | **自分以外** | 自分の分は `user` への CASCADE で落ちる |
| `verification` | 全部 | Better Auth の作業行。利用者に紐づかない |
| `invite_failures` | 全部 | **消さないと決めた**（PR #186。時間窓1時間で切れる。`user` への FK も外した） |

**上は R が1ペア・2人で実測した結果である**（`couples` は残らなかった）。
**それでも B は自分で実測して確かめること。**写した一覧は写した時点のものである。

`viewer-key-coverage.test.ts` の `MANUALLY_PLACED_CACHE_KEYS` と同じ枠だが、
**登録するのは表名ではなく条件である。**

### `sqlite_sequence` は走査から外す

`invite_failures.id` が `INTEGER PRIMARY KEY AUTOINCREMENT` のため、
**SQLite の内部表 `sqlite_sequence` が存在する**（R が実測）。

- **`name NOT LIKE 'sqlite_%'` で外す**（既存の `couple_id` 走査と同じ形）
- **免除の一覧には入れない。**アプリの表ではないものをアプリの判断として
  登録すると、**次に読む人が「これは消すべきなのか」と考える**
- **外した理由をその場に書く。**外し方だけ書くと、なぜ外したかが消える

## 4. 消す前のチェックは、そのまま残す

いまの網が持っている**「消す前に行が実在すること」**の要求を落とさない。

**新しい表が増えたら、テストデータを足さないと落ちる。**
**それがこのテストの本体である。**気づかせたいのはそこである。

- **`couple_id` を持つ表**は、いまと同じくペアの行が実在することを要求する
- **それ以外の表**は、`me.delete` の前に**1行以上あること**を要求する
  （どのペアの行かを判定しなくてよい。DBにはそのペアしか居ない）

**これが3つのもれを同じ場所で鳴らす**（R の整理）。

| もれ | 鳴り方 |
|---|---|
| **テストデータのもれ** | 削除前に0件で落ちる |
| **削除文のもれ** | 削除後に行が残って落ちる |
| **登録のもれ** | 残ってよいと書いていない行が残って落ちる |

**行があったことを前提にしないと、「消えた」と「そもそも空だった」を
区別できない。**

## 5. 既存の走査を消さない。ただし理由を書き直す

**当初「落ちたときにどの表かが分かるから」と書いた。理由として弱い**
（R の指摘）。**全表0件の側も、表ごとに数えて名指しできる。**
**エラーメッセージの精度だけなら、片方に寄せられる。**

**2つが主張していることが違う。**

| 走査 | 主張 |
|---|---|
| `couple_id` を持つ全表 | **その列で直接スコープされて消えている。**他の表への CASCADE や join 経由で偶然消えたのではない |
| 残ってよい行以外は0件 | **どこにも残っていない。**何ホップ先でも |

**片方が通ってもう片方が落ちる状況がありうる。**だから2つある。

## テストで証明すること
- **`post_images` と `reactions` が網に映る**（031 の前は映っていなかった）
- **登録の無い行が残っていたら落ちる**（実際にその状況を作って確かめる。
  **落ちることを見てから通す**）
- **自分の `session` が残っていたら落ちる**（表ごと免除にしていないことの証明。
  **ここが表名での免除と条件での免除を分ける唯一の点である**）
- **消す前に行が無い表があったら落ちる**（空振りの緑にならない）
- 既存の `couple_id` 走査が、いままでどおり動く

## 確認観点

- **「残ってよい」と書いたものが、本当に残ったか**（実測したか）
- 新しい表を1つ足したつもりで、**このテストが落ちるか**
