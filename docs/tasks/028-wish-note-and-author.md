# 028: リストにメモと設定者を足す

## 目的

人間の要望（原文）。

> **設定者の名前を表示。編集権限は両方。メモ欄を追加して、自由入力できる。**

**027 の決定を2つ覆す。**覆すこと自体が目的である。

| 027 で決めたこと | 028 |
|---|---|
| `created_by` はレスポンスに出さない | **`createdByName` を出す**（`event.list` と同じ形） |
| `note` を持たない。title に書けば足りる | **`note` を足す** |
| 権限はペアで共有。作成者に限定しない | **変えない。**下記 2節 |

**B が「自分の一存でスキーマと契約を変えることになる」として上げてきた。正しい。**

## 1. 設定者の名前を出す

`event.list` の `createdByName` と**同じ形にする。**別の形を増やさない。

- **`createdByName`（表示名。null 許容。LEFT JOIN）を返す**
- **`created_by`（ユーザーID）は返さない。**027 と `event.list` の方針は維持する
  （`architecture.md` 5節。**出さないものを画面が使えないようにする**）

### 設定者は、編集しても変わらない

**`created_by` を更新しない。**

相手がメモを書き足しても、**言い出したのが誰かは変わらない。**
**「あなたが行きたいって言ってたところ」が残ることに価値がある。**

## 2. 権限は変えない。だが「変わらない」ことを確かめる

**「編集権限は両方」は 027 の現状である**（`security-requirements.md` 3節の既定。
**ペアの2人は同じものに触れる**）。**変更は要らない。**

**ただし、名前が出ると「その人のもの」に見える。**

- **`canEdit` を返さない。**返すと 021（予定の持ち主）と同じ仕組みに見え、
  **将来「なぜ常に true なのか」と読まれる。**
  返さないことで「2人とも触れる」が構造として表れる
- **画面で、名前を「持ち主」に見せない。**押せる／押せないの差を名前の横に作らない
- **テストで固定する。**「相手が入れた wish を、もう1人が更新・削除できる」
  （`conventions.md`「『◯◯のまま』と書くなら、変わらないことを確かめてから書く」）

**要望のうち1つが「現状維持」のとき、確かめずに現状維持と書かない。**

## 3. メモ

- **`note TEXT NOT NULL DEFAULT ''`。**任意。空でよい
- **上限は 200 文字**（trim 後）
- **一覧にそのまま出す。折りたたまない**

### なぜ 200 文字か、なぜ折りたたまないか

- **`title` の 100 文字では足りない。**URL や住所だけで埋まる
- **`post.body` の 2000 文字は日記の長さである。**メモは日記ではない
- **200 文字なら一覧に出しても一覧が壊れない。**
  折りたたみを入れずに済み、**画面を増やさずに済む**
- **折りたたみは「読まれない場所」を作る。**
  リストは**一覧で読み切れる**方がよい

**上限と表示の仕方はセットで決める。**片方だけ決めると、もう片方に無理が来る
（027 の 200 件上限と「1回で全件返す」と同じ関係）。

## 4. 編集を足す（027 から増える）

**027 は「編集は無し。間違えたら消して入れ直す」だった。メモを足すと成り立たない。**

メモは**あとから書き足したくなる**（行ったあとのひとことなど）。
消して入れ直すと、**チェック状態と `created_at` と設定者が失われる。**

```
wish.update  { id, title?, note? } -> 更新後の1件
```

- **`title` も編集できる。**メモだけ編集できて題名が編集できないのは説明できない
- 渡されなかった項目は変えない
- `title` は変更後も 1〜100 文字・trim 後に空なら拒否
- **他ペアの `id` は `NOT_FOUND`**（027 と同じ。存在を教えない）
- **ゲストは通らない**（サーバ側で拒む）

## 5. マイグレーション

`0017_wishes_note.sql`。**`ALTER TABLE wishes ADD COLUMN note TEXT NOT NULL DEFAULT ''`。**

- `wishes` は**子テーブル**であり、表の作り直しは起きない（`architecture.md` 4節）
- **行を消さない。**件数を数える手順は要らない（`architecture.md` 4節）
- 既存行は空文字になる。**`migration-existing-rows.test.ts` にケースを足す**
- `schema-integrity.test.ts` の `wishes` のケースを更新する

## 6. デモに入れる

- **メモのある wish と、無い wish の両方**を入れる
- **設定者が2人に分かれるように入れる。**名前が出ることが見えない
- **実在の店名を入れない**（027 と同じ）

## テストで証明すること
- `wish.list` が **`createdByName` を返し、`created_by` を返さない**
- **相手が入れた wish を、もう1人が更新・削除できる**（2節。現状維持の確認）
- **`wish.update` で `created_by` が変わらない**
- 他ペアの `id` を渡した `wish.update` が `NOT_FOUND`
- ゲストは `wish.update` を通れない
- `note` が trim 後 200 文字を超えたら `INVALID_INPUT`
- **`note` が空でも作れる・更新できる**
- 渡さなかった項目が変わらない（`title` だけ更新したとき `note` が残る）
- 既存行が空の `note` を持つ（マイグレーション）

## 確認観点
- **誰が入れたかが読めるか**
- **名前が出ていても、もう1人が触れることが分かるか**（「持ち主」に見えていないか）
- メモを**あとから書き足せるか**
- メモが長いとき、**一覧が読めるままか**
