# 034: `pnpm audit` の通信失敗にリトライを入れる

## 目的

**npm のセキュリティ勧告 API へのアクセスが落ちて、CI とデプロイが止まっている。**

2026-09-04 に**5回**（PR の CI で3回、`deploy.yml` で2回）。
どちらも `https://registry.npmjs.org/-/npm/v1/security/advisories/bulk` への
POST が `error (23)` / `503` でタイムアウトしている。

**デプロイが2回とも、マイグレーション適用の手前で止まった**（本番DBには影響なし）。

## 1. 緩めない。耐える

**これは通信の失敗であって、監査の結果ではない。**

| | |
|---|---|
| **`continue-on-error` を付ける** | **採らない。**ゲートが消える |
| **無視リストに足す** | **採らない。**無視リストは**勧告の中身**に対する判断であり、通信の失敗には効かない |
| **通信のリトライを入れる** | **採る。**`pnpm audit` は同じ厳しさで走る。**緩めていない** |

**通信の失敗に耐えることと、監査を甘くすることは別である。**

## 2. 訂正: pnpm は既にリトライしている（起票時に確かめていなかった）

**私は「3回、1秒 → 2秒 → 4秒」と書いた。実測を見ずに書いた。誤りである。**

B が出したジョブログ:

```
[WARN] POST .../security/advisories/bulk error (23). Will retry in 10 seconds. 2 retries left.
[WARN] ...error (23). Will retry in 1 minute. 1 retries left.
[23] The operation was aborted due to timeout
```

**pnpm は既に2回リトライしている**（10秒 → 1分。計3分待っている）。
**外側に「1秒 → 2秒 → 4秒」を足すのは、内側より短い待ちを重ねるだけで、
何も足していない。**

**やることは、外側にリトライを足すことではなく、pnpm の待ちを延ばすことである。**

- `fetch-retries` / `fetch-retry-mintimeout` / `fetch-retry-maxtimeout` /
  `fetch-timeout`（`.npmrc`）。**どの設定が audit の通信に効くかを実測してから書く**
- **「この設定で効くはず」で書かない。**効いていることを、
  **待ち時間がログで伸びたことで確かめる**

### 尽くしても駄目なら赤。逃げ道を作らない

**「N回失敗したら通す」にしない。**それは `continue-on-error` を回数で書いたものである。

**長時間落ちていたら、どれだけ延ばしても通らない。そのときは待つ。**

- **人間が承認したら audit を飛ばせる経路**を作らない。
  **「一時的に飛ばす」は常態化する**
- **futary は2人用の個人アプリで、緊急のデプロイが要る場面が無い。**
  止まって困るのは**機能追加が出せないことだけ**である。**待てる**
- **可用性を監査に従属させる。それがこの製品では正しい**

**逃げ道は、障害が終わったあとも残る。**

## 3. リトライするのは通信の失敗だけ（ここが一番大事）

**脆弱性が見つかって赤くなったものを、リトライしてはいけない。**

**`high` の勧告が出て赤くなったのに3回やり直す**——これは**ゲートを回数で溶かす**ことである。**絶対にやらない。**

### 先に実測すること

**終了コードだけで区別できるか、出力を見る必要があるかを、実測してから決める。**

1. **脆弱性で落ちたとき**の終了コードと出力
2. **通信で落ちたとき**の終了コードと出力（**当日のログが `artifacts/033/` と
   ジョブログにある。`error (23)` と `TimeoutError`**）

**区別できないなら止めて A に上げる。**
**「たぶん区別できる」で書かない。**区別を間違えると、**脆弱性を通す。**

## 4. リトライを1箇所に置く

**audit がレジストリを叩く場所は3つある。**

| ステップ | 叩くか |
|---|---|
| `pnpm audit \|\| true`（全重大度・出力のみ） | 叩く。**失敗しても止まらないので実害は無いが、時間を捨てる** |
| `pnpm audit --audit-level=high`（ゲート） | **叩く。ここが止まっている** |
| `node scripts/check-audit-ignore-staleness.mjs`（陳腐化検出） | **叩く。**中で `pnpm audit` を呼んでいる |

**3つに別々のリトライを書かない。**共通の関数を `scripts/` に置き、
**`check-audit-ignore-staleness.mjs` もそれを使う。**

**`ci.yml` と `deploy.yml` の両方を直す。**

**016 の R-2 で「`deploy.yml` が `ci.yml` の部分集合になっていた」を直した。
同じ形をもう一度作らない。**片方だけ直すと、**もう片方で止まる。**

## テストで証明すること
- **待ちが実際に伸びている**（設定の前後でログの待ち時間が変わる）
- **尽くして失敗したら赤になる**（通らない）
- **脆弱性で落ちたときは、リトライしない**（1回で赤。**ここを落とすと意味が反転する**）
- 通信の失敗と脆弱性の**区別の根拠**（終了コードか出力か）が、実測とともに記録されている

- **リトライが1箇所にあるか**（3つに散っていないか）
