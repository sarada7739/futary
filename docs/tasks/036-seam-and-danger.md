# 036: 継ぎ目を消し、危険な操作の色を分ける

## 目的

**人間が実機（iPhone）で見つけた2件。**

1. **ボケ画像の下端に継ぎ目が見える**（035 で一度直したが、消えていなかった）
2. **「ふたりのデータを削除する」がピンクの枠。**取り返しのつかない操作にブランド色

## 1. 継ぎ目

### 実測（A が人間のスクリーンショットから測った）

画面の上から**約51%**（1320×2868 の実機画像で **y ≈ 1470〜1490**）。

| | 緑 | 青 |
|---|---|---|
| 境目の上（y=1440〜1460） | **238.0** | **236.0** |
| 境目の下（y=1500〜） | **242.4** | **238.7** |

**30px の間で緑が +4.4。**

### なぜ目立つのか

**段差の大きさではない。その後の平坦さである。**

- 境目の**上**は、下に向かってじわじわ濃くなっている
- 境目の**下**は、**251 / 242 / 238 が何百行も1ずつも動かない。完全に平坦**

**「変化していた面」が「まったく変化しない面」に切り替わるので、人の目はそこを線として見る。**

### 035 の直し方が効かなかった理由

035 では**下端140ptを固定色（`surfaceTint`）へフェード**させた。

**地が斜めのグラデーションなので、どの固定色を選んでも、どこかで必ずずれる。**

B は当時「ピクセル値では同程度の差が残るが、**見た目には現れていない**」と報告した。
**現れていた。**「見た目に出ていない」は**「無い」の主張**であり、
**画像を見ただけで言い切れるものではなかった。**

### 直し方

**フェード先を色にしない。画像そのものを透明にする。**

- **ボケ画像の PNG を作るときに、下端へ向かうアルファのランプを焼き込む**
  （切り出しのスクリプトで、下 30〜40% を alpha 255 → 0 へ線形に落とす）
- **画面上の高さで切らない。**`Screen` では画像を敷くだけにし、
  **「420pt で切る」「下端140ptをフェード」という指定を外す**
- **フェード先の色が存在しなくなるので、地のグラデーションと一致しないという問題が消える**

### 訂正: `cover` をやめて `stretch` にする（R の実測。2026-09-05）

**`BOKEH_HEIGHT`(420) と `resizeMode="cover"` の組み合わせは、窓が広いと崩れる。**

R が倍率を幅ごとに計算した。

```
窓幅  390 -> 倍率 1.400  描画高 420   縦はクロップされない
窓幅 1194 -> 倍率 1.400  描画高 420   縦はクロップされない
窓幅 1280 -> 倍率 1.501  描画高 450   ★ 縦がクロップされる
窓幅 1920 -> 倍率 2.251  描画高 675   ★ 縦がクロップされる
```

**1195px を超えると倍率が幅で決まり、`cover` が縦を中央で切る。**
**焼き込んだアルファのランプの下端が切り落とされ、箱の下端でアルファが0にならない。
継ぎ目が戻る。**

**そしてボケ画像は `layout.maxWidth` の内側にない。**窓幅いっぱいに広がる
（`screen.tsx` で `position:absolute` / `left:0` / `right:0`）。
**1280・1440・1920 はどれも普通のデスクトップである。**

**確認は3枚とも 390×844 で行われていた。**
**「デバイス幅で成り立つ前提」を、デバイス幅でだけ確かめていた。**

#### `resizeMode="stretch"` にする

- **`stretch` は箱にぴったり合わせる。クロップが起きない。**
  **倍率の計算に依存しなくなる**
- **これはボケであって、形のある絵ではない。横に伸びても分からない**
- **`layout.maxWidth` の内側に入れない。**入れると、**広い窓で画像の左右に縦の境目ができる。**
  いまの「窓幅いっぱい」は正しい

**画像の縦横比への依存が消えるので、そのコメントも要らなくなる。**

#### 確かめる幅

**390 だけで確かめない。**

```
390 / 768 / 1280 / 1920
```

**4つとも測って、`artifacts/036/` に残すこと。**

### 訂正2: 横の継ぎ目が消えた代わりに、縦の継ぎ目が出た（R の実測。2026-09-05）

**`stretch` にしても、画像は横に引き伸ばされていない。**

R が `seam-w1920.png` の画素を読んだ。

```
seam-w768.png   768px幅   最大の横方向段差: x=16→17    差=1（ノイズ）
seam-w1280.png 1280px幅   最大の横方向段差: x=852→853  差=5
seam-w1920.png 1920px幅   最大の横方向段差: x=852→853  差=4
```

**853 は `bokeh.png` の元の幅である。**画像がそこで終わり、右は地のグラデーションだけ。
**窓が 853px より広いときだけ、そこに縦の段差が出る。**768px では出ない（画像の方が広いため）。

**段差 4〜5 は、人間が iPhone で見つけた横の継ぎ目（+4.4）と同じ水準である。**

**アルファのランプ自体は効いている**（R が y=410〜430 で段差なしを確認）。
**横の継ぎ目は消えた。縦が出た。**

#### 原因を測ってから直すこと

**`resizeMode` は箱の中の収め方であって、箱の大きさではない。**
**`stretch` にしても、画像の要素そのものが 853px しか無ければ、そこで終わる。**

**まず、画像が実際に何 px で描かれているかを DOM で測ること。**

- 画像要素の `getBoundingClientRect().width`
- `getComputedStyle(el).backgroundSize` と `backgroundImage`

**「たぶん `width: "100%"` が要る」で直さない。**
**測った値を `artifacts/036/` に残してから直すこと。**

### 訂正3: 測り方が、この壊れ方を含んでいなかった

**いまの測定は、行ごとの平均色を前の行と比べる形である。**

**縦の段差は、行と行の差を作らない。**上下に走る線なので、どの行でも同じだけずれている。
**そして 1920px のとき、測っていた4列（x=1%・3%・97%・99% ＝ 19・58・1862・1901）は
853 の近くを1本も通らない。**

**「差が1.0以上の行」も「20行以上の平坦区間」も、この段差には反応しない。**

**#242 と同じ形である**（R の指摘）。

| | |
|---|---|
| #242 | **対象の無いところでも落ちる基準**（基底ノイズで落ちた） |
| **今回** | **対象があっても動かない基準**（縦の段差に反応しない） |

**向きが逆なだけで、どちらも基準が対象を測っていない。**

#### 横方向も測る

**列ごとに、隣の列との差を出す。**行方向と同じことを90度回して行う。

- **4列だけ見ない。全列を走査して、隣接列の差の最大とその位置を出す**
- **対照区間も同じように取る**（ボケが乗らない帯で、隣接列の差の最大）

**「どこに段差があるか」を位置つきで出すこと。**
**位置が出れば、それが何の端なのかを突き合わせられる**（今回は 853 = 画像の元幅）。

### 確かめ方（人間と同じやり方で）

**目視で「見えない」と書かない。**

1. 実機（またはモバイル幅）のスクリーンショットを撮る
2. **行ごとに複数の x で平均色を取り、前の行との差を出す**
3. ~~**差が1.0以上の行が無いこと**を出す~~
4. **値が何百行も完全に同じになる区間が無いこと**を出す
   （**平坦な区間ができると、そこが境目になる**）

**2〜4の数値を `artifacts/036/` に残すこと。**

### 訂正: 3 の基準は誤りだった（B の実測。2026-09-05）

**「差が1.0以上の行が無いこと」は、この経路では成立しない。**

B が**ボケ画像が一切乗らない純粋なグラデーション領域**（y=500〜800）で同じ測定をしたところ、
**そこでも39行が差1.0以上（最大1.0）出た。**
**スクリーンショットの PNG 量子化とブラウザのグラデーション描画に、
行単位で 1.0 前後の基底ノイズが乗っている。**

**基準が、対象の無いところでも落ちるなら、その基準は対象を測っていない。**

**絶対値で切らない。対象の無い領域と比べる。**

| | |
|---|---|
| **対照区間**（ボケが乗らない純粋なグラデーション） | ここの最大差を**基底ノイズ**とする |
| **測る区間**（ボケのフェード帯） | **基底ノイズと同じ水準であること** |

**そして「何百行も完全に同じ値」という、今回の継ぎ目に固有の形が出ないこと。**

**数値で「見えない」とは言わない。**
**最終判定は人間の目である。**この継ぎ目は**人間が先に見つけた。**
**私も B も「見えない」と書かない。**

## 2. 危険な操作の色

**`danger` の色トークンと、`danger` バリアントを足した**（`architecture.md` 7節。A が記述済み）。

| | |
|---|---|
| 色 | `danger` = `#C9423C` |
| バリアント | `surface` 地 + **`danger` の枠線と文字** |

**塗りつぶしにしない。枠だけにする。危険な操作を、押しやすくしない。**

### 「バリアントを増やさない」に反していない

`primary` / `secondary` / `ghost` は**「主か従か」**の軸。
`danger` は**「取り返しがつくか」**の軸。**軸が違えば、選ぶときに迷わない。**

### 当てるのは1箇所だけ

| | |
|---|---|
| **退会**（`delete-account.tsx` の「ふたりのデータを削除する」） | **`danger`** |
| 投稿の削除 | **`danger` にしない。**論理削除で、行はテーブルに残る |

**「消える」ではなく「戻せない」で分ける。**

**他に破壊的な操作を見つけても、勝手に広げないこと。**
**取り返しがつくかどうかを A が判断する。**

## テストで証明すること
- 既存のテストが全部緑
- **`danger` が `delete-account.tsx` 以外から使われていない**

### そのテストが、2件目を捕まえられることを確かめる（R の指摘）

**`g` フラグ付きの正規表現を `.test()` で使い回すと `lastIndex` が進む。**
**次のファイルは前回の一致位置から探し始める。**

**いまは通る。**一致するファイルが1つだけで、`false` のたびに `lastIndex` が0へ戻るため。
**壊れるのは2件目が現れたときで、それはこのテストが書かれた理由そのものである。**

- **`g` を外すか、ループの中で作る**
- **そして、実際に2件目を作って落ちることを見てから通すこと**
  （一時的に別のファイルへ `variant="danger"` を足し、テストが赤くなることを確かめて戻す）

**「書いてある」と「効く」は別である。**

- **押しやすくなっていないか**（塗りつぶしにしていないか）
