# 022: 時刻の選択と、日付の8桁入力

## 目的
**入力の形を、手打ちから選択に変える。**

人間が 021 の実機確認で出した要望3件。

1. カレンダーの時間を、`12:00` と打つのではなく**選択する**
2. 時間を1つではなく、**開始と終了**にする
3. 付き合った日を `YYYY-MM-DD` で打つのではなく、**数字8桁**で入れる

## 中で2つに分かれる

| | 何が変わるか | いつ必要か |
|---|---|---|
| **A. 時刻**（1・2） | **`events` に列が増える。**契約も変わる | **014 の前。**シードが `events` に行を入れる |
| **B. 日付8桁**（3） | **画面だけ。**契約もサーバも変わらない | いつでもよい |

**A を先にする。**B は落としても A は進む。

## なぜ 014 の前に置くか

**`events` に列が増え、既存の列の名前も変わる。**
`docs/tasks/014` のシードはこの表に行を入れる。**後から変えれば書き直しになる**
（018・019・021 と同じ理由）。

**順序は 021 → 022 → 014 → 015 → 016。**

## A. 時刻を選択式にし、開始と終了にする

### スキーマ

| いま | これから |
|---|---|
| `time TEXT`（`HH:MM`、NULL 許容） | `start_time TEXT`（同）**に改名** |
| — | `end_time TEXT`（`HH:MM`、NULL 許容）**を追加** |

**`events` は他のどの表からも参照されていない**（`architecture.md` 4節の実測）。
**表を作り直す形のマイグレーションが通る。**

**ただし作り直しは索引を落とす。**`events_meetup_unique`（018 の部分 UNIQUE）が
消える経路である。**`schema-integrity.test.ts` がこれを見る。**
**生成された SQL に `CREATE INDEX` が戻っていることも目で確かめる。**

### 制約

**2つとも入力スキーマと CHECK の両方に書く**（R の指摘。
`architecture.md` 4節には両方入っているが、ここが片方しか書いていなかった）。

```sql
CHECK (end_time IS NULL OR start_time IS NOT NULL)
CHECK (end_time IS NULL OR end_time > start_time)
```

- **`end_time` は `start_time` が無いと立てられない**
- **終了は開始より後。**同じ日の中だけで、**日をまたがない**
- **`anniversary` に時刻は付けられない**（018 の判断。変えない）

**シードが入力スキーマを通らない書き込み口になる。**014 は `events` に
`meetup` を80〜100件・`plan` を5〜8件入れる。**019 で `married_date` の順序を
TRIGGER に足したのと同じ理由である**（R の指摘）。

**今回は 019 より楽である。`events` は親表ではないので、TRIGGER ではなく
普通の CHECK が書ける。**そして 022 はどのみち表を作り直すので、**追加の費用はゼロ。**

`HH:MM` はゼロ詰めなので、**文字列比較がそのまま時刻の前後になる。**

**CHECK には必ず名前を付ける**（`CONSTRAINT <名前> CHECK (...)`。R の指摘）。
**名前なしで書くと `schema-integrity.test.ts` の一覧に出ず、消えても気づけない。**
`architecture.md` 4節「CHECK には必ず名前を付ける」。

**日をまたぐ予定は作れない。**行が持つ `date` は1つで、
**終了が開始より前になると、その行だけでは何日のことか決まらない。**
夜をまたぐなら2件に分けるか、終了を空にする。

### 契約

```
event.create   { date, title, kind, repeatYearly, startTime?, endTime? }
event.update   { id, ... }
event.list     items[].startTime  HH:MM または null
               items[].endTime    HH:MM または null
```

**`time` は残さない。**018 で入れてから日が浅く、**使っている場所が少ないうちに直す。**

### 選択の形: ホイール（人間が絵で指定）

**時と分の2列。中央に選択帯を置き、上下は薄くする。**24時間表記。
人間が絵で示した形である。

- **5分刻み。**当初 15分と書いていたが、**絵が5分刻みだったので合わせた**
- **刻みに乗らない既存の値は、その値自身を選択肢として差し込む**（下記）
- **終了は空のままにできる。**開始だけの予定は普通にある
- 開始を選ぶ前に終了を選べない形にする（**押せてから断られる形にしない**）

#### 刻みに乗らない既存の値

**「表示できる」と「保存で消えない」は別である**（R の指摘）。

`event.update` は**部分更新ではなく全項目の置き換え**なので、
**画面が持っている値がそのまま送られる。**
`12:07` の予定を開いてタイトルだけ直して保存したとき、
**ホイールの初期化で `12:05` に丸められると、触っていないのに書き換わる。**

**丸めない。`12:07` を選択肢として差し込む。**

- 現在値が5分刻みに乗らないとき、**その値を1行として列に加え、そこを選択状態にする**
- **表示と保存値が食い違わない。**利用者は `12:07` を見て、`12:07` を保存する
- **利用者がホイールを動かせば、その値は列から消えてよい。**
  **自分で動かしたなら、それは利用者の操作である**

**「人間が入れたものを、こちらの都合で消さない」**（021 と同じ）。
**触っていないものが変わるのが、いちばん悪い。**

#### Safari に `scrollend` が無い

**ここが唯一の落とし穴である。**

スクロールが止まったことを知らせる `scrollend` は、**Chrome と Firefox にはあるが
Safari（デスクトップ・iOS とも）に無い。**
**`scrollend` を前提に値を確定させると、iPhone で決まらない。**

- **タイマーで確定しない**（下記。当初「一定時間動きが無ければ確定」と書いていた）
- CSS の `scroll-snap-type: y mandatory` + 各行の `scroll-snap-align: center` で
  行に吸い付かせる。**これは Safari にもある**
- 上下を薄くするのに `mask-image` を使うなら、**Safari には `-webkit-` 接頭辞が要る**

#### タイマーで確定しない。スクロール位置から常に導く

**当初「`scroll` が一定時間止まったら確定」と書いた。これを取り消す。**

理由は2つある。

**1つ目。値がずれる形が実在する。**
iPhone はフリックしたあとも慣性で回り続ける。**減速が終わる前にタイマーが切れると、
通り過ぎた途中の値で確定する。表示はさらに流れて別の数字で止まるのに、
保存されるのはそれではない。**PC のマウスホイールでは出ない
（弾かれた瞬間に止まるため）。

**2つ目。それを 016 まで確かめられない。**
**iPhone は開発サーバーに届かない。実機で触れるのはデプロイのあとである**
（人間の指摘。023 → 014 → 015 → 016 の順で、まだ先）。
**確かめられないものを、確かめる前提で設計しない。**

**確定という操作をなくす。**

- **スクロール位置から、いま中央にある行を毎回そのまま値にする**
  （`scroll` ごと。必要なら `requestAnimationFrame` でまとめる）
- **止まったかどうかを判定しない。**慣性で動いている間は値も動き、
  **止まればそこが値になる**
- **表示と値が、常に同じ行を指す。**構造として一致するので、ずれようがない

**これは「刻みに乗らない値を丸めない」と同じ形である。**
**画面が見せているものと、保存されるものを、食い違わせない。**
**食い違わない作りにすれば、食い違っていないことを確かめずに済む。**

**テストで時間を待たない。**スクロール位置を与えれば値が決まるので、
**タイマーを挟まずに固定できる。**

##### 自分が動かした分で、位置を戻さない（R の指摘）

**「確定を無くせばずれようがない」と書いたが、回していない。**
**そのままでは、別のずれが入る。**

毎スクロールで `onChange` を呼ぶと `value` が変わり、
**位置合わせの `scrollTo` が慣性スクロールの最中に走る。**
タイマー版では確定が止まったあとに1回だけ起きていたものが、**指が動いている間に起きる。**

R が紙上で回した2例。

```
10:05 から下へフリック   offsetY=66  値 05->10  scrollTo=80  ずれ +14px
10:03（刻みに乗らない値）  offsetY=66  値 03->05  options 13->12
                          scrollTo=40  ずれ -26px（下へ動かしているのに上へ戻る）
```

**2つ目は慣性に依存しない。決定的に起きる。**
`"03"` が選択肢から消えて index が繰り上がるためで、
**「丸めないために入れた特別行」がそのまま引き金になっている。**

**位置合わせは、外から `value` が変わったときだけ走らせる。**
**自分のスクロールに起因する変更では走らせない。**

- **利用者が動かしている間、位置は利用者のものである。**こちらから触らない
- 外から値が入ったとき（初期表示・別の値を読み込んだとき）だけ合わせる

##### この2例はテストで固定できる。人間を待たない

**決定的に起きるので、実機もタイマーも要らない。**
`onScroll` に `contentOffset` を与えれば再現する。

**`apps/app/test/` は18ファイルあるが、`WheelColumn`・`onScroll`・`contentOffset` に
触れるものは1件も無い**（A が実測）。**125件緑は、この経路を1行も通っていない。**

- **フリック中の連続した `onScroll` で、こちらから `scrollTo` を呼ばないこと**
- **刻みに乗らない値から動かしたとき、選択肢が1つ減っても位置が戻らないこと**
- 外から `value` を変えたときは、位置が合うこと
- **刻みに乗らない値から、離れた行をタップしたら、その行の値になること**（下記）

##### 行き先を index で決めない。値で引き直す（R の指摘）

**上の3件はスクロール経路しか通らない。タップ経路が残る。**

`selectByPress` が `scrollTo({ animated: true })` の行き先を
**タップした時点の index** で決めると、その直後の `onChange` で
**`"03"` が選択肢から消えて index が繰り上がり、行き先がずれる。**

```
開始 03（options 13個）で「30」をタップ
  行き先 y=280（タップ時点の index=7）
  onChange 後 options 12個 → 「30」の正しい位置は y=240
  終端 y=280 を新しい options で読むと index=7 → "35"
  結果: タップした行と違う値になる
```

**原因は上の2例目と同じである。選択した結果として選択肢の数が変わる。**
**index は、決めた瞬間と着地する瞬間で意味が変わる。**

**行き先を index で固定しない。値が変わったあとの選択肢で引き直す。**
**index は位置の名前ではなく、そのときの並びの中の順番でしかない。**

**これは1案目で悪化した箇所ではない**（R の指摘。撤去の前後どちらでも同じ値に落ちる）。
**ただし「自分の `onChange` 起因では位置合わせを走らせない」にすると、
後から偶然直る経路も消える。**だからテストで押さえる。

**これも慣性に依存しない。決定的に起きるので、いま固定できる。**

**「iPhone でしか確かめられない」のは慣性の感触だけである。
上の2つは論理であって、いま固定できる。**
**確かめられないものと、確かめていないものを混ぜない。**

#### `<input type="time">` は採らない

**iPhone の Safari なら、OS のホイールがそのまま出る。**絵に一番近く、書く量も最小である。

**それでも採らない。PC の Safari・Chrome では別物になる。**
デモは公開前提で、**最初に触る画面が環境ごとに違う形になる。**
`layout.maxWidth = 640` を入れたときと同じ理由で、**PC 幅の見た目を捨てない。**

**自前で作れば、どこでも同じ形になる。**

### 表示

**`12:00〜13:00`。**終了が無ければ `12:00` のまま。
018 で入れた「設定者の名前・時間」の並びを崩さない。

## B. 日付を数字8桁で入れる

**画面だけ。契約もサーバも変わらない。**送るのは `YYYY-MM-DD` のままである。

`20240115` と打つと `2024-01-15` になる。**区切りは打たせない。**

### 対象

| 場所 | タスク |
|---|---|
| ~~オンボーディングの**付き合った日**~~ | **対象から外した。023 でこの入力自体が消える**（下記） |
| マイページの**付き合った日** | 019 |
| マイページの**結婚した日** | 019 |
| カレンダーの**日付** | 011 |

**人間が名指ししたのはオンボーディングだけだった。**そこを外している。

**そのあと人間が「登録時に付き合った日を聞くのをやめたい」と言ったため
（023）、この入力は無くなる。消える画面に作り込まない。**
**名指しされた1件が対象から消え、名指しされていない3件だけが残った形である。**

**残る3つは人間が言っていない。**揃えた理由は、**同じ形の入力が画面ごとに違うと、
どちらが正しいのか利用者が判断できない**ため。

### 決めること

- **8桁に満たないうちは、まだ日付として扱わない**（`2024011` を `2024-01-1` にしない）
- **存在しない日付は拒む。**`20240230` は通さない
  （`packages/date` の `isValidDate` が既にある）
- **上限・下限は既存のまま。**付き合った日は1年後まで、結婚した日は2年後まで（019）
- 数字以外は受け付けない

## テストで証明すること

- **`end_time` は `start_time` が無いと立てられない**（入力・CHECK の両方）
- **終了が開始より前・同じ**ものを拒む（**入力スキーマと CHECK の両方**）
- **`12:07` の予定をタイトルだけ変えて保存すると、時刻が `12:07` のまま残る**
  （丸められない）
- `anniversary` に時刻を付けられない（**変えていないこと**）
- **改名後も `event.list` が既存行の時刻を返す**
- **マイグレーション後に `events_meetup_unique` が存在する**
  （`schema-integrity.test.ts`）
- **マイグレーション後に `events` の CHECK が全部そろっている**
  （`schema-integrity.test.ts` の走査に `type='table'` を足す。
  **`events_kind_check` にはいま DB レベルのテストが1つも無い。**
  `architecture.md` 4節「表の CHECK も見る」）
- **既存行が入った状態でマイグレーションを当てる**
  （`conventions.md` 6節「既存行の扱いが変わるマイグレーションは、行を入れた状態で当てる」。
  **`TEST_MIGRATIONS` をスライスする形。この規約が初めて実際に効く回である**）
- 8桁入力が `YYYY-MM-DD` になる。**存在しない日付を拒む**

## 確認観点
- **時刻の選択が、スマホ幅で押しやすいか**
- **iPhone の Safari で、強くフリックして指を離したあと、
  止まって見えている数字と保存された数字が一致するか。**
  **これは 016 のデプロイ後にしか確かめられない**（iPhone は開発サーバーに届かない）。
  **タイマーで確定しない形にしたので、構造としては一致するはずである。
  確認は「念のため」であって、これを待って何かを止めない**
- **PC の Safari・Chrome でも同じ形に見えるか**
- **既存の予定を開いたとき、入っていた時刻がそのまま出るか**
- 終了を空にしたまま保存できるか
- **8桁を打つ途中で、表示が壊れて見えないか**
- カレンダーの一覧で `12:00〜13:00` が読めるか
