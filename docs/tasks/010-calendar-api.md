# 010: カレンダーAPI

## 目的
記念日・予定・会った日を保存できるようにする。
「会った日」は統計カード（012）の「会った回数」の算出元にもなる。

## 変更対象ファイル

- （新規）`apps/api/src/lib/date.ts` — JST の日付ユーティリティ
- `packages/contract/` — `event.list` / `event.create` / `event.update` / `event.delete`

## 実装内容
- スキーマは `docs/architecture.md` 4節に従う。`kind` は `anniversary` / `plan` / `meetup`（ADR-009）
- **日付は `YYYY-MM-DD` の文字列で保持する。** Unix秒で持つとタイムゾーンで必ず壊れる
- `apps/api/src/lib/date.ts` に JST 前提の日付関数をまとめる
  - 「今日（JST）」の取得
  - 日付文字列の差分（日数）
  - `n` ヶ月前 / `n` 年前 の日付文字列
  - **ここに全ての日付計算を集約する。** 各所で `new Date()` を直接使わない
- `event.list`: `from` / `to` の範囲で取得する。**設計は `architecture.md` 5節
  「繰り返し記念日の射影」に従う。**要点:
  - **範囲が年をまたぐ前提で作る。**月表示のカレンダーは12月と1月で必ずまたぐ
    （日〜土のグリッドで 2026年12月は `2026-11-29 〜 2027-01-02`）。
    範囲が触れる年それぞれに射影する
  - **範囲は最大400日。**超えたら `INVALID_INPUT`
  - **射影する年を決め打ちにしない。**`year(from)`〜`year(to)` をループする。
    400日の窓は**3つの暦年に触れることがある**（`2026-12-20 〜 2028-01-24`）
  - **同じ記念日が2回現れることがある。重複を除去しない**
  - **平年の 02-29 は 02-28 に寄せる**（`+365日` がちょうどそこ。
    03-01 にすると2月の記念日が2月の表示から消える）。
    保存されている `date` は `02-29` のまま変えない
  - 応答は `date`（射影後）と `sourceDate`（登録された日付）を持つ
- `event.create` / `update` / `delete`: `writeProcedure` の上に載せる
  - 更新・削除は WHERE 句に `couple_id` を含めて1文で行う

## テストで証明すること
- `repeat_yearly` の記念日が、登録年と異なる年の照会で正しく返ること
- **範囲が年をまたぐとき（`2026-12-20 〜 2027-01-10`）に、
  年末側と年始側の記念日が両方返ること**
- **400日の範囲で同じ記念日が2回返ること**（重複を除去していないこと）
- **3つの暦年に触れる窓で、中間の年の記念日が返ること。**
  `from=2026-12-20, to=2028-01-24`（ちょうど400日）に対し `MM-DD=06-15` の記念日は
  **2027-06-15 だけが入る。**`year(from)`/`year(to)` の2年しか射影しない実装では
  丸ごと消える
- **401日の範囲が `INVALID_INPUT` になること**
- うるう年 02-29 の記念日が平年でも消えず、**02-28 に出ること**
- **うるう年へ射影したときは 02-29 のまま**であること
- 日付の差分計算が JST 基準で正しいこと（UTC との日跨ぎ時刻でテストする）

## 実装メモ

- `event.update` は部分更新にせず、`event.create` と同じ全項目（date/title/kind/
  repeatYearly）を受け取って置き換える形にした。architecture.md に部分更新の
  要求が明記されておらず、部分更新は「送らなかったフィールドを既存値のまま
  残す」ためのNULL上書き回避ロジックが必要になり複雑さが増すだけと判断した
- `event.delete` は論理削除にしていない（`posts` と異なり `events` に
  `deleted_at` 列を持たない。architecture.md 4節のスキーマにも無い）。物理削除
- 日付の実在性チェック（`refine`）は入れていない。02-29 の記念日は平年には
  実在しない日付として登録されるため、実在性チェックを入れると記念日そのものが
  登録できなくなる（`couple.anniversaryDateSchema` とは異なる判断）
- `event.list` の `repeat_yearly=1` 側は couple 全件を取ってから射影する
  （登録年に関わらず表示されうるため、SQL の `date` 範囲条件では絞れない）。
  MVP の想定規模（2人×記念日数件）では couple あたりの行数は小さく、
  全件取得のコストは無視できる
- `security-requirements.md` 10節1（認証・招待・画像アップロード・認可
  ミドルウェアを触ったタスク）に該当しないため、010単体でのsecurity-auditor
  監査は必須ではないと判断した（006・008と同じ扱い）。M3の他タスクと合わせて
  マイルストーン単位でまとめて監査する（10節2）

### Rレビュー往復1回目対応

- **必須修正**: `yearsBefore` が `monthsBefore(date, n*12)` へ委譲していたため、
  `projectMonthDay` の規則（平年の02-29は02-28に寄せる）と矛盾していた
  （`yearsBefore("2024-02-29", 1)` が `2023-03-01` を返していた）。
  `yearsBefore` を `projectMonthDay(month, day, year - n)` を直接呼ぶ実装に
  変更し、矛盾を解消した
- **判断依頼**: `monthsBefore` の月末繰り上がり（例: `2026-03-31` の1ヶ月前が
  `2026-03-03` になる。月末〈2/28〉に寄せない）は仕様未決定のため、
  現状の挙動のままテストで固定し、`docs/state.md` にL61として起票してAへ
  エスカレーションした。013着手前にAの判断が要る
