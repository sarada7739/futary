# 029: 気分の記録

## 目的

**1日1回、その日の気分を1タップで残す。ふたり分が並んで見える。**

人間の指示。`requirements.md` 5節「スコープ外」から次フェーズへ上げる3つ目。

**ホームの「気分の記録」パネルは 020 で既に置いてある**（`iconPanelMood`・
`onPress` 無し）。**027 と同じで、そこに `onPress` を付ける作業である。**

## 1. グラフ描画ライブラリを入れない

`requirements.md` 5節がこれをスコープ外に置いた理由は
**「グラフ描画ライブラリの追加が必要」**だった。**その前提を外す。**

**気分は「1日に1つの値」である。**折れ線も軸も要らない。
**月ごとのマス目に濃さを置けば読める**（`month-grid.tsx` が既にある形）。

- **`View` の背景色だけで描く。**依存を増やさない
- **折れ線グラフにしない。**日をまたぐ線は「連続した量」に見えるが、
  **気分は日ごとに独立している**

**「ライブラリが要る」は、作り方を1つに決めたときだけ正しい。**

## 2. 新しい色トークンを作らない

**`primary` の濃さ5段で表す。**

`architecture.md` 7節の色トークンは**役割**で持っている
（`event-anniversary`・`event-plan`・`event-meetup` は種類が違うもの）。
**気分の5段は役割ではなく量である。量は色を増やさずに表せる。**

- **濃いほど良い。**説明が1行で済む
- **青⇄ピンクの2色軸にしない。**どちらが良いかを色の意味に頼ることになる
- **未記録は、地のまま枠線だけ。**薄い色と未記録を見間違えない

### 色だけで区別しない

- **選んだ段階を言葉でも出す**（「今日: ふつう」）
- マスに `accessibilityLabel` を付ける（日付と段階）

## 3. 5段階。言葉はこれで固定する

| 値 | 言葉 |
|---|---|
| 1 | わるい |
| 2 | よくない |
| 3 | ふつう |
| 4 | よい |
| 5 | とてもよい |

**3段階では「ふつう」に寄りすぎ、7段階は選ぶのに迷う。**
**迷う粒度は、記録されない**（027 で分類を持たなかったのと同じ論法）。

## 4. 「今日どうだった？」と混ぜない

`requirements.md` 5節の**「今日どうだった？1日1回質問」は次フェーズ最有力**として
別に残っている。**近いが、別物である。**

| | |
|---|---|
| **気分の記録（029）** | **1タップ。**言葉を書かない |
| 今日どうだった？（次フェーズ） | **文章を書く。**質問マスタと開示制御が要る |

**気分にひとことを付けない。**付けると「今日どうだった？」と機能が重なり、
**あとから足すものの置き場所が無くなる。**

## 5. 今日の分しか記録できない

**過去の日に遡って付けられない。**

**あとから振り返って付けた気分は、気分ではない。**その日の記録であることが価値である。

- 入れ忘れた日は空のまま残る。**それでよい**
- **あとから緩める方が、あとから締めるより安い**（緩めるのは仕様変更、
  締めるのは既にあるデータの否定になる）

## 6. 自分の分しか書けない。相手の分は読めるだけ

**`couple_id` スコープの中でも、ここは書き手が分かれる。**

- **`mood.setToday` は `user_id` を引数に取らない。`ctx.userId` を使う**
  （`conventions.md` 5節「引数に `coupleId` を持つ手続きを作らない」と同じ考え方。
  **渡せないものは、間違えて渡せない**）
- **相手の気分は読める。**ふたり専用SNSであり、`couple_id` 内の共有が既定
  （`security-requirements.md` 3節）
- **021 の `canEdit` を持ち込まない。**「相手の分を編集できるか」という問いが
  そもそも立たない形にする

## 7. 消せる。ただし物理削除にする（`requirements.md` 6節の例外）

**気分は取り消せる**（「今日は記録したくない」）。

**論理削除にしない。物理削除にする。**

`requirements.md` 6節は「削除は論理削除。誤操作からの復旧余地を残す」としている。
**その余地が要るのは、失って困るものである。**

- **気分は 1〜5 の数値1つで、入れ直せる**
- **`deleted_at` を足すと主キーと衝突する**（消したあと同じ日を再登録できない）

**規則の例外を作るときは、規則が何のためにあるかを書く。**

## 8. データモデル

```
moods                                           -- 029
  couple_id   TEXT    NOT NULL -> couples.id
  user_id     TEXT    NOT NULL -> user.id
  date        TEXT    NOT NULL                  -- YYYY-MM-DD（JST）
  level       INTEGER NOT NULL
  created_at  INTEGER NOT NULL
  updated_at  INTEGER NOT NULL
  PRIMARY KEY (couple_id, user_id, date)        -- 1日1件/人をDBで担保
  CONSTRAINT moods_level_range_check CHECK (level BETWEEN 1 AND 5)
```

- **CHECK に名前を付ける**（`architecture.md` 4節）
- 「1日1件/人」は**主キーで担保する。**アプリの条件に頼らない
  （`events` の meetup 部分 UNIQUE と同じ思想）
- 論理削除を持たない（7節）
- マイグレーションは `0018_moods.sql`。**新規テーブルで、他表から FK 参照されない**

### `me.delete` に `moods` の削除文を足す

**`moods` は `couples` と `user` を参照する側である。D1 は FK を常に強制する。**

**足さないと、気分を1件でも記録したペアはアカウント削除が恒久的に失敗する。**
027 で `wishes` を足したときに同じことを踏んだ
（`architecture.md` 4節「表を足したら、消す手順にも足す」）。

**今回は起票の時点で書いてある。踏まないこと。**

## 9. 契約（oRPC）

```
mood.setToday    { level }        -> { date, level }   自分の今日の分。upsert
mood.clearToday  ()               -> { date }          自分の今日の分を消す
mood.list        { from, to }     -> { mine:    [{ date, level }],
                                       partner: { name: string | null,
                                                  items: [{ date, level }] } }
```

- **`mood.list` は2人分を分けて返す。**1本の配列に `userId` を混ぜない。
  **混ぜると、画面で取り違えられる**（`created_by` を返さない方針と同じ）
- **範囲は最大400日。超えたら `INVALID_INPUT`**（`event.list` と同じ数にする。
  **数を揃える。**別の数にすると、どちらが正しいか読めなくなる）
- **`INVALID_INPUT` はここで正しい。**DB を読まないと分からない条件ではないが、
  **`event.list` の 400 日と同じ場所に置く**（`conventions.md` 5節の
  「線に合っていないもの」の表に `mood.list` も足すこと。A が書く）
- ゲストは `setToday`・`clearToday` を通れない（サーバ側で拒む）

## 10. T9 の対象である

**`mood.list` は利用者ごとに違う値を返す**（`mine` と `partner` が入れ替わる）。
**キャッシュキーに `viewerKey` を含める**（`architecture.md` 5節）。

**ここは特に間違えると気持ちが悪い。**相手の気分が自分の欄に出る。

## 11. 画面

**`(tabs)/mood.tsx`。ボトムタブには出さない**（027 と同じ。`(tabs)` の中に置く）。

- ホームの「気分の記録」パネルから `router.push("/mood")`
- 上: **今日の気分を選ぶ5つのボタン。**選択中が分かる。もう一度押すと取り消す
- 下: **月のマス目を2つ縦に並べる。**「わたし」と相手の名前
  - **1マスに2色を詰めない。**読めなくなる
  - 相手が未参加（ペアが1人）のときは**相手の段を出さない**
- 3状態（読み込み中 / 空 / エラー）をすべて持つ
- **二重発火を防ぐ**（`conventions.md` 4節）

## 12. デモに入れる

- 2人分・**3ヶ月ぶん**を決定的に組み立てる（乱数を使わない。`packages/date` のみ）
- **空の日を混ぜる。**毎日埋まっているデモは、未記録の見え方を隠す
- 2人の傾向が違うように入れる（**同じ列が並ぶと、2段ある意味が見えない**）

## テストで証明すること
- **他ペアの気分が `mood.list` に出ない**
- **`mood.setToday` が今日以外の日を書けない**（引数に日付を取らない形で担保する）
- **自分の分しか書けない**（`user_id` を引数に取らない形で担保する）
- **同じ日に2回 `setToday` すると上書きされる**（行が増えない）
- `level` が 0 や 6 のとき拒まれる（**Zod で弾く。`BAD_REQUEST`**。
  `conventions.md` 5節）
- `moods_level_range_check` が DB 側にもある（`schema-integrity.test.ts`）
- 範囲が400日を超えたら `INVALID_INPUT`
- **ゲストは `setToday`・`clearToday` を通れない**
- **`me.delete` が `moods` を消す**（8節。**気分を持つペアで削除が通ること**）
- キャッシュキーに閲覧者が含まれる（T9）

## 確認観点
- **1タップで入るか。**選ぶのに迷わないか
- **未記録の日と、いちばん薄い日を見間違えないか**
- 相手の段に**自分の気分が出ていないか**（T9）
- ペアが1人のとき、**相手の段が出ていないか**
