# ADR: 設計判断の記録

なぜその設計にしたかを残す。実装中に「なぜこうなっているのか」と思ったらここを見る。
判断を覆す場合は、既存項目を消さず「変更」として追記する。

---

## ADR-001: データモデルを最初から複数ペア対応にする

**状況**: 当初の利用者は作者とパートナーの2人だけ。将来的に外部公開したい。

**決定**: `couples` を最上位の単位とし、ユーザーデータを持つ全テーブルに `couple_id` を持たせる。

**理由**:
- 2人固定（`user_id` のみ）で作ると、外部公開する時点で全テーブル・全クエリ・全認可の改修が必要になり、実質的な作り直しになる
- 最初から couple 単位にしても増える作業は招待フローの1〜2タスク分だけ
- 「マルチテナント設計と認可の分離」は転職アピールの設計軸として具体的に語れる

**結果**: 招待コードによるペア成立フローが MVP に必要になった（ADR-005）。

## ADR-002: Expo + React Native Web の単一コードベース、LP のみ別置き

**状況**: Web で公開し、後々 iOS アプリ化を検討したい。同時に「面接官がその場で触る公開URL」が評価対象。

**決定**: アプリ本体は Expo Router + React Native Web の単一コードベース。
紹介とデモ入口を兼ねるランディングページのみ、素の HTML/CSS で別途配置する。

**却下した案**:
- *Expo 単一コードベースのみ*: LP もアプリ内の1画面になる。React Native Web は SEO・OGP・Webらしい見た目が素直に出ず、第一印象を損なう
- *Web(Next.js) と Mobile(Expo) を分離*: 設計の見せ場は最大だが、2コードベースの同期コストが2〜4週間に収まらない
- *Web専用で作る*: Web品質は最高だが、iOS化が事実上の作り直しになる

**理由**: 第一印象はLPで確保し、アプリ本体は単一コードベースの開発速度を取る。LP の作成コストは半日〜1日。

## ADR-003: API 層に oRPC を採用する

**状況**: 型安全な API 層が必要。tRPC / Hono RPC / oRPC が候補。

**決定**: oRPC を採用する。

**理由**:
- Zod スキーマから OpenAPI 仕様を自動生成できる。「API仕様書が生成される設計になっている」は設計軸のアピールとして具体的
- Hono との統合があり、Cloudflare Workers 上で動く
- クライアント側で TanStack Query と組み合わせた型推論が効く

**トレードオフ**: tRPC より認知度が低く、面接官が知らない可能性がある。
このADR自体が説明材料になるため許容する。

## ADR-004: 認証は Google OAuth のみ

**状況**: Better Auth を使う。認証方式の選択肢はメール+パスワード / OAuth。

**決定**: MVP では Google OAuth のみを提供する。

**理由**:
- メール+パスワードは確認メールとパスワードリセットのためにメール送信基盤（Resend 等）が必要になり、「無料運用」と「2〜4週間」の両方を圧迫する
- パスワードを保存しないため、ハッシュ強度・リセットトークン・総当たり対策といった監査対象がまるごと消える
- 利用者が2人 + デモ閲覧者であり、Google アカウント必須による離脱がない

**将来**: iOS 配布時、Apple の審査要件により Apple Sign In の追加が必要になる。

## ADR-005: ペア参加は招待コード方式

**状況**: 2人目をペアに参加させる導線が必要。招待コード / 招待リンクが候補。

**決定**: 6桁の招待コードを発行し、相手がアプリに入力して参加する。有効期限を持たせる。

**理由**:
- 招待リンクは iOS アプリ化した際に Universal Links の設定が必要になる。コード入力なら Web もアプリも同一実装で済む
- コードは LINE 等で送れる。手間は1回だけ

**セキュリティ**: 6桁は総当たりが可能な長さのため、有効期限（24時間）と1ペアあたり同時1件、および参加試行のレート制限で担保する。詳細は `security-requirements.md`。

## ADR-006: 「去年の今日」を「思い出し」に一般化する

**状況**: デザイン案には「去年の今日」がある。

**問題**: 使い始めてから最初の1年間、一切何も表示されない。MVP の1機能が実質1年間死ぬ。

**決定**: 1ヶ月前 → 半年前 → 1年前 の順に該当投稿を探し、無ければ過去投稿からランダムに1件を出す。

**理由**: 実装コストは「去年の今日」とほぼ同じで、使い始めた翌日から機能する。
デモペアにはシードデータを入れるため、面接官には1年前の思い出も見える。

## ADR-007: 画像は1投稿1枚、クライアント側で圧縮して R2 に直アップロード

**決定**:
- 1投稿につき画像1枚まで
- クライアント側で長辺 1600px / JPEG 品質 0.8 に圧縮してからアップロード
- Worker は署名付き PUT URL を発行するだけで、画像本体を経由しない

**理由**:
- Worker が画像本体を中継すると CPU 時間とリクエストサイズの制約を受ける。直アップロードなら Worker の負荷はゼロ
- クライアント側圧縮により Cloudflare Images（有料）を使わずにサムネイル問題を回避できる
- 複数枚対応はギャラリー表示・並べ替えUIを呼び込むため MVP から外す

## ADR-008: 通知を作らない

**決定**: プッシュ通知・Web Push・WebSocket をいずれも実装しない。
画面を開いている間の更新は TanStack Query のポーリングで賄う。

**理由**: 利用者が2人であり、「相手が投稿したら気づく」は LINE で代替されている。
実装ゼロで体験が成立する。Web Push は iOS Safari で PWA インストールを要求するため、
コストに対する見返りが薄い。

## ADR-009: 記念日・予定・会った日を1テーブルに統合する

**状況**: カレンダーには「記念日ディナー」と「水族館デート」が並ぶ。
また統計カードには「会った回数」が必要で、この数字の出所が必要。

**決定**: `events` テーブル1つに `kind`（`anniversary` / `plan` / `meetup`）を持たせる。

**理由**:
- 3種類とも「日付 + タイトル」という同じ形をしている。テーブルを分けると同じCRUDを3回書くことになる
- 「会った回数」を `kind = 'meetup'` の件数として算出できるため、統計のための専用テーブルが不要になる
- 記念日は `repeat_yearly = true`、予定と会った日は `false` で区別する

## ADR-010: デモは未認証・閲覧専用

**決定**: `couples.is_demo = true` のペアを1つ用意し、未認証アクセス時はそのペアのデータのみを読み取り専用で返す。書き込み系の手続きはサーバ側で一律拒否する。

**理由**:
- 面接官がログインの壁で離脱するのが最大の損失。URLを開いた瞬間に中身が見える状態を優先する
- デモ用アカウントで書き込みを許すと、荒らし対策（レート制限・不適切投稿の削除・定期リセット）が必要になる
- 拒否をサーバ側の1箇所（認可ミドルウェア）に集約することで、UI側の実装漏れが本番データに波及しない

**実装方針**: 別エンドポイントを作らず、認可ミドルウェアで
「セッション無し → `couple_id` はデモ固定 + 書き込み系は全拒否」とする。

## ADR-011: リポジトリは Private で開始し、016 で Public にする

**状況**: 転職アピールを兼ねるため、最終的にはコードを公開したい。

**決定**: `sarada7739/futary` を Private で作成し、タスク016（公開）のタイミングで Public に切り替える。

**理由**:
- GitHub は公開範囲を切り替えてもコミット履歴を保持する。
  「継続して積み上げた履歴」を見せる機会は、後から公開しても失われない
- 作りかけの状態が人の目に触れる期間を作らずに済む
- Public 化の判断を016に置くことで、公開前に必ず全体セキュリティ監査を通る

**結果**: 016 の完了条件に「リポジトリを Public に切り替える」を含める。

## ADR-012: 投稿を端末側で暗号化しない（運営は読める）

**状況**: 運営（`wrangler d1 execute --remote` と R2 の資格情報を持つ者）は、
**投稿本文・画像・記念日・予定を全部読める。**
`security-requirements.md` 1節の「最高」区分は「ペア外に一切出さない」としているが、
**それは利用者と攻撃者に対する話で、運営は含まれていなかった**（人間が指摘）。

**決定**: **端末側での暗号化はしない。運営が読める状態のまま公開する。**
**その事実を書く。**

**理由**:
- **鍵の置き場所ではなく、鍵が消えることが問題である。**
  ネイティブは SecureStore に置ける。ブラウザも WebCrypto の鍵を
  **取り出せない形で IndexedDB に置ける**（JS からも読めない）。
  **どちらも、サイトデータを消せば終わり、別の端末では読めない**
- **同期する手段が無い以上、合言葉を別に持つことになる。
  忘れたら全部消える。**「ふたりの毎日を、もっと特別に。」に対して重すぎる
- **思い出し（013）が壊れる。**サーバが中身を読めないので探せない
- **利用者は身内に限られる**（人間の判断）

**結果**:
- `security-requirements.md` 1節に「**運営は全部読める。対策していない**」を明記した
- **T1〜T9 は運営を対象にしない。**そう書いてある

**この判断が切れる条件**:
- **身内でない利用者を招くとき。**「身内だけ」が前提なので、前提が変われば判断も変わる
- そのときは**利用者に伝えるか、暗号化を検討するか**の分かれ道になる
- **016 で Public にすること自体は、この判断を変えない**
  （コードが読まれることと、データが読まれることは別である）

**同じ条件で見直すもの**:
- **制御文字・双方向制御文字の正規化**（`security-requirements.md` 6節。027 で
  「対策しない」と判断した。理由が同じ〈書ける相手が身内しか居ない〉ため、
  **前提が変わる日も同じ**である）
