# 要件定義: futary

## 1. プロダクト概要

ふたり専用SNS。パートナーと2人だけの閉じた空間に日々の出来事を残し、
時間が経つほど「思い出」として価値が増していくアプリ。

- 名称: **futary**
- タグライン: ふたりの毎日を、もっと特別に。
- 形態: Webアプリ（将来 iOS アプリ化を検討）

## 2. 目的

| 優先 | 目的 | 成功の定義 |
|---|---|---|
| 主 | 作者とパートナーが実際に日常的に使う | 2人が週に数回、自然に投稿している |
| 副 | 転職活動での技術アピール | 面接官がURLを開いて即座に触れる／設計文書で判断の根拠を説明できる |

副目的の評価軸は **設計・アーキテクチャ** と **動くプロダクトのURL** の2つ。
この2つに効かない作業は優先度を下げる。

## 3. 利用者

| 種別 | 説明 | 認証 | 権限 |
|---|---|---|---|
| ペアメンバー | 実際の利用者。1ペア = 2人 | Google OAuth | 自ペアのデータの読み書き |
| ゲスト | デモ閲覧者（面接官・紹介先） | なし | デモペアのデータの**閲覧のみ** |

- 1つの couple に所属できるのは最大2人
- 1人のユーザーが所属できる couple は1つまで

## 4. MVP スコープ（公開版に含めるもの）

| # | 機能 | 概要 |
|---|---|---|
| 1 | Googleログイン | Better Auth 経由。メール送信基盤を持たない |
| 2 | ペア作成・招待 | 6桁の招待コードを発行し、相手が入力して参加。コードには有効期限あり |
| 3 | 投稿 | テキスト + 画像（任意。**031 で4枚まで**）。**本文か画像のどちらかは必須**（両方空の投稿は作れない）。一覧はカーソルページング。画像はタップで全画面表示できる |
| 4 | リアクション | 投稿へのリアクション付与・取り消し |
| 5 | カレンダー | 記念日 / 予定 / 会った日 を月表示で登録・閲覧 |
| 6 | ペア統計カード | 「付き合って○日目」「**会った日数**」。ホーム最上部の主役 |
| 7 | 思い出し | 1ヶ月前 → 半年前 → 1年前 の順に探し、無ければ過去投稿からランダムに1件 |
| 8 | ゲストデモ | 未認証でデモペアを閲覧できる。書き込みはサーバ側で全拒否 |
| 9 | ランディングページ | 紹介 + デモ入口。素の HTML/CSS で別途配置。OGP 対応 |

### 「会った回数」から「会った日数」へ

当初は**「会った回数」**と書いていた。**018 で言い方を変えた。**

018 で「会った日は1日1件」を部分 UNIQUE で保証したため、
**同じ日に2回会っても 1 にしかならない。**
`COUNT(*)` は原理的に**日数の上限を超えられない。**
「回数」という語が数えているものと、実際に数えているものがずれていた（R の指摘）。

**「付き合って500日目 / 会った日数48日」**の方が、
1日1件という設計と読み手の中で矛盾しない。
ホーム最上部の主役であり、**最初に読まれる文言**である。

「会った回数」は人間の言葉ではなく、**設計フェーズで A が書いたものだった**
（`9147296`、2026-08-27）。**残す理由が無い。**

**契約のフィールド名も `meetupCount` → `meetupDays` に変える。**
名前が「回数」のままだと、次に読んだ人が
**「同じ日に複数回数えるべきでは」と直しにかかる。**
`woman2.jpg` が男性だったのと同じで、**名前は中身の情報ではない**状態を残さない。

## 5. スコープ外（明示的にやらない）

「やらない」と決めたことを記録する。実装中に迷ったらここを見る。

**理由の違うものを、1行にまとめない。**

「画像のピンチズーム・**スワイプ操作**」を1行に書いていた。
**理由は「ジェスチャライブラリが要る」と「1600pxでは粗くなる」の2つで、
後者はピンチズームにしか効かない。**

**まとめたせいで、片方の理由がもう片方に効いているように読めた。**
031 で A がそう読み、**「スワイプにしない」と決めた。**
**理由が成り立たないのに、結論だけが残った**（033 で覆した）。

**この表は「やらない理由」を持ち越すために書いている。
理由が混ざると、持ち越される先も混ざる。**

| 項目 | 理由 | 将来の扱い |
|---|---|---|
| 音声投稿 | 録音UI・波形描画・容量で実装が重い | 次フェーズ検討 |
| 「今日どうだった？」1日1回質問 | 質問マスタ・回答・相手の回答の開示制御が必要で MVP 最重量 | **次フェーズ最有力**。プロダクトの一番尖った部分 |
| アルバム（月ごと集約） | 既存データの見せ方を変えるだけ。後から足せる | 次フェーズ |
| ~~気分の記録・ムード推移~~ | ~~グラフ描画ライブラリの追加が必要~~ | **029 で実装する**（2026-09-02、人間の指示）。**ライブラリは入れない。**月のマス目に `primary` の濃さを置く |
| AI要約（週次・月次） | LLM API コストが無料運用と衝突する | 課金導入後 |
| ~~行きたい場所・食べたいものリスト~~ | ~~体験の中心ではない~~ | **027 で実装する**（2026-09-01、人間が次に足す機能として選んだ） |
| 動画投稿 | 容量・トランスコード・再生プレーヤーでタスクが跳ねる | 未定 |
| ~~1投稿に複数画像~~ | ~~ギャラリー表示・並べ替えUIが増える~~ | **031 で実装する**（2026-09-04、人間が選んだ）。**4枚まで。**並べ替えUIは作らない（選んだ順） |
| 画像のピンチズーム | ジェスチャライブラリ（`react-native-gesture-handler` + `reanimated`）の導入が要る。**保存解像度が長辺1600pxなので深く拡大しても粗くなる**。全画面表示だけ 017 で入れる | 保存解像度を上げる判断とセットで次フェーズ |
| ~~横スワイプでの画像送り~~ | ~~上と同じ行にまとめていた~~ | **033 で実装する**（2026-09-04）。**ライブラリは要らない**（ページング付き `ScrollView`）。**「1600pxで粗くなる」はピンチズームにしか効かない** |
| プッシュ通知 / Web Push | 開けば見える。TanStack Query のポーリングで代替する | 次フェーズ |
| リアルタイム同期（WebSocket） | 無料枠と実装コストの両方で重い | 未定 |
| 検索 | **枠も持たない。**当初はボトムタブに枠だけ置いていたが、020 でタイムラインに置き換えた（`architecture.md` 3節） | 次フェーズ |
| 課金 | まず無料で運用する | 将来検討 |
| iOSアプリ配布 | EAS Build。Apple Developer Program の登録が前提 | Web公開後 |
| メール+パスワード認証 | 確認メール・リセットのためにメール送信基盤が要る | 必要になったら |

## 6. 非機能要件

| 項目 | 要件 |
|---|---|
| 運用コスト | **無料**。Cloudflare 無料枠（Workers / D1 / R2 / Static Assets）に収める |
| 期間 | 2〜4週間で公開まで |
| 対応端末 | スマートフォン優先。PCブラウザで開いてもレイアウトが破綻しない |
| ブラウザ | モダンブラウザの最新2バージョン |
| 言語 | 日本語のみ |
| 可用性 | 個人利用。SLA なし。障害時は手動復旧 |
| データ保持 | 削除は論理削除。誤操作からの復旧余地を残す。**ただし画像は削除時に R2 から即座に消える**（本文は復旧できるが画像は戻らない） |

### 無料枠の把握（超えたら設計を見直す信号）

- Workers: 10万リクエスト/日
- D1: 5GB ストレージ / 500万行読み取り・10万行書き込みが1日あたり
- R2: 10GB ストレージ、エグレス無料

想定利用（2人 × 1日数投稿）では、いずれも桁違いに下回る。

## 7. マイルストーンと受け入れ

各マイルストーンの区切りで、**人間が実際に触って**受け入れを判定する。
自動テストはレイアウト崩れ・操作の流れの不自然さ・要件の取り違えを検出できない。

| M | 範囲 | 人間が確認すること |
|---|---|---|
| M1 | 足回り・認証・ペア成立 | Googleでログインでき、招待コードで2人目が参加できる |
| M2 | 投稿・画像・リアクション | スマホから写真付きで投稿でき、相手の投稿にリアクションできる |
| M3 | カレンダー・統計・思い出し | ホームに日数と**会った日数**が正しく出る。カレンダーに予定を入れられる |
| M4 | デモ・LP・公開 | 未ログインのURLでデモが見え、書き込みができないことを確認する |
