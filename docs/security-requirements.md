# セキュリティ要件: futary

このアプリが守るのは **2人の私的な写真と文章** である。
漏洩した場合の被害は金銭ではなく、当事者の私生活そのものに及ぶ。
利用者が少ないことは、守る必要が薄いことを意味しない。

## 1. 機密データの分類

| 区分 | データ | 扱い |
|---|---|---|
| 最高 | 投稿本文・投稿画像 | ペア外に一切出さない。ログに本文を出力しない。**ただし運営は読める**（下記） |
| 高 | セッショントークン、OAuth トークン、招待コード | ログ出力禁止。URLクエリに載せない |
| 中 | メールアドレス、表示名、プロフィール画像 | ペア内とデモ表示のみ |
| 中 | 記念日・予定・会った日 | 投稿本文に準ずる |
| — | デモペアのデータ | 公開前提。**実在の人物の写真・実際の出来事を入れない** |

### 運営は全部読める。対策していない

**「ペア外に一切出さない」は、利用者と攻撃者に対する話である。運営は含まれていない。**

| 経路 | 何が読めるか |
|---|---|
| `wrangler d1 execute --remote` | **投稿本文・記念日・予定・会った日。全部** |
| R2 の資格情報 | **画像。署名付き URL も自分で発行できる** |
| Cloudflare のダッシュボード | 同上 |

**暗号化していないので、見ようと思えば見られる。**

**対策しない**（2026-09-01、人間の判断。ADR-012）。
**理由と、その判断が切れる条件は ADR-012 に書いた。**

**書いていないことが、いちばん良くない。**
T1〜T9 は全て「他の利用者」と「攻撃者」の話で、**運営は一度も出てこなかった。**
**防いでいないと書いてあるのと、書いていないのは別である。**

## 2. 認証

- Google OAuth のみ（ADR-004）。パスワードを保存しない
- セッションは Cookie。属性は `HttpOnly` / `Secure` / `SameSite=Lax`
- ネイティブアプリではトークンを Expo SecureStore に保存する。`AsyncStorage` に置かない
- `BETTER_AUTH_SECRET` は 32 バイト以上のランダム値。リポジトリに含めない

**024 の再認証要件（`me.delete`）は 9節 T8 参照。**

## 3. 認可（最重要）

**単一の防御線に集約する。** 手続きごとに認可を書くと、必ずどこかで書き忘れる。

- 認可ミドルウェアが `ctx.coupleId` を確定させる
- **手続きの引数に `coupleId` を受け取らない**。他ペアのIDを送りつける経路を作らない
- 全てのクエリに `couple_id = ctx.coupleId` を含める
- 投稿削除・イベント更新は、対象が自ペアのものであることを WHERE 句で保証する
  （SELECT で確認してから UPDATE、という2段階にしない）

### テストで証明すること

| # | 内容 |
|---|---|
| 1 | ペアAのユーザーがペアBの投稿IDを指定しても取得・削除できない |
| 2 | 未認証アクセスで書き込み系の手続きが全て `FORBIDDEN` になる |
| 3 | 未認証アクセスで読み取れるのがデモペアのデータのみである |
| 4 | ペアに未所属のユーザーが投稿系の手続きを呼ぶと `NEEDS_ONBOARDING` になる |
| 5 | **`DEMO_COUPLE_ID` が未設定のとき、未認証アクセスが拒否される（fail-closed）** |
| 6 | **`DEMO_COUPLE_ID` が実在するが `is_demo` でないペアを指すとき、未認証アクセスが拒否される** |
| 7 | **ペアのもう1人が、共有でない `plan` を更新・削除できない**（`event.update` / `event.delete` の両方） |
| 8 | **更新の結果、更新前に編集できた側が編集できなくなる更新を拒否する**（`event.update`。**実行者自身と相手の両方**。とくに `anniversary`・`meetup` を非共有の `plan` へ変える経路。理由は `docs/tasks/021-plan-ownership.md`「`kind` の変更が権限を奪う」） |

**この表の全項目は、認可を触った全てのタスクで維持される。壊れたら実装が間違っている。**

**件数をここに書かない。**「7件」と書いてあったが、項目8を足した時点でずれた
（B が発見）。**表と件数を両方持つと、増やすたびに片方が古くなる。**
参照する側にも「件数と内容は出典側を見る」と書いてある（`docs/tasks/021`）。
**出典が自分の件数を数え直さなくて済む形にする。**
1つのタスクで書いて終わりにせず、以降のタスクでも緑であり続けることを確認する。

5 について。デモペアを作るのは 014 であり、それ以前は `DEMO_COUPLE_ID` が存在しない。
未設定のまま `ctx.coupleId` に `undefined` を入れて先へ進めると、
**条件が意図せず外れて全ペアのデータが返る**形になり得る。
「設定されていないから制限しない」ではなく「設定されていないから通さない」にする。

6 は 5 と別の経路である。**5 は値が無い場合、6 は値が有るが指す先が違う場合。**

`resolveCoupleContext` は冒頭で `if (!demoCoupleId)` を弾き、そのあと
`SELECT id FROM couples WHERE id = ?1 AND is_demo = 1` で照合する。
**5 のテスト（`null` と `""`）は冒頭のガードで止まり、照合まで到達しない。**
つまり **`AND is_demo = 1` を誰かが外しても、5 だけでは1件も落ちない**（R が走査して確認）。

**014 はこの値に初めて実在の ID が入るタスクである。**
設定を誤って**実在の非デモペア**を指した場合、未認証の閲覧者にそのペアのデータが出る。
T4（デモ経路からの本番データ漏洩）そのものであり、
**必要になる直前まで無防備だった。**

7 は**種類が違う。**1〜6 はすべて「**他のペアに触れない**」か「**未認証を通さない**」の話で、
**ペアの内側は同じ権限**という前提に立っている。

021 でその前提が変わった。`plan` にだけ**行ごとの持ち主**ができる
（`docs/tasks/021-plan-ownership.md`）。
**ペアの2人が同じものに触れるとは限らなくなった**ので、独立した項目にする。

`anniversary` と `meetup` は**変えていない。**ふたりの記念日・ふたりが会った事実であり、
個人のものではない。**「plan だけ」であることもテストで押さえる。**

拒否するのは**読み取りを含めた未認証アクセス全体**である。
書き込みは 2 で既に拒否されるため、5 が新たに保証するのは読み取りの側になる。
範囲が 2 と一部重なるが、fail-closed の原則としては
「有効な `couple_id` が存在しないなら何も通さない」が正しいので、あえて広く取る。

## 4. 招待コード

6桁は総当たりが現実的な長さである。以下の3点を**必ず全て**実装する。

| 対策 | 内容 |
|---|---|
| 有効期限 | 発行から24時間 |
| 同時発行数 | 1ペアにつき有効なコードは1件。再発行で前のコードを無効化する |
| レート制限 | `invite.accept` の失敗を **`user_id` と IP の二本立て**で制限する（下記）。超過で `RATE_LIMITED` |

- コードは暗号論的乱数（`crypto.getRandomValues`）で生成する。`Math.random()` を使わない
- 紛らわしい文字（0/O、1/I/l）を除いた文字集合を使う
- 使用済みコードは再利用しない（`used_at` で判定）

### レート制限のキー

**IP 単位だけに頼らない。** 当初はそう設計していたが、004 の監査で High 指摘を受けて変更した。

| キー | 上限 | 役割 |
|---|---|---|
| `account_hash` | 10回/時間 | **主たる防御線** |
| `ip_address` | 50回/時間 | 補助的な網 |

- **`user_id` を主にする理由**: `invite.accept` は認証必須なので `user_id` が必ず取れる。
  IPv6 では /64 のアドレスをローテーションできるため、IP 単位のみだと容易に回避される。
  `user_id` を回避するには Google アカウント自体を作り直す必要があり、コストが桁違いに高い

#### 訂正: 024 でその前提が崩れた。キーを Google アカウントに変える

**「Google アカウント自体を作り直す必要がある」は、024（アカウント削除）で
成り立たなくなった**（security-auditor が発見）。

**同じ Google アカウントで消して入り直すと、新しい `user.id` になる。**
`invite_failures` を `user_id` で消していたので、**10回失敗 → 削除 → 再登録 → また10回**
が無制限に回せる。

**実害は小さい。**コード空間は 32^6 ≈ 10.7億で、有効なコードは1ペアにつき1件・24時間。
**成功率は無視できる。**

**それでも直す。書いてある統制が、実際には効いていないからである。**

**キーを `user_id` から「Google アカウントのハッシュ」に変える。**

| | |
|---|---|
| 何を持つ | `account.accountId`（Google 側の識別子）を**塩付きでハッシュ**した値 |
| なぜ | **削除して入り直しても同じ値になる。**元の意図がそのまま成り立つ |
| `user` への FK | **持たない。**削除で消さない。**時間窓で自然に切れる** |
| 保持 | ハッシュと IP と時刻のみ。**元の識別子は復元できない** |

**024 が1つ簡単になる。**`invite_failures` が `user` を参照しなくなるので、
**削除の順序から1本外れる**（`user` より先に消す必要が無くなる）。

**アカウントを消しても、この行は時間窓が切れるまで残る。**
不正利用の防止のためであり、**「まっさらに登録し直せる」ことは損なわない**
（もう誰も指していない）。

**実装**: ハッシュは `apps/api/src/lib/account-hash.ts`
（`BETTER_AUTH_SECRET` で鍵付けしたHMAC-SHA256）。列の定義は
`packages/db/src/schema/couple.ts` の `inviteFailures`。
- **IP 側を緩くする理由**: CGNAT では多数の正当な利用者が1つの IP を共有する。
  IP を厳しくすると巻き添えで正当な利用者が締め出される。
  広く薄い網として置き、アカウントを量産する攻撃だけを捉える

両方を独立に評価し、どちらかを超えた時点で `RATE_LIMITED` を返す。

**IP が取得できない場合（ローカル開発等）は `account_hash` 単独で判定する。**
このとき記録には `ip_address` として `NULL` を入れる。
`"unknown"` のような固定の代用文字列を入れてはならない。
将来 IP 単位で集計したときに、その1つの値へ無関係な記録が集まり、
正当な利用者が巻き添えで締め出される。

## 5. 画像

- R2 バケットは**非公開**。公開URL・カスタムドメインを設定しない
- 表示は署名付き GET URL（有効期限1時間）
- アップロードは署名付き PUT URL（有効期限5分）。発行時に `contentType` とサイズ上限を検証する
- オブジェクトキーに推測可能な連番を使わない（`imageId` は ULID/UUID）
- **オブジェクトキーをクライアントから受け取らない。** 鍵は `couples/{coupleId}/...` という
  形をしており、受け取ることは `coupleId` を受け取ることと同じになる（3節に反する）。
  `post.uploadUrl` がサーバ側で `imageId` を生成し、鍵はサーバだけが組み立てる。
  **受け取ってから前綴りを検証する形にしない**
- 投稿削除時は D1 を先に更新し、そのあと R2 の削除を試みる。
  **R2 の削除に失敗しても投稿の削除は成功として扱う**（利用者の操作を掃除の失敗で失敗させない）。
  孤児オブジェクトは残りうる。**031で`post_images`は論理削除を持たない設計にしたため、
  `image_key`（`post_images.key`）はD1から消える**（それより前は`image_key`を
  残すことで回収していたが、その経路は無くなった）。回収は`post_images.key`・
  `user.image`のいずれからも参照されないオブジェクトをバケット走査で見つける形に
  一本化した（`architecture.md` 6節「アップロードされたが投稿に紐づかなかった画像」）

## 6. 入力検証

- 全ての手続きの入力を Zod で検証する
- 投稿本文に長さ上限を設ける（例: 2000文字）
- Drizzle のクエリビルダを使い、SQL 文字列を組み立てない
- React Native のテキスト描画は既定でエスケープされるが、
  Web 側で `dangerouslySetInnerHTML` を**使わない**

### 制御文字・双方向制御文字は正規化していない（027 で判断。2026-09-01）

`wish.title`・`wish.note`・`post.body`・`event.title` は **trim と長さしか
見ていない。**C0 制御文字も、表示の向きを変える双方向制御文字（U+202E 等）
も通る（`wish.note` は 028 で追加。方針は変えていない。security-auditor指摘:
列挙が実装に追いつかないと、次に読む人が「意図して外したのか、忘れたのか」
を判別できなくなる）。

**対策していない。**

**書ける相手がペアの2人しか居ないためである。**
9節の脅威一覧（T1〜T9）は「他の利用者」と「攻撃者」を相手にしている。
**自分のパートナーはそこに居ない。**

**入れるなら1箇所にまとめる。**`wish` にだけ入れると規則が2系統に割れる
（B の指摘。027）。置き場所は**共通の正規化**であって、手続きごとではない。
**片方だけ直すと、直っていない方が「意図して外した」のか
「忘れた」のか読めなくなる。**

**見直す条件は ADR-012 と同じである。身内でない利用者を招くとき。**

## 7. 通信・設定

| 項目 | 方針 |
|---|---|
| CORS（Worker） | 自ドメインのみ許可。`*` を設定しない |
| CORS（**R2 バケット**） | **別の設定である。**署名付きURLへのブラウザ直PUTに必要。許可は `PUT`/`GET` と実際のオリジンだけ。`*` を設定しない（`architecture.md` 6節） |
| CSRF | `SameSite=Lax` + oRPC の POST 経由。状態変更を GET で行わない |
| CSP | ランディングページと Web アプリに設定する |
| HTTPS | Cloudflare により常時。HTTP へのフォールバックを作らない |

## 8. ログとエラー

- 投稿本文・画像キー・メールアドレス・トークンをログに出さない
- クライアントに返すエラーメッセージにスタックトレース・SQL・内部パスを含めない
- サーバ内部のエラーは一意なIDを振り、クライアントにはIDのみ返す

| T7 | 依存ライブラリの既知脆弱性 | CI で `pnpm audit`。Dependabot を有効化（下記） |
| T8 | セッション奪取 | `HttpOnly` / `Secure` / `SameSite`、SecureStore。**024 以降は破壊的操作に再認証を要求する**（下記） |
| **T9** | **ログアウト後のクライアントキャッシュ残留による開示** | **利用者ごとに違う値を持つキャッシュは、キーに「誰であるか」を含める**（`architecture.md` 5節）。**手続きの戻り値に限らない**（招待コードのように、こちらが置いた値も対象）。**サーバ側の `couple_id` スコープはこれを止められない** |

### T8 の被害範囲が 024 で広がった

**024 より前、セッションを盗まれたときの被害は「私的な写真と記録を読まれる」だった。
024 以降は「2人分のデータが恒久的に消える」になる**（security-auditor の指摘）。

**`me.delete` はセッションの有無しか見ていない。**

**サーバ側でセッションの新鮮さを要求する。**

- **直近 N 分以内にサインインしたセッションでなければ `me.delete` を拒む**（既定は5分）
- **UI の確認段階を増やす形では足りない。**盗まれたセッションで直接呼ばれる。
  **UI 側の制御に依存しない**（T5 と同じ）
- **拒むときは、再認証が要ると分かる専用のエラーで返す。**
  画面は「もう一度ログインしてください」に落とす
- **レート制限は置かない。1回で全部消えるので、回数を絞っても意味が無い**

**先に確かめること。**Better Auth のセッションが持つ時刻のうち、
**どれが「実際にサインインした時刻」で、活動のたびに動かないか。**
**動く値を使うと、いつでも新鮮になって統制が効かない。**
**「`createdAt` のはず」で進めない**（`harness.md`「A は主張の根拠を実行して取る」）。

**対象は `me.delete` だけである。**他の削除（投稿・イベント）は1行で、
**取り返しのつかなさが桁違いに違う。**同じ扱いにしない。

**実装**: `session.createdAt` が固定値であることは Better Auth 本体のソース
（`node_modules` 配下）で確認済み。判定は `apps/api/src/lib/reauth.ts`。
`me.get` が返す真偽値は `sessionIsFresh`（`packages/contract/src/me.ts`）。
拒むときのエラーは `REAUTH_REQUIRED`。

**T9 は 015 の実機確認で人間が踏んだ**（ログアウト → ゲストモード → 前の利用者の
ペアのデータが出た）。**T1〜T8 はすべてサーバ側か通信路の話で、
クライアントのキャッシュだけが素通りしていた。**

**同じ人が使っている限りは実害が小さいが、端末を人に渡した瞬間に開示になる。**
**「自分のアカウントだから抜け穴ではない」は、同じ人が使っている間だけ成り立つ。**

T9の対策は`apps/app/test/viewer-key-coverage.test.ts`が機械的に固定して
いる（`apps/api/src/procedures/`の実際の定義を読み取ってから、対応する
呼び出し箇所を確認する形。手で一覧を維持しない）。ただしT1〜T8のように
security-auditorによる独立監査は通していない。次にセキュリティ監査を
行うときはT9も対象に含めること。

### CI の合否基準

**「CI で実行する」だけでは統制にならない。**何が起きたら赤くなるのかを決める。

| 検査 | 赤にする条件 | 理由 |
|---|---|---|
| gitleaks | **検出1件で赤。例外なし** | 秘密情報の混入は程度問題ではない。1件でも公開されれば失効させるしかない |
| `pnpm audit` | **high 以上で赤**（`--audit-level=high`）。moderate 以下は出力のみ。既知の到達不能な勧告は無視リストで除外する（下記） | 下記 |
| Dependabot | — | **セキュリティ更新のみ**。通常のバージョン更新は開けない |

**`pnpm audit` を moderate で赤にしない理由。**
修正版の出ていない moderate な間接依存の勧告が1件出ると、
**全てのPRが恒久的にマージ不能になる。**そのとき働く力は「勧告を直す」ではなく
「検査を外す・閾値を下げる・`--ignore` を足す」である。**検査そのものを殺す圧力を作らない。**
moderate 以下は出力に残し、公開前の全体監査（10節3）で人間が読む。

**Dependabot をセキュリティ更新のみにする理由。**
通常のバージョン更新を有効にすると、2〜4週間で公開する規模の開発に対して
PR の量が機能開発を圧迫する。T7 が求めているのは既知脆弱性への追随であって
最新版への追随ではない。

### 修正版の無い勧告の扱い（無視リスト）

**当初この節は「high なら赤」とだけ書いていた。それは誤りだった。**
`high` を「対処できる」の代用にしていたが、両者は別の軸である。

L11 の実装時に実測したところ、**導入した瞬間に high が2件出て CI が恒久的に赤くなる**
ことが分かった。どちらも `image-size` で、**修正版が存在しない**。

| | |
|---|---|
| GHSA | `GHSA-w3rx-r6r6-pgpr` / `GHSA-5p2g-fcmc-qvqq` |
| 経路 | `@better-auth/expo` → `expo` → `@expo/cli` → `react-native` → `metro` → `image-size` |
| 到達可能性 | Metro（開発時のバンドラ）経由のみ。デプロイ後の Worker と配信アセットには含まれない |
| 修正版 | **無し** |

**`pnpm audit --prod` では分離できない。** `@better-auth/expo` が `apps/api` の
**本番依存**であり、そこから Expo のツールチェーン一式が依存グラフに入るため、
`--prod` を付けても同じ4件が出る（実測確認済み。再挑戦しないこと）。
npm audit は package.json のグラフを歩くだけで、**実際にバンドルされるかは見ない。**

そこで無視リスト（`pnpm-workspace.yaml` の `auditConfig.ignoreGhsas`）を使う。
**`package.json` ではなく `pnpm-workspace.yaml` に置く。**理由は2つ。
`package.json` は標準 JSON でコメントを書けず、下記2の理由を項目ごとに残せない。
そして **pnpm 自身がこのファイルに書き込む**（下記）。

これは「検査を殺す圧力」の入り口になりうるため、**4つの縛りを付ける。**

1. **登録できるのは A だけ。** B は自分を通すために足さない。塞がれたら A に上げる
2. 各項目に **GHSA ID・パッケージ・なぜ到達不能か・修正版が出たら消すこと**を
   YAML コメントで書く
3. **無視した項目が不要になったら CI が赤くなるようにする**（下記「陳腐化の検出」）
4. **016 のリリース前に、無視リストの全項目を再評価する**（10節3の全体監査の一部）

#### `--ignore-unfixable` を使わない

**このフラグはフィルタではない。`pnpm-workspace.yaml` を書き換える。**

実測した（pnpm 11.24.0）。`pnpm audit --audit-level=high --ignore-unfixable` は
exit 0 を返すが、同時に `auditConfig.ignoreGhsas` を**ファイルに追記する**。
2回目以降は「No new vulnerabilities were ignored」となり、追記済みだから静かになる。

「修正版が無いものは赤にしない」という規則をフラグ1つで表現できるように見えるが、
実際には無視リストを**理由のコメントを伴わない形で自動生成する**。
CI で使えば、実行のたびに作業ツリーが書き換わる。

**CI・スクリプト・手元の確認、いずれでも使わない。**

#### 陳腐化の検出

当初この節は「無視リストとは別に、全重大度の `pnpm audit` を出力専用で走らせる。
無視したものが見えなくなる状態を作らない」と書いていた。
**`pnpm audit` の CLI のオプションだけでは実現できない。**
無視リストを一時的に外す方法が無く、出力専用で走らせても要約が `(N ignored)` に
なるだけで詳細は出ない（L11 の実装時に B が実測して報告した）。

`auditConfig` を**一時的に取り除いてから走らせる**なら可能である。
A は当初これを「実現できない」と書いたが、B が陳腐化検出の実装でこの手法を採り、
**実際に動くことを示した。**記述を訂正する。

CI には全重大度の `pnpm audit` を出力専用（`|| true`）で置いてある。
無視リストの影響を受けるため詳細は出ないが、要約の `(N ignored)` で件数は見える。
**これは統制ではなく、人間が読む材料である。**

そのうえで、**無視リストを外した全件出力のステップは足さない。**
緑の CI のログは読まれない。同じ手法を使うなら、読まれない出力を増やすより
**赤くなる検査**に使う方が強い。

**CI は、`ignoreGhsas` の項目が監査結果に現れなくなったとき赤にする。**

その項目はもう不要である。修正版が出て依存が上がったか、依存自体が消えたか、
いずれにせよ**無視し続ける理由が無くなっている。**放置すると、無視リストは
「かつて何かがあった痕跡」の山になり、次に本物が紛れ込んでも気づけない。

この検査があれば、無視リストは**放っておくと縮む方向に働く。**

この検査は `auditConfig` を一時的に外して `pnpm audit` を走らせる。
**リポジトリのファイルを書き換える手法である以上、2つの性質を満たすこと。**

| 性質 | 理由 |
|---|---|
| **途中で失敗しても元に戻る** | 手元で実行した人の作業ツリーを壊さない。CI は使い捨てだが手元は違う |
| **レジストリの障害で赤にしない** | npm レジストリが落ちただけで赤くなる検査は、いずれ外される。`--ignore-registry-errors` に相当する扱いにする |

2つ目は 9節の冒頭と同じ理屈である。**検査そのものを殺す圧力を作らない。**

#### ゲートと陳腐化検出で、障害時の倒れ方を変える

**この2つは意図的に非対称である。後から揃えないこと。**

| 検査 | レジストリ障害・解析失敗のとき | 理由 |
|---|---|---|
| `pnpm audit --audit-level=high`（ゲート） | **赤にする**（`--ignore-registry-errors` を付けない） | 脆弱性の有無が確認できていない。「確認できないから通す」は 3節のテスト5と同じ誤り。**確認できないなら通さない** |
| 陳腐化検出 | **判定を見送る**（赤にしない） | 無視リストが陳腐化しているかは衛生の問題であって、脆弱性の有無ではない。判定できないことは危険を意味しない。取りこぼしは 016 の再評価で拾える |

ゲートが赤いまま止まるのは、レジストリが復旧するまでの短い間である。
**その不便を理由に `--ignore-registry-errors` をゲート側へ足さない。**
足せば、レジストリが落ちている間のPRは**検査を通っていないのに緑になる。**


全重大度の `pnpm audit` は引き続き実行してログに残すが、
それは人間が読む前提の材料であって統制ではない。

**「赤いから外す」ではなく「到達しないから外す」である。**
判断の根拠は重大度ではなく、**攻撃者が到達できる経路にあるかどうか**に置く。
到達可能な勧告は、修正版が無くても赤にする。そのときは依存自体を捨てる判断に進む。

### 公開前に履歴全体を1度走査する

CI の gitleaks は差分を見る。**リポジトリは 016 で Private から Public に切り替える**
（ADR-011）。切り替え前に、**履歴全体**に対して gitleaks を1度走らせる。

差分検査は、検査を導入する前に混入したものを見つけられない。
Public にした時点で履歴は全て読まれる。

## 10. 監査の実施タイミング

`.claude/agents/security-auditor.md` を起動する。

1. 認証・招待・画像アップロード・認可ミドルウェアを触ったタスクの完了時（**必須**）
2. その他のタスクはマイルストーン単位でまとめて
3. 公開直前に全体監査

静的ツール（`pnpm audit`、gitleaks）を先に実行し、その出力を監査エージェントに読ませる。

### 監査結果の記録手順

監査エージェントは**書き込み権限を持たない**（`Read` / `Grep` / `Glob` のみ）。
報告を返すだけなので、B が以下の2箇所に残す。

| 保存先 | 内容 |
|---|---|
| `artifacts/NNN/security-audit-raw.md` | 監査エージェントの返答を**一字一句そのまま**保存する |
| `docs/security-report.md` | 上記を追記形式で転記する |

- **指摘ゼロの場合も記録する**（「監査済み・指摘なし」）
- **監査役を呼ぶときにモデルを指定しない。** `.claude/agents/security-auditor.md` の
  frontmatter が `model: opus` を持っており、呼び出し側が指定しなければそれが使われる。
  B が Sonnet でも監査役は Opus のまま動く。呼び出し時の明示指定は frontmatter より
  優先されてしまうため、指定してはならない（コスト設計上、監査は Opus に寄せる。`docs/harness.md` 11節）
- 2箇所に分けるのは、B が指摘を薄めていないかを R が突き合わせて検証できるようにするため。
  R は生の出力と `security-report.md` の両方を読み、**生の出力の内容が転記側に
  すべて含まれていること**を確認する
- **完全一致は求めない。**指摘が後から誤りと分かった場合、転記側には打ち消し線と
  訂正が加わる（`conventions.md` 9節）。**元の内容が残った上での追記**であることを
  確認する。元の内容ごと消えていたら、それは薄めたのと同じである
- 監査エージェントに書き込み権限を与えない。与えた時点で読み取り専用の監査役ではなくなる
