# 規約: futary

## 1. 言語

- コードコメント・ドキュメント・コミットメッセージ・UI文言はすべて**日本語**
- 識別子（変数名・関数名・テーブル名）は英語

## 2. TypeScript

- `strict: true`。`any` を書かない。どうしても必要なら `unknown` + Zod で絞る
- 型は `packages/contract` の Zod スキーマから導出する。同じ形の型を手で二重定義しない
- 関数の戻り値型は公開APIには明示、内部関数は推論に任せる
- `null` と `undefined` を混在させない。DB由来の欠損は `null`、未指定は `undefined`

## 3. ディレクトリと命名

| 対象 | 規則 | 例 |
|---|---|---|
| ファイル | kebab-case | `post-card.tsx` |
| コンポーネント | PascalCase | `PostCard` |
| 関数・変数 | camelCase | `daysTogether` |
| DB テーブル・カラム | snake_case | `couple_members`, `created_at` |
| oRPC 手続き | `名詞.動詞` | `post.create` |

## 4. UI とスタイリング

### スタイリング

- 色・余白・角丸は `packages/ui` のトークン経由でのみ参照する。**生の16進カラーをコンポーネントに書かない**
- トークンにない値が必要になったら、まずトークンを増やすべきか検討する

### 副作用を伴うボタンは二重発火を防ぐ

**送信・認証・作成・削除など、押すと状態が変わるボタンは全て対象。**
処理中は無効化し、完了または失敗まで再度発火させない。

これは見た目の問題ではない。M1 の実機確認で、
**ログインボタンの二重発火が OAuth の state 競合を起こして認証が失敗した**（PR #22）。
二重に走った結果が壊れるかどうかは、押した先の処理に依存する。
**個別に判断せず、副作用があるなら一律で防ぐ。**

対象の例: ログイン / 投稿 / リアクション / 招待コードの発行と使用 / イベントの登録・削除。

#### ガードは `Button` に組み込む。呼び出し側に任せない

**`packages/ui` の `Button` が自前でガードを持つ。** 各画面が個別に書かない。

呼び出し側に任せると、005 で認可について潰したのと同じ形になる。

> 手続きごとに認可を書くと、必ずどこかで書き忘れる（`security-requirements.md` 3節）

実際、この規約を書いた時点で 004 のボタン3つ
（`couple.create` / `invite.issue` / `invite.accept`）は未対応のまま残っていた。
**規約を書いただけでは遡及しない。** 単一の防御線にする。

- ガードは `useRef` で持つ。`useState` は更新が非同期で、
  同一ティック内の2回目の発火を取りこぼす（PR #22 のレビュー指摘）
- **副作用のある操作に、生の `Pressable` を直接使わない。** `Button` を通す。
  `Pressable` を直接使ってよいのは、画面遷移や表示の切り替えなど副作用が無いものだけ
- 根本原因は `react-native-web` の `Pressable` が環境によって
  1クリックで `onPress` を2回発火させること。**上位で塞ぐ**

## 5. API 実装

- 全ての手続きの入力を Zod で検証する。検証なしの手続きを作らない
- **引数に `coupleId` を持つ手続きを作らない。** `ctx.coupleId` のみを使う（`architecture.md` 5節）
- エラーは oRPC のエラー型で返す。スタックトレースをクライアントに出さない
- エラーコードは `NEEDS_ONBOARDING` / `FORBIDDEN` / `NOT_FOUND` / `INVALID_INPUT` / `RATE_LIMITED` を基本とする

## 6. テスト

| 種別 | 対象 | 道具 |
|---|---|---|
| 単体 | 日付計算、統計、`memory.get` の探索順、招待コード生成 | Vitest |
| 結合 | oRPC 手続き（D1 のローカル実体に対して） | Vitest + Miniflare |
| 画面結合 | 画面とデータ取得の配線（一覧・投稿作成・空状態・エラー） | Vitest + React Native Testing Library（oRPC クライアントをモック） |
| E2E | **未認証のデモ閲覧経路のみ**（014 で導入） | Playwright（Web） |

**認証を伴う導線（ログイン → 投稿 → リアクション）を Playwright で自動化しない。**
Google OAuth の自動化は実アカウントかモック IdP を要し、得られる保証に対して重い。
この範囲はマイルストーンの区切りで**人間が実機で確認する**ことで担保する
（`docs/state.md` の受け入れ記録がその証跡になる）。

画面結合テストは oRPC クライアントをモックするため、**サーバとの契約は検証しない**。
契約は `packages/contract` の型と、`apps/api` 側の結合テストが受け持つ。
自動テストで担保していない範囲を、担保しているかのように書かない。

### 必ずテストを書く対象

- **認可**: 他ペアのデータが取得できないこと、未認証で書き込みが拒否されること
- 日付・タイムゾーンが絡む計算（JST 固定である以上、ここは必ず壊れる）
- 制約（1人1ペア、1ペア2人、招待コードの1回限り）

「動くこと」より「**壊れてはいけないことが壊れていないこと**」を優先して書く。

## 7. Git

### ブランチの命名

3種類だけ。`main` に直接コミットしない。

| 形 | 用途 | 受け入れ基準 |
|---|---|---|
| `task/NNN-短い説明` | タスクファイルに紐づく実装 | タスクファイルの確認観点と完了条件 |
| `fix/短い説明` | **タスク外で見つかった不具合の修正** | 下記「不具合修正 PR の受け入れ基準」 |
| `docs/短い説明` | 設計ドキュメントのみの変更（A） | 差分が設計ドキュメントに閉じていること |

- 1タスク = 1ブランチ = 1PR
- 不具合修正にタスク番号を付けない。**どのタスクの責任かを決められないことが多い**
  （実機確認で見つかった不具合は複数タスクにまたがる）。
  無理に番号を付けると、その番号のタスクの完了条件が誤って適用される

### `fix/` と `task/` の境界

**設計判断を含むかどうか**で分ける。

| 判定 | 例 |
|---|---|
| `fix/` | 相対パスを絶対パスに直す。二重発火を防ぐ。条件の書き忘れを足す |
| `task/`（A がタスクを起票する） | 認証方式を変える。テーブルを足す。新しい手続きを増やす |

判断に迷ったら A に上げる。**迷った時点で設計判断の可能性が高い。**

### 不具合修正 PR の受け入れ基準

`fix/` にはタスクファイルが無い。**採点表が無いままレビューさせない。**
PR 本文に次の4点を書く。これが R の採点表になる。

1. **観測した事象** — 再現手順を含む
2. **原因**
3. **再発を防ぐ手段** — 回帰テスト。書けない場合は**書けない理由**
4. **影響範囲** — 他に同じ形の箇所が無いか確認した結果

加えて既存のテストが緑であること。

**手続きを重くしない。** タスクファイルを作らせない、証跡ディレクトリを要求しない。
不具合修正が面倒になると、機能開発にまとめて紛れ込ませる方向に働く。
それは修正そのものより悪い。

### コミットメッセージ

- 日本語1行。必要なら本文で理由を書く
  ```
  投稿一覧にカーソルページングを追加

  1回の取得を20件に固定し、created_at と id の複合カーソルで
  同一秒の投稿が重複・欠落しないようにした。
  ```
- `main` に直接コミットしない

### マージ戦略

**squash merge を使う。** `main` は「1タスク = 1コミット」に保つ。

rebase / merge commit を採らない理由は、レビュー往復の途中経過
（「R-17対応」「テスト追加」等）が `main` に載るため。このリポジトリは
転職活動で読まれる想定であり、`main` の履歴が
「001: 歩くスケルトン」「002: デザイントークン」…と並ぶ形の可読性を優先する。

### squash 時の必須手順

squash merge は、PR が複数コミットのとき各メッセージを本文に連結するため、
**`Session:` トレーラーが解析できなくなる**（実例: `a2f6eb2` で消失）。
マージする者が squash コミットのメッセージに明示的に書き込む。

```bash
gh pr merge <番号> --squash --subject "003: 認証基盤 (#5)" --body "$(cat <<'EOF'
<変更の要約>

Session: B
EOF
)"
```

マージ後、`main` 上でトレーラーが残っていることを確認する。

```bash
git log -1 --format='%(trailers:key=Session,valueonly)'
```

## 8. 動作証跡

タスク完了時に `artifacts/NNN/` へ残す。

| 内容 | 常に | UI変更時 |
|---|---|---|
| テスト実行結果（テキスト） | ○ | ○ |
| スクリーンショット | − | ○ |
| 手動確認の手順と結果 | ○ | ○ |

スクリーンショットは容量を食うため、UI変更を含まないタスクでは撮らない。

### 人間の操作が要る証跡が取れないとき

実機ログインのように**人間しか実行できない**証跡は、その人間が居ないと取れない。
このとき取る手順を決めておく。

1. **条件を満たしたことにしない。** チェックを付けない
2. **未達として `state.md` の論点に起票する。** 何が未確認で、いつ・誰が回収するかを書く
3. **タスクのマージは止めない。** レビューは証跡と独立に進められる
4. **マイルストーンの受け入れでまとめて回収する。**
   人間が実機に触るのはそこなので、複数タスク分を1回で消化できる

前例: 003・004 は Google OAuth クライアント未取得のため実機確認を残したまま
マージし、L14 として追跡して 2026-08-29 にまとめて回収した。

**「証跡が取れないから条件を緩める」ではない。**条件はそのまま残し、
未達であることを見える場所に置く。回収されないまま公開に至る経路を作らない。

## 9. 設計ドキュメントの所有権

**設計ドキュメントを書き換えられるのは A だけ。**

| ファイル | 書き換えられる役 |
|---|---|
| `docs/requirements.md` / `architecture.md` / `decisions.md` / `security-requirements.md` / `conventions.md` | **A のみ** |
| `docs/harness.md` / `CLAUDE.md` / `.claude/agents/*` | **A のみ** |
| `docs/tasks/NNN-*.md` の **目的 / 実装内容 / 確認観点 / 完了条件 / 停止条件** | **A のみ** |
| `docs/tasks/NNN-*.md` の **進捗チェックボックス / 実装メモ節** | B |
| `docs/state.md` / `docs/worklog.md` | A / R / B すべて |
| `artifacts/NNN/` | B |

タスクファイルは「A が定めた受け入れ基準」と「B が残す進捗記録」が同居している。
前者は B が触らない。後者は B が毎回更新する。**受け入れ基準を実装者が
書き換えられる状態にしない**ことが目的であり、進捗の記録を止める意図はない。

### `state.md` は3役が書ける唯一のファイル。競合しうる

worktree を分けた結果、A / R / B はそれぞれ別のブランチで同じ `state.md` を
編集できる。**マージ時に競合が起きうる。**

| 状況 | 結果 |
|---|---|
| B が「現在のフェーズ」、A が「未解決の論点」を編集 | 自動マージされる |
| **A と B が両方とも論点テーブルの末尾に行を足す** | **競合する** |
| 同じ論点を両方が解決済みに書き換える | 競合する |

論点の追加は毎回テーブル末尾に足すため、そこが最も起きやすい。

#### 回避しない。競合したら解消する

**各役は必要なときに `state.md` を書く。** 他の役の状態を見て書くのを控えない。

競合したときの正解は常に「**両方残す**」。論点テーブルはリストなので、
和集合が正しい。どちらかを選ぶ判断はしない。
番号が重複したら、後から入った方を採番し直す。

これはコードの競合とは質が違う。**git が止めるだけで、内容の判断は不要。**

#### なぜ「B の PR が開いている間は書かない」としないのか

一度その回避策を書いたが、削除した。理由は2つある。

1. **`harness.md` の worktree 分離で消したはずの構造が戻る。**
   「B の状態を見て A が書くのを控える」という形そのものが、分離の目的だった
   「A はいつでも書ける」を打ち消す
2. **A → メッセージ → B が転記、という経路が帰属を壊す。**
   B が A の文言を転記すれば `Session: B` になる。
   書き手の記録（9節）が意味を失い、003 で訂正させた形が運用として常態化する

競合の実害（git が止まる、和集合を取る）より、回避の実害
（B の状態を気にする認知負荷、帰属の破壊）の方が重い。

### なぜ例外を作らないか

監査プロトコルを定めているのは `security-requirements.md` である。
**監査される側（B）がそれを書き換えられる状態は、Maker-Checker の穴になる。**
今回は強化方向の変更だったが、「監査役の出力は要約でよい」という弱化方向の変更も
同じ経路を通る。方向を問わず経路ごと塞ぐ。

「明白なバグだから」という例外も作らない。明白さの判定を実装者に委ねた時点で、
判定基準が実装者の都合に寄る。

### B が設計ドキュメントの誤りを見つけたとき

1. `docs/state.md` の「未解決の論点」に起票する
2. A にメッセージで知らせる（中身ではなくポインタを渡す）
3. **A の返答を待たずに実装を進める。** ドキュメントの誤りは実装を止めない。
   正しいと判断した実装を進め、ドキュメントは A が並行して直す
4. 食い違ったまま実装が進んだ場合は、R が受け入れ判定で差し戻す

この手順により、A 待ちで B が止まることは無い。

### 書き手の記録（違反が痕跡を残すようにする）

A / R / B は**同じ git identity を共有している**。したがって差分からもコミットからも
書き手を判別できない。所有権のルールがあっても、違反が記録に残らなければ意味が薄い。

**全てのコミットメッセージの末尾に、書き手の役を1行入れる。**

```
Session: B
```

- `A` / `R` / `B` のいずれか
- **`Co-Authored-By` と同じブロックに、空行を挟まずに置く。** git はメッセージの
  最後の段落だけをトレーラーとして解析するため、間に空行があると
  `Session:` 行は本文として扱われ、`%(trailers)` で取り出せなくなる

```
<本文>

Session: B
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```
- **1つの PR に含める役は1つだけ。** A の設計変更と B の実装を同じ PR に混ぜない
- R は受け入れ判定時、設計ドキュメントの差分を含む PR の `Session:` 行を確認する。
  `B` になっていれば所有権違反として差し戻す

#### この仕組みで検出できること・できないこと

| | |
|---|---|
| 検出できる | 事故・失念（役の付け忘れ、意図しない混入） |
| **検出できない** | **意図的な詐称。** B が自分の設計変更に `Session: A` と書いても見抜けない |

`Session:` 行は**自己申告**である。統制の実体は
「R がマージ前のブランチ上で差分を確認すること」の方にあり、
`Session:` 行はそれを事後に辿れるようにする補助にすぎない。
**この記録があることをもって「所有権が保証されている」と読んではならない。**

### 役ごとに作業ディレクトリを分ける

**A / R / B はそれぞれ別の作業ディレクトリで動く。** 設定は `harness.md` 3節を参照。

| ディレクトリ | 役 |
|---|---|
| `futary/` | **B**（実装）。`main` ブランチはここが持つ |
| `futary-A/` | **A**（設計） |
| `futary-R/` | **R**（レビュー） |

- **自分のディレクトリの外でファイルを編集しない。** 他の役の作業ツリーに書き込むと、
  分離した意味が消える
- A はいつでも設計ドキュメントを変更できる。B の区切りを待つ必要はない
- R はブランチを自由にチェックアウトできる。B の作業ツリーは動かない

分離前は単一の作業ツリーを共有しており、A の編集が B のコミットに混入し、
B が `git reset --hard` を打てば A の未コミット分が消える状態だった（旧 L18）。

#### 急ぎの設計判断が必要になったとき（「1 PR = 1 役」の例外を作らない）

R からのエスカレーションなどで、B の作業を止めないために A の判断が急ぎ必要になることがある。
このとき**同じ PR に A と B を混ぜる必要は無い**。判断とドキュメントを分けて考える。

| 運ぶもの | 経路 | B が待つか |
|---|---|---|
| **判断そのもの** | A から B / R へのメッセージ | **待たない。** 受け取った時点で実装できる |
| **ドキュメントへの反映** | A 単独の PR | 待たない。並行して進む |

B が必要としているのは判断であって、ドキュメントのマージではない。
ドキュメントはコンパイルされないので、B の実装を1秒も止めない。

したがって **「1 PR = 1 役」に例外は無い。**
A は自分の PR を出し、B は自分の PR を出す。

**ただし新しいセッションは別。** `/clear` した B はメッセージを引き継がない。
タスクファイル・`state.md` のみを読む。
**新セッションが着手する前に反映が必要な変更は、着手前に main へマージする。**

### 引用先と引用元の食い違いをどう判定するか

タスクファイルは恒久ドキュメントを出典に指すことがある
（例: 005 の「テストで証明すること（`security-requirements.md` 3節）」）。
両者の文言が違うとき、**逐語一致を求めない。**

判定基準は「**引用側が出典側を満たしているか**」だけ。

| 向き | 例 | 扱い |
|---|---|---|
| 引用側が**広い** | 恒久側「投稿IDを指定しても取得できない」→ タスク側「レコードIDを指定しても取得・更新・削除できない」 | **妥当。** その時点の実装に合わせた一般化であり、恒久側の要求を満たしたうえで超えている |
| 引用側が**狭い** | 恒久側が5項目、タスク側が4項目 | **危険。** タスク側だけを見て実装すると恒久基準を満たせない。直す |

逐語一致を規則にすると、上段の妥当な特殊化まで潰れる。

#### 件数・項目数を引用側に書かない

「005 の認可テスト**4件**が緑」のように、引用側に数を書くと**そこがズレの起点になる**。
恒久側が5件に増えても、引用側の数は誰も直さない。

**数は出典側にだけ置く。** 引用側は「`security-requirements.md` 3節のテストが緑」と書く。
006 で実際にこれが起きた（恒久側は PR #17 で5件になっていたが、
タスクファイルは4件のまま。実装は5件とも満たしていたので実害は出なかった）。

他のタスクファイルが「005 の認可テストも緑」と件数抜きで書いていたのは正しい形である。

**恒久ドキュメント側が狭い場合はより深刻。** タスクファイルは1タスク限りだが、
恒久ドキュメントは以降の全タスクで維持される基準である。
恒久側に無い項目は、そのタスクが終わった時点で失われる。
**タスクで基準を1つ足したら、恒久側にも足したかを必ず確認する。**

## 10. 完了時の必須動作

**ファイル変更を伴う作業が終わったら、必ず両方を更新する。**

1. `docs/state.md` を現在地に合わせて書き換える
2. `docs/worklog.md` に追記する（既存行は編集・削除しない）

これを怠るとコンテキスト圧縮後に再開できなくなる。
