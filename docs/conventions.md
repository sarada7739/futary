# 規約: futary

## 1. 言語

- コードコメント・ドキュメント・コミットメッセージ・UI文言はすべて**日本語**
- 識別子（変数名・関数名・テーブル名）は英語

## 2. TypeScript

- `strict: true`。`any` を書かない。どうしても必要なら `unknown` + Zod で絞る
- 型は `packages/contract` の Zod スキーマから導出する。同じ形の型を手で二重定義しない
- 関数の戻り値型は公開APIには明示、内部関数は推論に任せる
- `null` と `undefined` を混在させない。DB由来の欠損は `null`、未指定は `undefined`

## 3. ディレクトリと命名

| 対象 | 規則 | 例 |
|---|---|---|
| ファイル | kebab-case | `post-card.tsx` |
| コンポーネント | PascalCase | `PostCard` |
| 関数・変数 | camelCase | `daysTogether` |
| DB テーブル・カラム | snake_case | `couple_members`, `created_at` |
| oRPC 手続き | `名詞.動詞` | `post.create` |

## 4. UI とスタイリング

### スタイリング

- 色・余白・角丸は `packages/ui` のトークン経由でのみ参照する。**生の16進カラーをコンポーネントに書かない**
- トークンにない値が必要になったら、まずトークンを増やすべきか検討する

### 副作用を伴うボタンは二重発火を防ぐ

**送信・認証・作成・削除など、押すと状態が変わるボタンは全て対象。**
処理中は無効化し、完了または失敗まで再度発火させない。

これは見た目の問題ではない。M1 の実機確認で、
**ログインボタンの二重発火が OAuth の state 競合を起こして認証が失敗した**（PR #22）。
二重に走った結果が壊れるかどうかは、押した先の処理に依存する。
**個別に判断せず、副作用があるなら一律で防ぐ。**

対象の例: ログイン / 投稿 / リアクション / 招待コードの発行と使用 / イベントの登録・削除。

#### ガードは `Button` に組み込む。呼び出し側に任せない

**`packages/ui` の `Button` が自前でガードを持つ。** 各画面が個別に書かない。

呼び出し側に任せると、005 で認可について潰したのと同じ形になる。

> 手続きごとに認可を書くと、必ずどこかで書き忘れる（`security-requirements.md` 3節）

実際、この規約を書いた時点で 004 のボタン3つ
（`couple.create` / `invite.issue` / `invite.accept`）は未対応のまま残っていた。
**規約を書いただけでは遡及しない。** 単一の防御線にする。

- ガードは `useRef` で持つ。`useState` は更新が非同期で、
  同一ティック内の2回目の発火を取りこぼす（PR #22 のレビュー指摘）
- **副作用のある操作に、生の `Pressable` を直接使わない。** `Button` を通す。
  `Pressable` を直接使ってよいのは、画面遷移や表示の切り替えなど副作用が無いものだけ
- 根本原因は `react-native-web` の `Pressable` が環境によって
  1クリックで `onPress` を2回発火させること。**上位で塞ぐ**

## 5. API 実装

- 全ての手続きの入力を Zod で検証する。検証なしの手続きを作らない
- **引数に `coupleId` を持つ手続きを作らない。** `ctx.coupleId` のみを使う（`architecture.md` 5節）
- エラーは oRPC のエラー型で返す。スタックトレースをクライアントに出さない
- エラーコードは `NEEDS_ONBOARDING` / `FORBIDDEN` / `NOT_FOUND` / `INVALID_INPUT` / `RATE_LIMITED` を基本とする

## 6. テスト

| 種別 | 対象 | 道具 |
|---|---|---|
| 単体 | 日付計算、統計、`memory.get` の探索順、招待コード生成 | Vitest |
| 結合 | oRPC 手続き（D1 のローカル実体に対して） | Vitest + Miniflare |
| 画面結合 | 画面とデータ取得の配線（一覧・投稿作成・空状態・エラー） | Vitest + React Native Testing Library（oRPC クライアントをモック） |
| E2E | **未認証のデモ閲覧経路のみ**（014 で導入） | Playwright（Web） |

**認証を伴う導線（ログイン → 投稿 → リアクション）を Playwright で自動化しない。**
Google OAuth の自動化は実アカウントかモック IdP を要し、得られる保証に対して重い。
この範囲はマイルストーンの区切りで**人間が実機で確認する**ことで担保する
（`docs/state.md` の受け入れ記録がその証跡になる）。

画面結合テストは oRPC クライアントをモックするため、**サーバとの契約は検証しない**。
契約は `packages/contract` の型と、`apps/api` 側の結合テストが受け持つ。
自動テストで担保していない範囲を、担保しているかのように書かない。

### 画面結合テスト（jsdom）が見ないもの

**要素が実際に触れる場所にあるかを見ていない。**
`fireEvent` は対象の要素へ直接イベントを発火する。その要素が他の要素に覆われて
いても、画面外にあっても、大きさがゼロでも、**テストは緑になる。**

017 で実際に踏んだ。閉じるための領域が別の要素に覆われていて実機では閉じられない
のに、テストは通っていた。**「通っているのに壊れている」形である。**

- `onLayout` は jsdom で発火しない。**レイアウトに依存する計算はテストできない**
- 重なり・寸法・スクロール位置も見えない

**だから、当たり判定に依存する設計を避ける。**テストを足すのではなく、
**当たり判定が正しさを左右しない形に寄せる。**
どうしても必要なら、そこは人間の実機確認が唯一の担保になると明記する。

### 期待値と突き合わせるテストが見ないもの

**「テストが緑」は「期待値が正しい」を意味しない。**

`apps/api/test/schema-integrity.test.ts` は、DB の実体（`sqlite_master`）を
**手で書いた期待値の配列**と突き合わせる。**実体が期待値から外れれば落ちる。**

**期待値そのものは、誰も証明していない**（R の指摘）。

表の作り直しで索引が2本消えたとき、**期待値からその2本を消せば緑になる。**
テストは「実体と期待値が一致した」と**正しく報告する。**
守りたかったものは消えているのに、である。

- **期待値を減らす差分は、テストが守れない場所である。**
  **減った行は差分に出る。R はそこを読む。**
  減らした理由を PR 本文に書いておくと、**理由まで含めて確かめられる**ので速い
- **本文に頼らない。**「本文に書く」を主にすると、
  **書き忘れた瞬間に網が消える**（R の指摘）。**差分が主、本文は補助である**
- **実装した側が自分で気づく形にはなっていない。**Maker-Checker でしか埋まらない
- 019 で「制約が存在することを証明する」と書いたが、証明しているのは
  **期待値に対して**である

**同じ形は、期待値を持つテスト全部にある。**スナップショット・期待値の配列・
固定の文字列。**落ちたときに期待値を書き換えて通すのが、最も速い直し方であり、
最も見えない壊し方である。**

### 検証の範囲から外したものは、結果に書く

**テストに限らない。**「確認した」「一致した」「0件だった」と報告するとき、
**何を見なかったかを一緒に書く。**

A が古いブランチ6本の中身が main にあるかを1行ずつ照合し、
**`fix/persistent-tab-bar-review-record` は「31行中 main に無い行は0」と
報告した。誤りだった**（R が発見）。照合が
**`docs/worklog.md` と `docs/state.md` を除外していた**のに、
**除外したことを結果に書いていなかった。**実際には `docs/worklog.md` に
**1日ぶんの節（13行）が丸ごと欠けていた。**

**除外そのものは妥当だった**（追記専用で `merge=union` のため差分が大きい）。
**問題は、除外を黙ったまま「0」と言ったことである。**

**「0件」は範囲とセットでしか意味を持たない。**
範囲を書かない0件は、**見た範囲が広いほど正しく見える。**

同じ形を同じ日に3人が踏んでいる。

| 誰 | 何を見ていないのに、見たように書いたか |
|---|---|
| A | 照合から `worklog.md` を外したまま「0件」 |
| R | `git diff --exit-code` は**未追跡ファイルを見ない**のに「差分が無ければ通る」 |
| A | `git add -A` だけを禁じ、**`git commit -a` を塞いでいない**のに「歯止め」 |

**除外することと、除外したと書くことは別である。**
後者を落とすと、**網の目が実際より細かく見える。**

### 「`main` に直接コミットしない」には機械的な網が無い

この規約は**2箇所で**そう書いている（7節・下記）。**破れる。**

欠落した worklog の節を main へ戻すとき、**PR を通さず main へ直接 push された**
（`5807dab`）。**内容は原本と一字一句一致していた。**
main の他のコミットはすべて PR 由来である。

**実害は「内容が違うこと」ではなかった。**同じ復元が
**`5807dab`（main）と `a1d76a5`（`task/021-plan-ownership`）の2つ**として存在し、
**追加内容が完全に一致している**（R が発見）。
`docs/worklog.md` は `merge=union` なので、**021 をマージした時点で同じ節が
2回並び、警告は何も出ない。**

**PR を通していれば、マージの場で誰かが気づいた。直接 push はその場所を飛ばす。**
`.gitattributes` のコメントが書いているとおり union は
「**競合そのものが起きない**」——**衝突しない設定は、二重化も静かに通す。**

**内容が正しかったことと、経路が規約どおりだったことは別である。**
**R は見ていない。**とくに**「消えた記録を戻す」変更**は、
戻し方が正しいかを**誰かが確かめる価値が最も高い部類**である。

**GitHub のブランチ保護を掛ければ、この規約は破れなくなる**
（`main` への直接 push を拒否し、PR を必須にする）。
**リポジトリの設定なので、人間の操作が要る。**016 の公開前に掛けるのが自然である。

**規約に「しない」と書いてあるものは、まだ誰も止めていない。**

### 必ずテストを書く対象

- **認可**: 他ペアのデータが取得できないこと、未認証で書き込みが拒否されること
- 日付・タイムゾーンが絡む計算（JST 固定である以上、ここは必ず壊れる）
- 制約（1人1ペア、1ペア2人、招待コードの1回限り）

「動くこと」より「**壊れてはいけないことが壊れていないこと**」を優先して書く。

## 7. Git

### ブランチの命名

3種類だけ。`main` に直接コミットしない。

| 形 | 用途 | 受け入れ基準 |
|---|---|---|
| `task/NNN-短い説明` | タスクファイルに紐づく実装 | タスクファイルの確認観点と完了条件 |
| `fix/短い説明` | **タスク外で見つかった不具合の修正** | 下記「不具合修正 PR の受け入れ基準」 |
| `docs/短い説明` | 設計ドキュメントのみの変更（A） | 差分が設計ドキュメントに閉じていること |
| `dependabot/…` | **Dependabot が自動で作る**（人が作らない） | 下記 |

- 1タスク = 1ブランチ = 1PR
- 不具合修正にタスク番号を付けない。**どのタスクの責任かを決められないことが多い**
  （実機確認で見つかった不具合は複数タスクにまたがる）。
  無理に番号を付けると、その番号のタスクの完了条件が誤って適用される

### Dependabot のブランチ

Dependabot はこの命名規約を知らない。`dependabot/…` を4つ目の形として認める。

- **`Session:` トレーラーを求めない。** セッションが作ったものではない
- 対象はセキュリティ更新のみ（`security-requirements.md` 9節）
- B が扱う。CI が緑であることと、変更が依存関係のバージョンに閉じていることを確認する
- **メジャーバージョンの更新は自動で通さない。** 破壊的変更を含むため A に上げる

### `fix/` と `task/` の境界

**設計判断を含むかどうか**で分ける。

| 判定 | 例 |
|---|---|
| `fix/` | 相対パスを絶対パスに直す。二重発火を防ぐ。条件の書き忘れを足す |
| `task/`（A がタスクを起票する） | 認証方式を変える。テーブルを足す。新しい手続きを増やす |

判断に迷ったら A に上げる。**迷った時点で設計判断の可能性が高い。**

### 不具合修正 PR の受け入れ基準

`fix/` にはタスクファイルが無い。**採点表が無いままレビューさせない。**
PR 本文に次の4点を書く。これが R の採点表になる。

1. **観測した事象** — 再現手順を含む
2. **原因**
3. **再発を防ぐ手段** — 回帰テスト。書けない場合は**書けない理由**
4. **影響範囲** — 他に同じ形の箇所が無いか確認した結果

加えて既存のテストが緑であること。

**手続きを重くしない。** タスクファイルを作らせない、証跡ディレクトリを要求しない。
不具合修正が面倒になると、機能開発にまとめて紛れ込ませる方向に働く。
それは修正そのものより悪い。

### コミットメッセージ

- 日本語1行。必要なら本文で理由を書く
  ```
  投稿一覧にカーソルページングを追加

  1回の取得を20件に固定し、created_at と id の複合カーソルで
  同一秒の投稿が重複・欠落しないようにした。
  ```
- `main` に直接コミットしない

### ブランチを放置しない

**出した PR はその日のうちに取り込む。**溜めると2つの壊れ方をする。

| 壊れ方 | 実例 |
|---|---|
| **玉突きの競合** | A が docs PR を4本溜めた。1本マージするたび squash が祖先を切り、残り3本が競合し直した（#62 のマージで #63・#64・#65 が同時に DIRTY）。3本を1本にまとめ直して解消（#72） |
| **マージすると前進が巻き戻る** | PR #66 が長く開いたまま `main` が先へ進み、**マージすると解決済みの論点が未解決へ、完了タスクが未完了へ戻る差分**になっていた。新しい内容だけを現行 `main` から切ったブランチへ移して解消（#75） |

2つ目の方が危ない。**競合は git が止めてくれるが、巻き戻りは止めてくれない。**
差分としては正当なので、そのままマージできてしまう。

- 出したら取り込むまでを1つの作業として扱う。「後でまとめて」にしない
- どうしても開いたままになったら、**マージ前に `main` との差分の向きを見る。**
  解決済みが未解決に戻っていないか、完了が未完了に戻っていないか
- 巻き戻りが混ざっていたら、**新しい内容だけを現行 `main` から切り直したブランチへ移す。**
  古いブランチを直そうとしない

### マージ戦略

**squash merge を使う。** `main` は「1タスク = 1コミット」に保つ。

rebase / merge commit を採らない理由は、レビュー往復の途中経過
（「R-17対応」「テスト追加」等）が `main` に載るため。このリポジトリは
転職活動で読まれる想定であり、`main` の履歴が
「001: 歩くスケルトン」「002: デザイントークン」…と並ぶ形の可読性を優先する。

### squash 時の必須手順

squash merge は、PR が複数コミットのとき各メッセージを本文に連結するため、
**`Session:` トレーラーが解析できなくなる**（実例: `a2f6eb2` で消失）。
マージする者が squash コミットのメッセージに明示的に書き込む。

```bash
gh pr merge <番号> --squash --delete-branch --subject "003: 認証基盤 (#5)" --body "$(cat <<'EOF'
<変更の要約>

Session: B
EOF
)"
```

**`--delete-branch` を付ける。**リモートブランチを消すのはマージした者の担当である
（`harness.md` 3節）。切った側はローカルしか消さない。

マージ後、`main` 上でトレーラーが残っていることを確認する。

```bash
git log -1 --format='%(trailers:key=Session,valueonly)'
```

## 8. 動作証跡

タスク完了時に `artifacts/NNN/` へ残す。

| 内容 | 常に | UI変更時 |
|---|---|---|
| テスト実行結果（テキスト） | ○ | ○ |
| 手動確認の手順と結果（テキスト） | ○ | ○ |
| スクリーンショット | − | **− タスク単位では撮らない**（下記） |

### タスクごとにスクリーンショットを撮らない

当初は UI 変更時に必須としていた。**撤回する。**

実績がそれを支えていない。UI を含む4タスクのうち、**実際に撮れたのは 002 だけ**である。
001 は保存手段が無く、003 はブラウザペインが使えず、008 は人間が
「面倒なので撮らない」と判断した。**4回中3回、例外として処理されている。**

**毎回例外で通る要件は統制ではない。**残るのは、その都度「なぜ撮れなかったか」を
書く作業だけになる。要件の側を実態に合わせる。

UI が正しいことの担保は**人間が実機で操作した記録**（テキスト）が受け持つ。

#### スクリーンショットが本当に要る場所は2つある

無くしたのではなく、**必要な場所に集約した。**

| タスク | 何のために |
|---|---|
| **015** ランディングページ | **製品の素材。**LP に載せる画面画像。証跡ではなく成果物 |
| **016** 公開 | **本番URLの証跡。**完成した画面を、実データが入った状態で撮る |

途中のタスクで撮るより、この2箇所の方が**見せる相手にとって有効な画像**になる。
リポジトリを読む人が見たいのは、作りかけの画面ではなく完成した画面である。

#### 何を失うか（等価な置き換えではない）

当初ここに「視覚回帰テストが無い以上、画像があっても誰も比較しない。実態は変わらない」
と書いた。**誤りだった。**スクリーンショットの用途を2つ混ぜていた（R の指摘）。

| 用途 | 実態 |
|---|---|
| **回帰比較**（前回の画像と突き合わせる） | **行われていない。**道具も無い。ここは失っても変わらない |
| **初見のレビュー**（結果を一度見る） | **行われていた。失う。** |
| **後から再検証する** | **行われた。失う**（下記） |

2つ目には実例がある。**002 で R がロゴ画像の背景が地の色と一致していないことを、
画像のピクセルを実測して見つけた**（R-7）。B の実装メモは
「背景色がトークンの `bg` と同一であることを利用し、透過せず矩形のまま採用した」と
書いており、**テキストの証跡だけなら通っていた。**実測すると一致していなかった。

**この種の不具合は「人間が実機で操作した記録」からは出ない。**
現に 002 では人間は触っておらず、R が画像から見つけている。

3つ目の用途にも実例が出た。R は 002 で PC 幅のレイアウトについても指摘していたが、
**その指摘はどこにも記録されずに消えていた。**30タスク後、R が
`artifacts/002/desktop-home.png` を実測して再現している
（カードが 1280px 中 **1248px = 97.5%** に伸びる。最大幅の制約が無い。L59）。

**テキストの証跡は、書いた人が気づいたことしか残さない。
画像は気づかなかったものも残す。**記録が失われても、画像からは掘り返せた。

#### 検出の主体が R から人間へ移る

「人間が受け持つ」と書くと等価な置き換えに読めるが、**等価ではない。**

002 では **R が**見つけた。今後は、**人間が使っていて気づかない限り
UI の不具合は残る。**画面を独立した目で一度見る工程が無くなる。

個人プロダクトの判断としては妥当である。人間が撮らないと決めた以上、
要件を残す方が有害になる。**ただし、代償を知らずに読まれない形にしておく。**

### R のレビュー結果を `artifacts/NNN/review.md` に保存する

**B が保存する。**R は書き込み権限を持たない。

これまで、R の指摘のうち**B が対応したものだけ**がタスクファイルに残っていた
（「レビュー往復1回目（R の指摘への対応）」など）。
**R が「記録のみ・差し戻さない」とした指摘は、どこにも残らずに消えていた。**
R のメッセージの中だけに存在し、B が `/clear` した時点で失われる。

**順序が逆である。対応しない指摘こそ、後から「なぜ差し戻さなかったか」を
読み返す価値がある。**対応したものはコードに現れるが、しないものは何にも現れない。
L59 は実際にこれで30タスク失われていた。

- **R のレビュー結果を一字一句そのまま保存する。**要約しない
- 往復ごとに追記する。**前の回の指摘を消さない**
- `docs/security-report.md` と同じ理屈で、B が指摘を薄めていないかを
  後から検証できる状態になる（`security-requirements.md` 10節）

#### 論点表に上げるのは、タスクを跨いで効くものだけ

`state.md` の論点テーブルは**復帰時に最初に読むファイル**である。
レビュー指摘を全部載せると、そこが読めなくなる。

| 指摘の性質 | 行き先 |
|---|---|
| そのタスクで閉じる | `artifacts/NNN/review.md` のみ |
| **他のタスク・将来の判断に効く** | 加えて `state.md` の論点として起票する |

**判断するのは R である。**R が起票を求めたものを B が論点に上げる。
R が何も言わなければ `review.md` に残るだけになるが、**消えはしない。**

### 人間の操作が要る証跡が取れないとき

実機ログインのように**人間しか実行できない**証跡は、その人間が居ないと取れない。
このとき取る手順を決めておく。

1. **条件を満たしたことにしない。** チェックを付けない
2. **未達として `state.md` の論点に起票する。** 何が未確認で、いつ・誰が回収するかを書く
3. **タスクのマージは止めない。** レビューは証跡と独立に進められる
4. **マイルストーンの受け入れでまとめて回収する。**
   人間が実機に触るのはそこなので、複数タスク分を1回で消化できる

前例: 003・004 は Google OAuth クライアント未取得のため実機確認を残したまま
マージし、L14 として追跡して 2026-08-29 にまとめて回収した。

**「証跡が取れないから条件を緩める」ではない。**条件はそのまま残し、
未達であることを見える場所に置く。回収されないまま公開に至る経路を作らない。

## 9. 設計ドキュメントの所有権

**設計ドキュメントを書き換えられるのは A だけ。**

| ファイル | 書き換えられる役 |
|---|---|
| `docs/requirements.md` / `architecture.md` / `decisions.md` / `security-requirements.md` / `conventions.md` | **A のみ** |
| `docs/harness.md` / `CLAUDE.md` / `.claude/agents/*` | **A のみ** |
| `docs/tasks/NNN-*.md` の **目的 / 実装内容 / 確認観点 / 完了条件 / 停止条件** | **A のみ** |
| `docs/tasks/NNN-*.md` の **進捗チェックボックス / 実装メモ節** | B |
| `docs/state.md` / `docs/worklog.md` | A / R / B すべて |
| `artifacts/NNN/` | B |

### 名前を変えたとき、どこまで書き換えるか

**過去の記録と、現在の定義を分ける。**

| 種類 | 扱い |
|---|---|
| **`decisions.md`（ADR）** | **触らない。** |
| 恒久ドキュメント（`architecture.md` / `requirements.md` 等） | **書き換える。**ここが現行の定義 |
| **完了タスクの定義表** | **打ち消し線で現行を示し、出典を指す。**消さない |
| 付随的な言及（説明文の中の一語など） | 素直に直す |

**ADR を書き換えると、決定の根拠が消える。**

ADR-009（`events` を1テーブルに統合する）は「統計カードには**会った回数**が必要で、
この数字の出所が必要」を根拠にしている。018 で「会った日数」に改名したからといって
ここを書き換えると、**当時なぜ1テーブルに統合したのかが読めなくなる。**
決定は**その時点の理解の記録**であり、後から辻褄を合わせるものではない（R の指摘）。

**完了タスクの定義表は消さない。**そこは「何を作れと言われたか」の記録でもある。
ただし**フィールド名の定義を読みに来る人が向かう場所**でもあるため、
打ち消し線で現行を示し、**現行の定義がどこにあるか**を指す。
`docs/security-report.md` の訂正を元の行に書くのと同じ理由である。

### 人間が指定したものと違うことをしたときだけ、「戻せる」と書く

**理由を厚く書くのは正しい。**次に読んだ人に直しにかからせないためであり、
決定済みに見えて構わない。`meetupCount` → `meetupDays` や union の改名がそれである。

**ただし、厚さが判断の重みとして読まれる。**人間の指定と違うことをしたときにそれが働くと、
**理由の量が「もう決まったこと」の圧になる。**

線引きは1つで足りる（R の整理）。

| 判断の相手 | 書き方 |
|---|---|
| **自分たちの中で閉じた判断** | 理由を厚く書く。**決定済みに見えてよい** |
| **人間が指定したものと違うことをした** | 理由を書いたうえで、**戻せると明示する** |

実例。020 のホームのパネルを、人間のモックアップの7枚に対して**8枚にした。**
理由を3つ書いたうえで「**7枚に戻す選択肢**」を併記した。
書いていなければ、**理由の厚みがそのまま決定の重みに見えていた。**

**理由をいくら積んでも、「人間が違うと言えば戻る」が上位にある。**

**いつ書くべきかを毎回考えない。判断の相手が誰かで決まる。**

### 判断は、それが上書きする記述と同じ場所に書く

**既にその話題の節があるなら、そこを書き換える。別の場所に新しい節を立てない。**

新しい判断を足したのに古い記述を消さず、**同じドキュメントの中で食い違う**形を
5回起こしている（L28・L36・017 の証跡要件・013 のタップ挙動・ナビゲーション）。
**5回とも見つけたのは R であり、A は自分では気づいていない。**

R の分析（そのまま採る）。**これは注意力ではなく構造の問題である。**

- **A は前へ書く。**新しい判断を、その判断として最も自然な場所に書く
- **R は後ろから読む。**実装と突き合わせるために、既存の記述を毎回読み直す

**古い記述は、新しい判断を書いている人の視野に入らない。**
書いている場所と、矛盾が生じる場所が違うからである。
ナビゲーションの件では、A は 6節末尾を見ており、矛盾は 7節にあった。**94行離れていた。**

だから「次は気をつける」では減らない。**5回とも気をつけていた。**

上書きする記述と同じ場所に書けば、**編集する行がそこにあるので旧記述が目に入る。**
視野の外に矛盾が生まれる経路自体が消える。

**R のレビュー観点にもなる。**「既にその話題の節があるのに、別の場所に新しい節を
立てた」PR は、それだけで疑わしい。

#### これで消えるのは5件中2件である

**過大に書かない。**5件を数え直すと、この規則が効くのは形が合うものだけである。

| # | 形 | 効くか |
|---|---|---|
| ナビゲーション | 同じ文書の別の節に書いた | **効く** |
| L36（E2E の方針） | 007 の決定が 008 の完了条件を上書きしていた | **効く**（同時に 008 を直すことになる） |
| L28（認可テストの件数） | 件数を引用側にも書いていた | 効かない。**別の規則**（件数・項目数を引用側に書かない）で対処済み |
| 017 の証跡要件 | 恒久側を直した時点で 017 が未マージだった | 効かない。**タイミングの問題** |
| 013 のタップ挙動 | B が実装で読み替え、A が仕様を追随させた | 効かない。**そもそも B からの申告で発覚した** |

同じ節の中で**本文と根拠が食い違う**形も残る（010 の「射影する年は最大2つ」。
本文は正しく、すぐ下の一文が誤っていた。同じ PR の中の矛盾である）。

**「これで解決」ではない。「視野の外に生まれる分は消える」である。**

タスクファイルは「A が定めた受け入れ基準」と「B が残す進捗記録」が同居している。
前者は B が触らない。後者は B が毎回更新する。**受け入れ基準を実装者が
書き換えられる状態にしない**ことが目的であり、進捗の記録を止める意図はない。

### `state.md` は3役が書ける唯一のファイル。競合しうる

worktree を分けた結果、A / R / B はそれぞれ別のブランチで同じ `state.md` を
編集できる。**マージ時に競合が起きうる。**

| 状況 | 結果 |
|---|---|
| B が「現在のフェーズ」、A が「未解決の論点」を編集 | 自動マージされる |
| **A と B が両方とも論点テーブルの末尾に行を足す** | **競合する** |
| 同じ論点を両方が解決済みに書き換える | 競合する |

論点の追加は毎回テーブル末尾に足すため、そこが最も起きやすい。

#### 回避しない。競合したら解消する

**各役は必要なときに `state.md` を書く。** 他の役の状態を見て書くのを控えない。

`state.md` の論点テーブルで競合したときの正解は「**両方残す**」。
**リストなので和集合が正しい。**どちらかを選ぶ判断はしない。
番号が重複したら、後から入った方を採番し直す。

これはコードの競合とは質が違う。**git が止めるだけで、内容の判断は不要。**

#### `worklog.md` は union マージにしてある

`.gitattributes` に `docs/worklog.md merge=union` を置いた。
**追記が衝突しなくなる。**両方の追記が残るので、解消の作業自体が発生しない。

3つの役が同じファイルの末尾に追記するため、**内容が一度も衝突していないのに
git が止まっていた。**末尾が同じというだけである。

- **`docs/state.md` には適用しない。**既存行を書き換えるファイルであり、
  union だと最終更新行が2行になり、マイルストーン表の行が新旧2つ残る
  （実際に自動解決を書いて踏んだ）。**論点テーブルの競合は今までどおり手で解く**
- union が安全なのは「**既存行を編集しない**」ファイルだけである。
  `worklog.md` は追記専用と決めてあるので条件を満たす
- 同じ事実を2つの役が別々に書いた場合、union は**両方残す。**
  これは上の表の「同じ事実の別表現」に当たるので、気づいたら1つにする

#### 「両方残す」は他のファイルに広げない

**この規則は `state.md` の論点テーブルを対象にしている。**
他の共有ファイルにそのまま当てはめない（R の指摘）。判定はこう分ける。

| 競合した2つが | 正解 |
|---|---|
| **別々の事実** | 両方残す。`worklog.md` の別々のエントリ、論点テーブルの別々の行 |
| **同じ事実の別表現** | **1つにする。**どこが正典かを決め、他方を落とす |

`worklog.md` は追記専用なので前者になりやすいが、
**「追記専用だから両方残す」ではない。**同じ事実を2箇所に書いたなら重複であり、
和集合ではない。判断が要る。

### `docs/security-report.md` の訂正は元の行に書く

監査の指摘が後から誤りと分かった場合、**元の指摘の行に打ち消し線と訂正を書く。**
独立したエントリを新しく追加しない。

理由は読み手にある。**表を上から読む人が、訂正を見落とさない形にする。**
別の場所に訂正を置くと、元の行だけを読んだ人が
**実在しない脆弱性を追う**か、**実在すると誤解したまま**になる。

- 訂正するのは**転記側**（`docs/security-report.md`）だけである
- **`artifacts/NNN/security-audit-raw.md` は書き換えない。**
  生の出力を一字一句のまま保つことが、転記が薄められていないかを
  R が突き合わせられる根拠になっている（`security-requirements.md` 10節）

#### なぜ「B の PR が開いている間は書かない」としないのか

一度その回避策を書いたが、削除した。理由は2つある。

1. **`harness.md` の worktree 分離で消したはずの構造が戻る。**
   「B の状態を見て A が書くのを控える」という形そのものが、分離の目的だった
   「A はいつでも書ける」を打ち消す
2. **A → メッセージ → B が転記、という経路が帰属を壊す。**
   B が A の文言を転記すれば `Session: B` になる。
   書き手の記録（9節）が意味を失い、003 で訂正させた形が運用として常態化する

競合の実害（git が止まる、和集合を取る）より、回避の実害
（B の状態を気にする認知負荷、帰属の破壊）の方が重い。

### なぜ例外を作らないか

監査プロトコルを定めているのは `security-requirements.md` である。
**監査される側（B）がそれを書き換えられる状態は、Maker-Checker の穴になる。**
今回は強化方向の変更だったが、「監査役の出力は要約でよい」という弱化方向の変更も
同じ経路を通る。方向を問わず経路ごと塞ぐ。

「明白なバグだから」という例外も作らない。明白さの判定を実装者に委ねた時点で、
判定基準が実装者の都合に寄る。

### B が設計ドキュメントの誤りを見つけたとき

1. `docs/state.md` の「未解決の論点」に起票する
2. A にメッセージで知らせる（中身ではなくポインタを渡す）
3. **A の返答を待たずに実装を進める。** ドキュメントの誤りは実装を止めない。
   正しいと判断した実装を進め、ドキュメントは A が並行して直す
4. 食い違ったまま実装が進んだ場合は、R が受け入れ判定で差し戻す

この手順により、A 待ちで B が止まることは無い。

### 書き手の記録（違反が痕跡を残すようにする）

A / R / B は**同じ git identity を共有している**。したがって差分からもコミットからも
書き手を判別できない。所有権のルールがあっても、違反が記録に残らなければ意味が薄い。

**`main` に載る全てのコミットメッセージの末尾に、書き手の役を1行入れる。**

```
Session: B
```

- `A` / `R` / `B` のいずれか
- **`Co-Authored-By` と同じブロックに、空行を挟まずに置く。** git はメッセージの
  最後の段落だけをトレーラーとして解析するため、間に空行があると
  `Session:` 行は本文として扱われ、`%(trailers)` で取り出せなくなる

```
<本文>

Session: B
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
```
- **1つの PR に含める役は1つだけ。** A の設計変更と B の実装を同じ PR に混ぜない
- R は受け入れ判定時、設計ドキュメントの差分を含む PR の `Session:` 行を確認する。
  `B` になっていれば所有権違反として差し戻す

#### 対象は `main` のコミットに限る

**作業ブランチの途中のコミットには求めない。** squash merge により
`main` には残らないためである（実例: 008 の作業中に作られた `f7bcea2`
「Merge branch 'main' into task/008-timeline-ui」は `main` に載っていない）。

git が自動生成するメッセージ（`git merge` のマージコミット等）と、
人以外が作るコミット（Dependabot）にも求めない。**書けないものを要求しない。**

この規約が守られているかは、次の1行で機械的に確かめられる。
出力が空なら、トレーラーの無いコミットは無い。

```bash
git log fad1bb1..origin/main --format='%h %(trailers:key=Session,valueonly,separator=%x2C)' | awk 'NF<2'
```

- **`separator=` を省かない。** 省くとトレーラー出力の末尾に改行が入り、
  コミットごとに空行が1つ出る。`awk 'NF<2'` はその空行を拾うため、
  **全件が違反しているかのように見える**（この規約を書いた際に実際に踏んだ）
- **`fad1bb1..` から数える。** それ以前の7件（`9147296`〜`a2f6eb2`）は
  この規約自体が無かった時期のコミットで、トレーラーを持たない。
  `a2f6eb2` は squash でトレーラーが消えた実例でもある（L19）。
  **遡って書き換えない。**規約は書かれた時点から先に適用する

#### この仕組みで検出できること・できないこと

| | |
|---|---|
| 検出できる | 事故・失念（役の付け忘れ、意図しない混入） |
| **検出できない** | **意図的な詐称。** B が自分の設計変更に `Session: A` と書いても見抜けない |

`Session:` 行は**自己申告**である。統制の実体は
「R がマージ前のブランチ上で差分を確認すること」の方にあり、
`Session:` 行はそれを事後に辿れるようにする補助にすぎない。
**この記録があることをもって「所有権が保証されている」と読んではならない。**

### 役ごとに作業ディレクトリを分ける

**A / R / B はそれぞれ別の作業ディレクトリで動く。** 設定は `harness.md` 3節を参照。

| ディレクトリ | 役 |
|---|---|
| `futary/` | **B**（実装）。`main` ブランチはここが持つ |
| `futary-A/` | **A**（設計） |
| `futary-R/` | **R**（レビュー） |

- **自分のディレクトリの外でファイルを編集しない。** 他の役の作業ツリーに書き込むと、
  分離した意味が消える
- A はいつでも設計ドキュメントを変更できる。B の区切りを待つ必要はない
- R はブランチを自由にチェックアウトできる。B の作業ツリーは動かない

分離前は単一の作業ツリーを共有しており、A の編集が B のコミットに混入し、
B が `git reset --hard` を打てば A の未コミット分が消える状態だった（旧 L18）。

#### 急ぎの設計判断が必要になったとき（「1 PR = 1 役」の例外を作らない）

R からのエスカレーションなどで、B の作業を止めないために A の判断が急ぎ必要になることがある。
このとき**同じ PR に A と B を混ぜる必要は無い**。判断とドキュメントを分けて考える。

| 運ぶもの | 経路 | B が待つか |
|---|---|---|
| **判断そのもの** | A から B / R へのメッセージ | **待たない。** 受け取った時点で実装できる |
| **ドキュメントへの反映** | A 単独の PR | 待たない。並行して進む |

B が必要としているのは判断であって、ドキュメントのマージではない。
ドキュメントはコンパイルされないので、B の実装を1秒も止めない。

したがって **「1 PR = 1 役」に例外は無い。**
A は自分の PR を出し、B は自分の PR を出す。

**ただし新しいセッションは別。** `/clear` した B はメッセージを引き継がない。
タスクファイル・`state.md` のみを読む。
**新セッションが着手する前に反映が必要な変更は、着手前に main へマージする。**

### 引用先と引用元の食い違いをどう判定するか

タスクファイルは恒久ドキュメントを出典に指すことがある
（例: 005 の「テストで証明すること（`security-requirements.md` 3節）」）。
両者の文言が違うとき、**逐語一致を求めない。**

判定基準は「**引用側が出典側を満たしているか**」だけ。

| 向き | 例 | 扱い |
|---|---|---|
| 引用側が**広い** | 恒久側「投稿IDを指定しても取得できない」→ タスク側「レコードIDを指定しても取得・更新・削除できない」 | **妥当。** その時点の実装に合わせた一般化であり、恒久側の要求を満たしたうえで超えている |
| 引用側が**狭い** | 恒久側が5項目、タスク側が4項目 | **危険。** タスク側だけを見て実装すると恒久基準を満たせない。直す |

逐語一致を規則にすると、上段の妥当な特殊化まで潰れる。

#### 件数・項目数を引用側に書かない

「005 の認可テスト**4件**が緑」のように、引用側に数を書くと**そこがズレの起点になる**。
恒久側が5件に増えても、引用側の数は誰も直さない。

**数は出典側にだけ置く。** 引用側は「`security-requirements.md` 3節のテストが緑」と書く。
006 で実際にこれが起きた（恒久側は PR #17 で5件になっていたが、
タスクファイルは4件のまま。実装は5件とも満たしていたので実害は出なかった）。

他のタスクファイルが「005 の認可テストも緑」と件数抜きで書いていたのは正しい形である。

**恒久ドキュメント側が狭い場合はより深刻。** タスクファイルは1タスク限りだが、
恒久ドキュメントは以降の全タスクで維持される基準である。
恒久側に無い項目は、そのタスクが終わった時点で失われる。
**タスクで基準を1つ足したら、恒久側にも足したかを必ず確認する。**

## 10. 完了時の必須動作

**ファイル変更を伴う作業が終わったら、必ず両方を更新する。**

1. `docs/state.md` を現在地に合わせて書き換える
2. `docs/worklog.md` に追記する（既存行は編集・削除しない）

これを怠るとコンテキスト圧縮後に再開できなくなる。
