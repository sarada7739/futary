Webアプリ開発を Claude Code の複数セッションで回すための構成。
Maker-Checker 分離、圧縮耐性、コスト最適化を満たす。

このファイルはリポジトリルート直下の `docs/harness.md` として配置し、

## 1. 体制

| 役割 | モデル | 担当 | 入力 |
|---|---|---|---|
| **A** 設計・壁打ち | Opus | 要件整理、設計、タスク一覧作成、仕様変更判断 | 人間との対話、`docs/` |
| **R** レビュー・指示 | Opus | 実装結果のレビュー、修正指示、受け入れ判定 | Bの差分、テスト結果、証跡 |
| **B** 実装 | Sonnet | コード、テスト、動作証跡の作成 | `docs/tasks/NNN-*.md`、Rからの指示 |
| **監査** | Opus（Bの読み取り専用サブエージェント） | セキュリティ監査 | コード、静的ツール出力 |

### 不変の原則
- **A は実装結果（差分・コード）を読まない**。読むのは `state.md` / `worklog.md` のみ
- **R は設計変更をしない**。仕様の問題を見つけたら A にエスカレーション
- **R は書き込み権限を持たない**。動かせる＝いじれる になった時点で Maker-Checker が崩れる
- **B は自分の実装を自己採点しない**

**線を越える方法を提案しない。**やりたいことが正しくても、
**やり方は何通りかある。**手番の違う役に渡す方法が必ずどれかに含まれている。

R が「記録と実装を別便にしたくない」ために
**「A が `ci.yml` を触ればいい」と提案した**（021）。目的は正しく、
**手番だけが違った。**同じことは **B が両方を出す**か
**B が入れてから A がマージする**でも実現できる。
**R 自身が3案を並べたうえで、線を越える1案を推していた。**

**「数行だから」は理由にならない。**行数は手番を変えない。

### 線は「誰が決めるか」で引く。「誰が何を見るか」では引かない

**2026-09-05、人間の指示。**「役の線は基本で、多少は逸脱してもいい。
よりよいものをつくっていこう」。

**上の4つを消すのではない。どこが固いかを言い直す。**

| | |
|---|---|
| **見る・調べる・気づく・指摘する** | **自由。むしろ推奨する。**役に閉じない |
| **決める・判定する・書き込む** | **役に固定する。ここは動かさない** |

**実際に効いていたのは、全部「見る」側だった。**

- **B が A の設計ドキュメントの誤りを見つけた**（027 の FK / 031 の孤児回収 /
  033 のジェスチャライブラリ / 034 のリトライの数字）。**どれも B が見なければ残っていた**
- **R が A の仕様の穴を見つけた**（032 の免除の粒度。**削除の網を直すタスクで
  網の穴を作るところだった**）
- **A が実装を読んで事実を取った**（`me.delete` の削除順・`post_images` の有無）

**「見なかったから気づかなかった」で失われたものの方が、
「見たから線を越えた」で失われたものより多い。**

**固いままにするもの。**

- **B は自分の実装を「受け入れ」と判定しない**（Maker-Checker の核。**ここが緩むと全部が緩む**）
- **R は実装しない。書き込まない**
- **設計ドキュメントを最終的に書き換えるのは A**（B が誤りを直して知らせるのはよい。
  **直したことを A が知らないまま進むのが駄目**）
- **`main` に直接コミットしない**
- **自分の作業ディレクトリの外でファイルを編集しない**（これは判断ではなく
  git worktree の機械的な安全）

**「多少の逸脱」は、気づいたことを黙っていないことである。
判定を勝手にやってよい、ではない。**

## 2. 情報伝達

| 経路 | 手段 |
|---|---|
| A → B（タスク） | ファイル（`docs/tasks/`） |
| B ↔ R（実装・レビュー往復） | クロスセッションメッセージング |
| B/R → A（エスカレーション） | `docs/state.md` ＋ メッセージ |

メッセージは短文のみ。**中身ではなくポインタを渡す**
（例: 「`docs/tasks/003-login-api.md` を実装して」
　　　「003完了。`artifacts/003/` を確認して」）。

### クロスセッションメッセージングの前提
- Claude Code v2.1.234 以降（ネイティブWindows）／v2.1.224 以降（macOS・Linux・WSL2）
- `/list-agents`（`/peers`）で疎通確認、`/status` の Peer address 行を確認
- `DO_NOT_TRACK` / `DISABLE_TELEMETRY` / `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` /
  `DISABLE_GROWTHBOOK` が設定されていると機能フラグ評価が止まり無効になる
- メッセージでは権限承認・設定変更はできない（受信側で通常のプロンプトが出る）
- 同一送信者の連投はレート制限、同一内容の短時間重複は破棄、未読は50件上限
  → 無限往復は自動で止まる
- セッション名は `/rename` または `--name` で設定する（A / R / B と명示すると混同しない）

#### この harness で出る形は「要約を読んで、原本を開かない」

**2026-09-04、R が 032 の着手前の材料として3件を出した。うち1件が外れていた。**

R は私のメッセージだけを読み、**タスクファイルを開かなかった。**
メッセージに「`couple_id` 走査の方はそのまま残す」としか書いていなかったので、
**「新しい方には無いのだろう」と推測した。**実際は起票時から書いてあった。

**3役は要約を渡し合って動いている。**

- A は**タスク定義**を渡す。B と R は**報告**を返す
- **渡されるのは常に要約である。**原本ではない
- **要約に無いことは、原本にも無いとは限らない**

**効くのは「無い」と言うときである**（R の絞り込み。2026-09-04）。

| 根拠 | 外れたとき |
|---|---|
| 要約に**書いてある**ことを根拠にする | 弱いが、**要約が誤っていたと分かる** |
| 要約に**書いていない**ことを根拠に「無い」と言う | **何にも当たっていない。**要約は誤っていない |

**後者は、要約のどこにも書かれていない。書いた側が作っている。**

**「無いのだろう」は推測である。**外れたときに、
**書いた人には「読まれていない」ではなく「間違っていた」と伝わる。**

**「実行できる主張は、実行してから書く」の隣に、
「無いと言うときは、無いことを見てから書く」が並ぶ。**
**あるものは要約からでも辿れる。無いものは原本にしか無い。**

**指摘する前に、指摘する対象を開く。**メッセージではなく、そのファイルを。
**これは3役ともである。**役に免除は無い。

### 担当するパスだけをコミットする

**A は `git add docs/` のあと `git commit`。`-a` を付けない。**
作業ツリーに何が入っていても、**担当外のファイルはコミットに入らない。**

**`git add -A` と `git commit -a` は、どちらも担当外まで拾う。**
`-a` を名指ししておかないと、**次に `git add` を使わない人が同じ穴に落ちる。**
しかもその人は**規則を読んで守ったつもりでいる**（R の指摘）。

**「拾い方」ではなく「コミットに入るパス」で書く。**手段を1つ禁じる形にすると、
**禁じていない手段が残る。**

021 で、A の PR に **B の実装2ファイルが混入した**（R が発見。
B が書いたものと一字一句同じだった）。**`git add -A` で拾っている。**

**混入した2つはどちらも新規ファイルではなく、追跡済みファイルへの変更だった。**
`git add -A` でも `git commit -a` でも同じように入る形である。

##### 原因: シェルの現在地が黙って戻る

**一度「原因不明」と書いたが、判明した。**

**A のシェルの現在地が、`C:/Users/coco7/futary`（B の作業ツリー）に戻っていた。**
そこは**環境の Primary working directory** であり、
**`cd` してもセッションの途中で戻される。**

つまり `git add -A` は **B の作業ツリーで実行されていた。**
A が拾ったのではなく、**A が B の部屋で作業していた。**

**「2つの作業ツリーが入れ替わった」は誤読だった。**
`git status` が B のツリーの状態を返していたのを、自分のツリーだと読んでいた。
`git worktree list` の「B のツリーが A のブランチを開いている」も、
**A がそこでブランチを切ったから**である。**B は何もしていない。**

**役ごとの `cd` を毎回明示する。**

- **1コマンドごとに `cd <自分のツリー> && ...` を書く。**
  前のコマンドで `cd` したから続いている、を前提にしない
- **`pwd` は `git status` より先に読む。**
  ブランチ名は正しく見えても、**それが別のツリーのブランチ名**でありうる
- **役ではなく、セッションの起動位置で決まる**（R の指摘）。
  **Primary working directory が自分のツリーと一致している役だけが踏まない。**
  いまはたまたま B がそれである。**役で覚えない。**
  **自分の Primary working directory を確かめる**——一致していなければ踏む側である

`.gitattributes` の union と同じ形である。
**止まらない仕組みは、間違いも止めない。**

**この規則は原因を知らなくても効いた。**何がどう紛れ込んでも、
**指定していないパスは入らない。**

**実際、原因が判明する前に1回止めている。**上の `cd` が戻っていた状態で
`git add docs/` を実行し、**B の未コミットの2ファイルは staged に入らなかった。**
**原因の特定を待たずに置ける歯止めを先に置く**のは、この形で報われる。

**コミットする前に `git status --porcelain` を読む**のは、これとは別に要る。
**担当パスの中に見覚えのない差分があれば、そこで止まる。**

### 作業ツリーの分離（git worktree）

**役ごとに別の作業ディレクトリを持つ。** 単一の作業ツリーを3セッションで共有すると、
以下が同時に起きる（futary では 003〜004 で実際に発生した）。

| 起きること | 内容 |
|---|---|
| 混入 | A がドキュメントを直すと B の作業ツリーに現れ、B のコミットに混ざる |
| 帰属不能 | 混ざった変更を誰が書いたのか、差分からもコミットからも判別できない |
| 待ち | A は B の区切りまで書けない |
| 消失 | B が `git checkout` や `git reset --hard` を打つと A の未コミット分が消える |

```bash
git worktree add ../futary-A --detach main   # A（設計）
git worktree add ../futary-R --detach main   # R（レビュー）
```

| ディレクトリ | 役 | 用途 |
|---|---|---|
| `futary/` | **B** | 実装。`main` ブランチはここが持つ |
| `futary-A/` | **A** | 設計ドキュメント。自分のブランチを切って PR を出す |
| `futary-R/` | **R** | レビュー。B のブランチを自由にチェックアウトできる |

- **`--detach` にする。** 同じブランチを2つの worktree でチェックアウトすることはできない。
  `main` は B の worktree が持つ
- `.git` は共有される。ブランチもコミットも全 worktree から見える
- `node_modules` は共有されない。A と R は依存関係を必要としない作業に限る。
  必要なら B の worktree のパスを直接読む
- **R がブランチをチェックアウトしても B の作業ツリーは動かない。**
  これが分離の最大の利点で、R は動いていないものをレビューできる

これにより `conventions.md` 9節の「B に未コミットの作業がある間、A は
設計ドキュメントを変更しない」という制約が不要になる。A はいつでも書ける。

#### ブランチの後片付けは、できる方が分担する

**リモートとローカルで担当を分ける。**別の worktree がチェックアウト中のブランチは
削除できないため、片方だけでは完結しない。

| 対象 | 誰が | 手段 |
|---|---|---|
| **リモート** | **マージした者** | `gh pr merge --squash ... --delete-branch` |
| ローカル | 切った worktree の持ち主 | `git branch -D <名前>` |

```bash
# 切った側: マージ後、自分の worktree で
git fetch --prune
git switch --detach origin/main            # ブランチから離れる
git branch -D docs/<名前>                   # ローカルだけ消す
```

##### 切った側はリモートを消さない

**`git push origin --delete` を打たない。**

**未マージの PR のリモートブランチを消すと、PR が閉じる。**
実際に2回起こした。1回目（#87）は気づいて復元・再オープンした。
**2回目（#106）は気づかず、B が `refs/pull/106/head` から復旧した。**

1回目のあと「以後、削除前に `gh pr view <番号> --json state` を見る」と決めた。
**その規則はこの文書に既に書いてあり、それでも2回目が起きた。**

> `-D` は「マージ済みか確認せずに消している」ことを意味する。
> PR がマージ済みであることを自分で確認してから打つ

**書いてあっても守られない。手順を覚える形をやめる。**

- **ローカルの削除は無害である。**間違って消しても PR は閉じない。コミットも残る
- **リモートの削除だけが PR を閉じる。**だからマージした者だけが打つ。
  マージした直後なら、未マージのものを消しようがない

**確認を足すのではなく、打てる場所を分ける。**
005 の認可・`Button` の二重発火・017 の当たり判定と同じ形である。

- **`-d` ではなく `-D` を使う。** squash merge ではブランチ先端が `main` の祖先に
  ならないため、`-d` は「未マージ」と判定して拒否する
- ローカルにだけ残ったものは `git fetch --prune` 後に
  `git branch` で見える。**リモートに残ることはもう無い**（マージした者が消すため）

---

## 4. 圧縮耐性

**原則: セッションの記憶をコンテキストではなくファイルに置く。**
圧縮で失われるのは会話履歴だけなので、再開に必要な状態が全部ファイルにあれば無害になる。

- `CLAUDE.md` 冒頭に復帰プロトコルを記載
  → セッション開始直後・圧縮直後は `state.md` を最優先で読む
- ファイル変更を伴う作業の完了時は必ず `state.md` を更新（CLAUDE.mdでルール化）
- タスクファイルは進捗チェックボックスを持ち、途中から再開できる粒度にする
- **そもそも圧縮させない方が安い**。1タスク完了ごとに `/clear` して次のタスクから始める

---

## 5. タスク分割

### 粒度
機能名ではなく「**B が1セッションで完了できる作業量**」で割る。

- ✕ 「ログイン機能」（スキーマ＋ハッシュ＋セッション＋UI＋テスト = 過大）
- ✕ 「ログアウト機能」（数十行 = 過小、セッション立ち上げの方が高い）
- ○ 「認証基盤とスキーマ」「ログインAPI」「ログインUI」

### 001 は必ず歩くスケルトン
機能の前に足回りを通す。DB接続・ルーティング・テスト1件が緑・CIが緑まで。
これが無いと B がその場で基盤を作り、後で全部やり直しになる。

### タスクファイルのテンプレート

```markdown
# NNN: <タスク名>

## 目的
<何のためのタスクか。1〜2行>

## 変更対象ファイル
- path/to/file.ts
- （新規）path/to/new.ts

## 実装内容
- <具体的に>

## 確認観点
- <レビュアが見るべき点>

## 完了条件
- [ ] 全受け入れ基準を満たす
- [ ] テストが緑
- [ ] artifacts/NNN/ に動作証跡を保存
- [ ] （リスクの高いタスクのみ）security-auditor の指摘で High 以上がゼロ

## 停止条件
- 完了: 上記をすべて満たす
- 中断: レビュー往復が3回を超えた場合、docs/state.md に論点を記載して A へエスカレーション
- R は「動作に影響しない好み」の指摘を完了判定に使わない（Low扱いで記録のみ）

## 進捗
- [ ] <サブステップ1>
- [ ] <サブステップ2>
```

## 6. 動作確認の証跡フロー

R は読み取り専用のままにする。動作確認は **B が証拠を残し、R が読む** 形で行う。

```
B: 実装 → E2Eテスト（Playwright等）を書く → 実行
   → 結果とスクリーンショットを artifacts/NNN/ に保存
   ↓ メッセージ「NNN完了。artifacts/NNN/ を確認して」
R: テスト結果・スクショ・差分を読んでレビュー
```

### スクショの扱い（トークン節約）
- 通常タスク: テスト結果のテキストのみ
- UI変更を含むタスク: スクショも添付
- レイアウト崩れ等の疑いが出たとき: 人間が直接見る

### 自動テストで埋まらない穴
テストは「書いた通りに動くか」しか見ない。以下はテストが緑でもすり抜ける。
- レイアウトの崩れ
- 操作の流れの不自然さ
- そもそも要件を満たしていない（B の理解が誤っていればテストごと誤る）

→ **マイルストーンで人間が実際に触る**。ここは自動化すると精度が落ちる。

## 7. セキュリティ監査

`.claude/agents/security-auditor.md`

```markdown
---
name: security-auditor
description: 実装完了後のセキュリティ監査。コード変更に対して脆弱性を指摘する。
tools: Read, Grep, Glob
model: opus
---

あなたはWebアプリのセキュリティ監査担当です。
コードの修正は行わず、指摘と根拠の提示のみを行います。

## 監査観点（OWASP Top 10 ベース）
- 認証・認可: 権限チェックの欠落、IDOR、セッション管理、トークンの有効期限
- 入力検証: SQLi、XSS、パストラバーサル、コマンドインジェクション
- 機密情報: ハードコードされた鍵/パスワード、ログへの機密出力、.env の取り扱い
- 通信・設定: CORS、CSP、Cookie属性（HttpOnly/Secure/SameSite）、CSRF対策
- 依存関係: 既知の脆弱性を持つライブラリ、不要な依存
- エラー処理: スタックトレースの外部露出、情報漏洩につながるエラーメッセージ

## 出力形式
docs/security-report.md に追記形式で出力。

### [日付] 監査対象: <対象ファイル/機能>
| 重大度 | 箇所 | 内容 | 推奨対応 |
|---|---|---|---|
| Critical/High/Medium/Low | file:line | 何が問題か | どう直すか |

## ルール
- 重大度は「悪用の容易さ × 影響範囲」で判定し、根拠を1行添える
- 指摘ゼロの場合も「監査済み・指摘なし」と記録する
- 推測ではなく、実際に読んだコードの該当行を必ず示す
```

### 起動タイミング（毎回は高コスト）
1. タスク単位の実装完了時
2. 認証・決済・ファイルアップロード・外部API連携を触ったとき
3. マイルストーン単位の全体監査

### 静的ツールと併用
`npm audit` / `pip-audit`（既知CVE）、Semgrep（静的解析）、gitleaks（シークレット混入）
を先に走らせ、**その出力を監査エージェントに読ませる**。
AI は論理的な穴を見つけるのが得意、静的ツールは既知CVEの網羅が確実。両輪にする。

## 8. Skill の方針

**初期は不要。** `CLAUDE.md` は毎ターン読み込まれるため固定コストになるが、
Skill は必要時のみ読まれる。この差を使って後から切り出す。

| 置き場所 | 内容 |
|---|---|
| CLAUDE.md | 復帰プロトコル、ファイル構成、役割分担、常に守る規約 — **短く** |
| Skill | 特定作業のときだけ必要な長い手順書 |

### 切り出し候補（育ってから）
- タスク定義の書式 … A が毎回書式をブレさせ始めたら
- レビュー手順 … R の出力が安定しないと感じたら
- リリース手順 … デプロイを始めたら

判断基準は「**同じ手順を3回以上やって、毎回説明している**」と気づいた時点。
先に作ると使われない Skill を保守する羽目になる。

## 9. 実行フロー

```
A: 要件・設計・タスク一覧(001-020)を一括作成
  ↓
001 歩くスケルトン → B実装 → 証跡 → Rレビュー → 完了
002 認証基盤/スキーマ → B → R → 完了
003 ログインAPI      → B → R → 監査 → 完了
...
  ↓ マイルストーン（認証一式完了）
人間: 実際に触って受け入れ判定
A: state.md を読んで次フェーズのタスクを追加
```

**A を呼ぶのは3つの場合だけ:**
1. R からのエスカレーション（仕様・設計そのものの疑義）
2. マイルストーンの区切り
3. 人間が仕様変更を持ち込むとき

A に差分を読ませないことで A の肥大を防ぐ。渡すのは `state.md` / `worklog.md` の該当部分。

## 10. 人間の役割

伝令役ではない。ファイル＋メッセージングで受け渡しは自動化される。残るのは3つ。

1. **権限承認** — メッセージでは承認できない仕様。B で都度プロンプトが出る
2. **マイルストーンの受け入れ判定** — 実際に触る。事業判断なので AI に渡さない
3. **仕様変更の持ち込み**

## 11. コスト設計

- 実装は Sonnet、設計・レビュー・監査のみ Opus
- `CLAUDE_CODE_SUBAGENT_MODEL` でサブエージェントのモデルを一括制御
- 同一プロジェクト内で作業を続けるとプロンプトキャッシュが効く
  （キャッシュヒット時の入力コストは通常の10%、最大90%削減）
- 曖昧な指示（参照ファイルなしの「Fix authentication」など）は高コスト
  → タスクファイルに変更対象ファイル・確認観点・完了条件を必ず書く
- Explore / Plan / general-purpose のビルトインエージェントで代替できないか先に確認
- Agent Teams はプランモードで通常の約7倍のトークン。独立性の高い並列フェーズに限定投入
- CLAUDE.md を1画面に収める（全セッションが毎ターン払う固定費）

## 12. 位置づけと次段階

現状は **ハーネスエンジニアリング + L2（検証付き修正）** 相当。
ループの6要素（自動化・隔離・知識・連携・分業・記憶）のうち、
自動化＝プロンプトの自動投入だけが人間に残っている。

L3（無人実行）に進む前に必ず決めること:
- 停止条件の明文化
- 1ループあたりのトークン上限
- `--permission-mode` / `--allowedTools` の緩和範囲とリスク許容度

ループ化したエージェントは標準セッションの数倍〜数十倍のトークンを消費する。
また、生成役と検証役を分けない自己採点ループは構造的に破綻するため、
Maker-Checker 分離（本構成では達成済み）が前提となる。
