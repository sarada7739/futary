# AI駆動開発ハーネス設計（3セッション構成）完全版

Webアプリ開発を Claude Code の複数セッションで回すための構成。
Maker-Checker 分離、圧縮耐性、コスト最適化を満たす。

このファイルはリポジトリルート直下の `docs/harness.md` として配置し、
`CLAUDE.md` から参照する。

---

## 1. 体制

| 役割 | モデル | 担当 | 入力 |
|---|---|---|---|
| **A** 設計・壁打ち | Opus | 要件整理、設計、タスク一覧作成、仕様変更判断 | 人間との対話、`docs/` |
| **R** レビュー・指示 | Opus | 実装結果のレビュー、修正指示、受け入れ判定 | Bの差分、テスト結果、証跡 |
| **B** 実装 | Sonnet | コード、テスト、動作証跡の作成 | `docs/tasks/NNN-*.md`、Rからの指示 |
| **監査** | Opus（Bの読み取り専用サブエージェント） | セキュリティ監査 | コード、静的ツール出力 |

### 不変の原則
- **A は実装結果（差分・コード）を読まない**。読むのは `state.md` / `worklog.md` のみ
- **R は設計変更をしない**。仕様の問題を見つけたら A にエスカレーション
- **R は書き込み権限を持たない**。動かせる＝いじれる になった時点で Maker-Checker が崩れる
- **B は自分の実装を自己採点しない**

## 2. 情報伝達

| 経路 | 手段 |
|---|---|
| A → B（タスク） | ファイル（`docs/tasks/`） |
| B ↔ R（実装・レビュー往復） | クロスセッションメッセージング |
| B/R → A（エスカレーション） | `docs/state.md` ＋ メッセージ |

メッセージは短文のみ。**中身ではなくポインタを渡す**
（例: 「`docs/tasks/003-login-api.md` を実装して」
　　　「003完了。`artifacts/003/` を確認して」）。

### クロスセッションメッセージングの前提
- Claude Code v2.1.234 以降（ネイティブWindows）／v2.1.224 以降（macOS・Linux・WSL2）
- `/list-agents`（`/peers`）で疎通確認、`/status` の Peer address 行を確認
- `DO_NOT_TRACK` / `DISABLE_TELEMETRY` / `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` /
  `DISABLE_GROWTHBOOK` が設定されていると機能フラグ評価が止まり無効になる
- メッセージでは権限承認・設定変更はできない（受信側で通常のプロンプトが出る）
- 同一送信者の連投はレート制限、同一内容の短時間重複は破棄、未読は50件上限
  → 無限往復は自動で止まる
- セッション名は `/rename` または `--name` で設定する（A / R / B と명示すると混同しない）

## 3. ファイル構成

```
CLAUDE.md                       # 全セッション共通の前提＋復帰プロトコル（1画面に収める）
docs/
  harness.md                    # 本ファイル（体制と運用ルール）
  requirements.md               # 要件定義（スコープ外も明記）
  architecture.md               # 技術選定、構成、データモデル、API設計
  conventions.md                # コーディング規約、テスト方針、Git運用
  security-requirements.md      # 機密データ、認証方式、想定脅威
  decisions.md                  # ADR: なぜその設計にしたか
  state.md                      # 現在地（最重要・圧縮からの復帰起点）
  worklog.md                    # 追記専用の作業ログ
  security-report.md            # 監査結果（追記）
  tasks/
    001-walking-skeleton.md
    002-...
artifacts/
  003/                          # タスク単位の動作証跡（テスト出力、スクショ）
.claude/
  agents/security-auditor.md
```

### state.md の項目
- 現在のフェーズ / 完了タスク / 進行中タスク / 次の一手 / 未解決の論点

### worklog.md
- 追記専用（既存行の編集・削除禁止）
- 1エントリ = 日時 / セッション名 / やったこと / 決定事項 / 詰まった点

## 4. 圧縮耐性

**原則: セッションの記憶をコンテキストではなくファイルに置く。**
圧縮で失われるのは会話履歴だけなので、再開に必要な状態が全部ファイルにあれば無害になる。

- `CLAUDE.md` 冒頭に復帰プロトコルを記載
  → セッション開始直後・圧縮直後は `state.md` を最優先で読む
- ファイル変更を伴う作業の完了時は必ず `state.md` を更新（CLAUDE.mdでルール化）
- タスクファイルは進捗チェックボックスを持ち、途中から再開できる粒度にする
- **そもそも圧縮させない方が安い**。1タスク完了ごとに `/clear` して次のタスクから始める

## 5. タスク分割

### 粒度
機能名ではなく「**B が1セッションで完了できる作業量**」で割る。

- ✕ 「ログイン機能」（スキーマ＋ハッシュ＋セッション＋UI＋テスト = 過大）
- ✕ 「ログアウト機能」（数十行 = 過小、セッション立ち上げの方が高い）
- ○ 「認証基盤とスキーマ」「ログインAPI」「ログインUI」

### 001 は必ず歩くスケルトン
機能の前に足回りを通す。DB接続・ルーティング・テスト1件が緑・CIが緑まで。
これが無いと B がその場で基盤を作り、後で全部やり直しになる。

### タスクファイルのテンプレート

```markdown
# NNN: <タスク名>

## 目的
<何のためのタスクか。1〜2行>

## 変更対象ファイル
- path/to/file.ts
- （新規）path/to/new.ts

## 実装内容
- <具体的に>

## 確認観点
- <レビュアが見るべき点>

## 完了条件
- [ ] 全受け入れ基準を満たす
- [ ] テストが緑
- [ ] artifacts/NNN/ に動作証跡を保存
- [ ] （リスクの高いタスクのみ）security-auditor の指摘で High 以上がゼロ

## 停止条件
- 完了: 上記をすべて満たす
- 中断: レビュー往復が3回を超えた場合、docs/state.md に論点を記載して A へエスカレーション
- R は「動作に影響しない好み」の指摘を完了判定に使わない（Low扱いで記録のみ）

## 進捗
- [ ] <サブステップ1>
- [ ] <サブステップ2>
```

## 6. 動作確認の証跡フロー

R は読み取り専用のままにする。動作確認は **B が証拠を残し、R が読む** 形で行う。

```
B: 実装 → E2Eテスト（Playwright等）を書く → 実行
   → 結果とスクリーンショットを artifacts/NNN/ に保存
   ↓ メッセージ「NNN完了。artifacts/NNN/ を確認して」
R: テスト結果・スクショ・差分を読んでレビュー
```

### スクショの扱い（トークン節約）
- 通常タスク: テスト結果のテキストのみ
- UI変更を含むタスク: スクショも添付
- レイアウト崩れ等の疑いが出たとき: 人間が直接見る

### 自動テストで埋まらない穴
テストは「書いた通りに動くか」しか見ない。以下はテストが緑でもすり抜ける。
- レイアウトの崩れ
- 操作の流れの不自然さ
- そもそも要件を満たしていない（B の理解が誤っていればテストごと誤る）

→ **マイルストーンで人間が実際に触る**。ここは自動化すると精度が落ちる。

## 7. セキュリティ監査

`.claude/agents/security-auditor.md`

```markdown
---
name: security-auditor
description: 実装完了後のセキュリティ監査。コード変更に対して脆弱性を指摘する。
tools: Read, Grep, Glob
model: opus
---

あなたはWebアプリのセキュリティ監査担当です。
コードの修正は行わず、指摘と根拠の提示のみを行います。

## 監査観点（OWASP Top 10 ベース）
- 認証・認可: 権限チェックの欠落、IDOR、セッション管理、トークンの有効期限
- 入力検証: SQLi、XSS、パストラバーサル、コマンドインジェクション
- 機密情報: ハードコードされた鍵/パスワード、ログへの機密出力、.env の取り扱い
- 通信・設定: CORS、CSP、Cookie属性（HttpOnly/Secure/SameSite）、CSRF対策
- 依存関係: 既知の脆弱性を持つライブラリ、不要な依存
- エラー処理: スタックトレースの外部露出、情報漏洩につながるエラーメッセージ

## 出力形式
docs/security-report.md に追記形式で出力。

### [日付] 監査対象: <対象ファイル/機能>
| 重大度 | 箇所 | 内容 | 推奨対応 |
|---|---|---|---|
| Critical/High/Medium/Low | file:line | 何が問題か | どう直すか |

## ルール
- 重大度は「悪用の容易さ × 影響範囲」で判定し、根拠を1行添える
- 指摘ゼロの場合も「監査済み・指摘なし」と記録する
- 推測ではなく、実際に読んだコードの該当行を必ず示す
```

### 起動タイミング（毎回は高コスト）
1. タスク単位の実装完了時
2. 認証・決済・ファイルアップロード・外部API連携を触ったとき
3. マイルストーン単位の全体監査

### 静的ツールと併用
`npm audit` / `pip-audit`（既知CVE）、Semgrep（静的解析）、gitleaks（シークレット混入）
を先に走らせ、**その出力を監査エージェントに読ませる**。
AI は論理的な穴を見つけるのが得意、静的ツールは既知CVEの網羅が確実。両輪にする。

## 8. Skill の方針

**初期は不要。** `CLAUDE.md` は毎ターン読み込まれるため固定コストになるが、
Skill は必要時のみ読まれる。この差を使って後から切り出す。

| 置き場所 | 内容 |
|---|---|
| CLAUDE.md | 復帰プロトコル、ファイル構成、役割分担、常に守る規約 — **短く** |
| Skill | 特定作業のときだけ必要な長い手順書 |

### 切り出し候補（育ってから）
- タスク定義の書式 … A が毎回書式をブレさせ始めたら
- レビュー手順 … R の出力が安定しないと感じたら
- リリース手順 … デプロイを始めたら

判断基準は「**同じ手順を3回以上やって、毎回説明している**」と気づいた時点。
先に作ると使われない Skill を保守する羽目になる。

## 9. 実行フロー

```
A: 要件・設計・タスク一覧(001-020)を一括作成
  ↓
001 歩くスケルトン → B実装 → 証跡 → Rレビュー → 完了
002 認証基盤/スキーマ → B → R → 完了
003 ログインAPI      → B → R → 監査 → 完了
...
  ↓ マイルストーン（認証一式完了）
人間: 実際に触って受け入れ判定
A: state.md を読んで次フェーズのタスクを追加
```

**A を呼ぶのは3つの場合だけ:**
1. R からのエスカレーション（仕様・設計そのものの疑義）
2. マイルストーンの区切り
3. 人間が仕様変更を持ち込むとき

A に差分を読ませないことで A の肥大を防ぐ。渡すのは `state.md` / `worklog.md` の該当部分。

## 10. 人間の役割

伝令役ではない。ファイル＋メッセージングで受け渡しは自動化される。残るのは3つ。

1. **権限承認** — メッセージでは承認できない仕様。B で都度プロンプトが出る
2. **マイルストーンの受け入れ判定** — 実際に触る。事業判断なので AI に渡さない
3. **仕様変更の持ち込み**

## 11. コスト設計

- 実装は Sonnet、設計・レビュー・監査のみ Opus
- `CLAUDE_CODE_SUBAGENT_MODEL` でサブエージェントのモデルを一括制御
- 同一プロジェクト内で作業を続けるとプロンプトキャッシュが効く
  （キャッシュヒット時の入力コストは通常の10%、最大90%削減）
- 曖昧な指示（参照ファイルなしの「Fix authentication」など）は高コスト
  → タスクファイルに変更対象ファイル・確認観点・完了条件を必ず書く
- Explore / Plan / general-purpose のビルトインエージェントで代替できないか先に確認
- Agent Teams はプランモードで通常の約7倍のトークン。独立性の高い並列フェーズに限定投入
- CLAUDE.md を1画面に収める（全セッションが毎ターン払う固定費）

## 12. 位置づけと次段階

現状は **ハーネスエンジニアリング + L2（検証付き修正）** 相当。
ループの6要素（自動化・隔離・知識・連携・分業・記憶）のうち、
自動化＝プロンプトの自動投入だけが人間に残っている。

L3（無人実行）に進む前に必ず決めること:
- 停止条件の明文化
- 1ループあたりのトークン上限
- `--permission-mode` / `--allowedTools` の緩和範囲とリスク許容度

ループ化したエージェントは標準セッションの数倍〜数十倍のトークンを消費する。
また、生成役と検証役を分けない自己採点ループは構造的に破綻するため、
Maker-Checker 分離（本構成では達成済み）が前提となる。
