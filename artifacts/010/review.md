## 往復1回目（2026-08-30）

R です。CI pass 2m3s 緑を確認しました。**`event.list` の実装は正しい**のですが、`lib/date.ts` に内部矛盾があります。**必須修正1件・判断依頼1件です。**

### 必須: `yearsBefore` がうるう年の設計判断に従っていません

実行して確かめました。**同じファイルの中で、同じ問いに2つの答えがあります。**
```
yearsBefore("2024-02-29", 1)  →  2023-03-01
projectMonthDay(2, 29, 2023)  →  2023-02-28
```

A は「平年の 02-29 は **02-28 に寄せる**（03-01 にはしない）」と決め、理由まで `architecture.md` に書いています。`projectMonthDay` はそのとおり実装されている。しかし `yearsBefore` は `Date` の繰り上がりに任せていて **03-01 を返します。**

タスク定義は `lib/date.ts` について「**ここに全ての日付計算を集約する**」としています。集約の目的は規則を1箇所に置いて一貫させることなので、**中で矛盾していると集約した意味が薄れます。** `projectMonthDay` を経由させれば揃うはずです。

### 判断依頼: `monthsBefore` の月末

```
monthsBefore("2026-03-31", 1)  →  2026-03-03
monthsBefore("2026-03-30", 1)  →  2026-03-02
```

コメントは「JS の `Date` が UTC 月末を自動で繰り上げる挙動にそのまま従う」と書いており意図的です。しかしこの関数は **013（`memory.get`）の「ちょうど1ヶ月前の投稿」**で使われます。

**3月31日に「1ヶ月前」として3月3日の投稿を出す**のは、利用者から見れば誤りに見えます。月末を月末に寄せる（3/31 → 2/28）方が期待に近いはずですが、**これは仕様判断なので A に上げてください。** うるう年の件と違い、まだどこにも決定がありません。

決まるまでは今の挙動のままで構いません。ただし**テストで固定して、コメントに「013 で再検討」と書いておいてください。** 今は暗黙の挙動になっています。

### テストが難しいケースを1つも通していません

`monthsBefore` / `yearsBefore` のテストはこの3件だけです。
```
monthsBefore("2026-03-15", 1)  →  2026-02-15   繰り上がりなし
monthsBefore("2026-01-15", 1)  →  2025-12-15   年跨ぎのみ
yearsBefore("2026-03-15", 1)   →  2025-03-15   繰り上がりなし
```
**月末も 02-29 も入っていません。だから矛盾が誰にも見えませんでした。**

conventions.md 6節は「日付・タイムゾーンが絡む計算（**JST 固定である以上、ここは必ず壊れる**）」を必ずテストを書く対象に挙げています。まさにその箇所です。`todayJst` と `diffDays` と `projectMonthDay` は境界を突いているのに、この2つだけ素通りしています。

なお両関数は**現時点でどこからも使われていません**（テスト以外）。012・013 のための先行実装です。**使われる前に直せるので、今が一番安いタイミングです。**

### 良かった点

**`yearsBetween` が正しく作られています。** 「射影する年を決め打ちにしないための唯一の窓口」というコメント付きで、テストに私が挙げた反例そのもの（400日の窓が3つの暦年に触れる）が入っている。指摘を関数の設計に反映したうえで、その理由をコメントに残しているのが良い。

**`todayJst(nowMs = Date.now())` の設計が的確です。** 引数で時刻を差せるので、UTC 15:00 = JST 翌日 00:00 の境界をテストで直接指定できる。**タイムゾーンのテストが書けない実装は、たいていこの引数が無いことが原因です。** ファイル冒頭に「実行時刻に依存する関数は nowMs を引数で受け取れるようにし」と設計意図まで書かれている。

`event.list` も、`couple_id` スコープ・400日制限・`from > to` の拒否（`rangeDays < 0`）・`repeat_yearly=1` を SQL で絞れない理由のコメント、すべて妥当です。`toEvent` で `sourceDate` を保ち、射影時に `date` だけ差し替える形も設計どおり。

認可チェックリストを 12 → 16 に更新した点も確認しました。

## A からの判断（L61。2026-08-30）

A のメッセージを一字一句そのまま保存する。

> **月末に寄せる。**`monthsBefore("2026-03-31", 1)` は **`2026-02-28`**。PR #87。
>
> ## 「別の問題」ではなかった
>
> あなたは「010 のうるう日規則（射影専用）とは別の問題」と書いていたが、**同じ問題だった。**素の `Date` を叩いて分かった。
>
> ```
> 2026-03-31 の1ヶ月前  → 2026-03-03
> 2028-02-29 の1年前    → 2027-03-01   ← ここ
> ```
>
> **2つ目が決定的。**私が射影で決めた「平年の `02-29` は `02-28`」と**正面から矛盾する。**
>
> 素の `Date` に任せると、同じ「存在しない2月29日をどうするか」に、**同じコードベースが `02-28` と `03-01` の2つの答えを持つ。**
>
> **`monthsBefore` だけ直すと `yearsBefore` に矛盾が残る。**場面ごとに規則を作らず、1つにした。
>
> ## 一般則にした
>
> `architecture.md` 5節に「**存在しない日付は、その月の末日に寄せる**」を新設。射影の 02-29 規則はその一例として位置づけ直し、**`lib/date.ts` の全関数がこれに従う。**
>
> | 場面 | 入力 | 結果 |
> |---|---|---|
> | 記念日の射影 | `02-29` を平年へ | `02-28` |
> | `monthsBefore` | `2026-03-31` の1ヶ月前 | `2026-02-28` |
> | `yearsBefore` | `2028-02-29` の1年前 | `2027-02-28` |
>
> **`yearsBefore` も直す対象。**今は素の `Date` のままだと思うので確認してほしい。テストで固定してある `monthsBefore("2026-03-31", 1) === "2026-03-03"` は期待値を差し替えること。
>
> ## 副作用を先に書いた
>
> 3月29日・30日・31日の「1ヶ月前」は**3日とも2月28日**になる（平年）。同じ投稿が3日続けて「1ヶ月前」として出ることがある。
>
> **不具合ではない。**どの日から見ても2月28日が「1ヶ月前」であることは正しく、月末の日数差から必然的にそうなる。013 のタスクファイルにも書いた。**後で見て直そうとしないため。**
>
> ---
>
> 010 の中で直すか 013 まで持つかは任せる。**`yearsBefore` の矛盾があるので、010 の中で揃えた方が安全だとは思う。**判断はそちらで。

## B の対応（L61反映）

010の中で揃えた（Aの提案どおり）。

- `projectMonthDay` を02-29専用の特殊分岐から、`daysInMonth`（月の日数）で

  期待値に更新し、`projectMonthDay`の一般化を確認するテスト（31日を持たない月
  への射影）を追加。テスト3件追加（178→181件）。型チェック・lint通過
