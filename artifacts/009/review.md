# #60: 指摘された脆弱性は存在しませんでした

security-report.md の High はこう書かれています。
> oRPC の RPCHandler が HTTP メソッドを見ないため、全ての書き込み手続きが GET で実行できる

**この前提が誤りです。** `@orpc/server/dist/adapters/fetch/index.mjs:169-176` を読みました。

```js
class RPCHandler extends FetchHandler {
  constructor(router, options = {}) {
    if (options.strictGetMethodPluginEnabled ?? true) {
      options.plugins ??= [];
      options.plugins.push(new StrictGetMethodPlugin());
    }
```

**`@orpc/server/fetch` の RPCHandler は、既定で StrictGetMethodPlugin を自分で有効化します。** このプロジェクトが `strictGetMethodPluginEnabled: false` を渡したことは一度もありません。バージョンも 1.15.0 固定で、私が読んだものと同一です。

**GET は最初から 405 で拒否されていました。CSRF の経路は存在しませんでした。**

## あなたの証跡がそれを裏付けています

manual-check.md の「修正前の再現確認」節です。
```
$ curl ... GET /api/couple/get (no data): 405
```
その直後の散文はこう書いています。
> 修正前は最後の行が `200`（…いずれにせよ `405` 以外）になっていた

**貼られた出力の方が正しく、散文が誤りです。** 405 は修正前から出ていた値です。実測が反証を含んでいたのに、それが読まれずに通りました。監査が High と言ったので、自分の手元の数字より監査を信じた形だと思います。**この順序は逆にしてください。** 実測が指摘と食い違ったら、まず実測を疑い、次に指摘を疑う。今回は実測が正しかった。

**訂正が必要なのは記述です。**

## 訂正の質について

`manual-check.md` の直し方が特に良い。
> 実際に貼った出力（`GET /api/couple/get (no data): 405`）は当時から正しく、修正前から一貫して405だった。それにもかかわらず直後の散文で「修正前は`200`になっていた」と誤って書いてしまっていた

**元の出力を消さず、誤っていたのは解釈だと明示している。** 記録の直し方として正しい形です。消してしまうと「なぜ間違えたか」が失われます。

`index.ts` のコメントも、既定値をソースで確認した事実・誤指摘が通った経緯・明示登録を残す理由・2重登録が意図的であることまで書かれていて、次に読む人が同じ順序で判断しないための材料になっています。

`security-report.md` の打ち消し線＋【訂正・誤指摘と判明】も、監査記録として適切です。監査記録は上書きより注記の方が価値があります。
