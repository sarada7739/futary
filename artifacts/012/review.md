## 確認したこと

**5つのクエリすべてが `couple_id = ?1` でスコープされています。** `couples` / `couple_members` / `events` / `posts` ×2、漏れなし。`stats.get` は集計なので範囲が広く、1本でも抜けると他ペアの数字が混ざります。

**`computeDaysTogether` の境界が両側とも正しい。**
```
diff >= 0 → { together, days: diff + 1 }   今日 → diff 0 → 1日目
diff <  0 → { upcoming,  days: -diff }     明日 → diff -1 → あと1日
```
テスト名に「**0日にならない**」と書いてあるのが良い。この関数の存在理由がそこなので、名前が仕様になっています。

**純粋関数として切り出した判断も的確です。** ハンドラは `todayJst()` を呼ぶので日付を差し替えられませんが、境界の判定は `computeDaysTogether` に閉じているので直接テストできる。**不純な境界を薄くして、その外側だけを検査可能にする**形になっています。

**L65 の対応も、テストで明示的に固定されています。**
> `photoCount`は未削除・画像ありの投稿のみを数える（削除済みの写真投稿は含めない）

コメントに「007の決定で論理削除後もimage_keyは残るため、これが無いと削除済みの写真投稿まで数えてしまう」と**なぜこの条件が要るか**が書かれている。次の人が「冗長では」と外す余地を潰しています。

## `anniversaryDateSchema` の変更の扱いが良い

004 で入れた「未来の日付を弾く」テストを**消さずに、新しい仕様の境界テストへ置き換えて**います。

```
ちょうど1年後の記念日は登録できる（上限の境界）
1年より先（1年後+1日）の記念日は入力バリデーションで弾かれる
```

**上下両方を押さえています。** 仕様が変わったとき、古いテストを消すだけで済ませると歯止めが静かに消えます。上限が「打ち間違いを弾くための歯止めであって業務上の意味は無い」という理由もコメントに残っている。

## 記録1件（対応不要）

L67（`kind==='anniversary' || !repeatYearly`）は Zod の入力スキーマで強制されており、**DB の CHECK 制約ではありません。** `couple_members.slot` や `events.kind` は DB 側にも CHECK があるので、そこと比べると1段弱い形です。

全ての書き込みが契約を通る以上、実害はありません。業務ルールであってセキュリティ不変条件ではないので、優先度も低い。ただ**同じ種類の不変条件が2つの強度で守られている**ことは記録しておいてください。将来 DB を直接触る経路（シード、マイグレーション、014 のデモデータ）ができたときに差が出ます。
