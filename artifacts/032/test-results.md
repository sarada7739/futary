# 032: 削除の網を、表の名前ではなく「残っていないこと」で張る — テスト結果

## 実装

`apps/api/test/me.test.ts`に新しいテスト
（`me.delete後、登録の無い全表が0件になる（列名ではなく表全体で見る）`）を
追加した。既存の`couple_id`走査テストは変更していない（5節の判断どおり、
2つの網を両方残す）。

- `sqlite_master`から**アプリの全表**（`sqlite_%`・`d1_migrations`・
  `_cf_METADATA`を除く）を機械的に検出する。列名には依存しない
- 免除は「表」ではなく「残ってよい行の条件」で`ALLOWED_TO_REMAIN`に登録する
  （3節）
- `couple_id`を持つ表・持たない表（`reactions`・`post_images`）を区別せず、
  同じループで「消す前チェック」「消した後チェック」を行う

## `d1_migrations`・`_cf_METADATA`の除外（実測して判明）

`sqlite_master`は`sqlite_%`以外にも`d1_migrations`（drizzle-kitのマイグレー
ション適用記録）・`_cf_METADATA`（D1の内部表）を返すが、**これらへの
`SELECT`はD1が拒む**（実行して確認: `D1_ERROR: not authorized: SQLITE_AUTH`）。
アプリの表ではないため、除外理由をクエリの直前に書いたうえでスキャン対象
から外した（免除の一覧には入れていない。3節「アプリの表ではないものを
アプリの判断として登録すると、次に読む人が『これは消すべきなのか』と
考える」と同じ扱い）。

## 残ってよい表の実測（3節「Bは自分で実測して確かめること」）

タスク定義に書かれた表は、実際に1ペア・2人（owner・partner）で実測して
確かめた。`couples`を含め、免除の無い全表（`couples`・`couple_members`・
`invites`・`posts`・`post_images`・`reactions`・`events`・`wishes`・
`moods`）が、このテストが増やした分だけ削除後にちょうど0へ戻ることを
確認した（Rの実測と一致）。

## 【実測して分かった前提の食い違い】D1の状態がit()をまたいで共有されている

タスク定義3節は「テストのDBにはそのペアのデータしか無いのだから、『0件』
だけを見れば足りる」としていたが、**実際にはこのテストファイル内で
D1の状態がテストをまたいで共有されており、この前提は成立しなかった。**

最初、「削除後は完全に0件」という素朴な実装で書いたところ、このテスト
単体では通るのに、`me.test.ts`全体（39件）を通しで実行すると
`couples`で落ちた:

```
AssertionError: couples に残ってはいけない行が残っています: expected { '1': 1 } to be null
```

デバッグ出力で確認したところ、**このテストの先頭（自分のデータを作る前）
の時点で、`couples`に既に1件見えていた**:

```
DEBUG couplesCountAtStart {"c":1}
```

`@cloudflare/vitest-plugin`のREADMEは「Implements isolated per-test
storage」と謳っているが、少なくともこのプロジェクトの現在のバージョン・
このテストファイルの構成では、D1の書き込みは後続の`it()`から見えている
（他のテストが意図的・非意図的に残した`couples`行が原因と考えられる。
`me.test.ts`には既に「孤児として残ることを受け入れている」テストが
存在する）。原因の完全な特定（プラグインの既知の制約か、設定か）は
032の範囲では行っていない。

**対応**: 「削除後は0件」ではなく「このテストが増やした分が、削除後に
ちょうど元へ戻ったか」（`COUNT(*)`の差分）で見る形に直した。他のテストが
残した行の中身を読む必要はなく、列名にも依存しない。フルスイートで
3回連続green、単体でも5回連続greenを確認した。

**この発見はB個人の実装詳細（テストの書き方）の範囲に収まるため、
`docs/tasks/032-delete-scan.md`（Aの起票）は書き換えていない。**
ただし他のテストファイルにも同種の前提（「DBはこのテストだけのもの」）を
置いている箇所があれば、同じ形で踏む可能性があるため、`docs/state.md`の
論点表に記録した。

## フォールトインジェクション（実際に落ちることを見てから通した）

いずれも一時的にコードを壊し、テストを実行して赤くなることを確認した
うえで、完全に元へ戻した（`git diff`で無変更を確認済み）。

### 1. テストデータのもれ

`mood.setToday`の呼び出しを一時的にコメントアウト:

```
AssertionError: moods にこのペアの行を作るテストデータがありません。このテストに追加してください: expected 0 to be greater than 0
```

**「消す前チェック」が正しく機能している。**

### 2. 削除文のもれ（`user`の削除を一時的に外す）

`apps/api/src/procedures/me.ts`の`DELETE FROM user WHERE id = ?1`を一時的に
コメントアウトした。`session`・`account`は`user`へのON DELETE CASCADEで
消える設計のため、これにより両方とも削除されなくなる:

```
AssertionError: account に残ってはいけない行が残っています: expected { '1': 1 } to be null
```

**自分のsession・accountが残っていたら落ちることを確認した。**

（`post_images`・`reactions`は`posts`をON DELETE no actionで参照するため、
この2つのDELETE文を外すと「消えずに残る」ではなく「FK違反でbatch全体が
失敗する」という別の壊れ方になる。027・029・031で実際に踏んだ形と同じで、
この2表については沈黙した漏れではなく大声の失敗になる。今回はこちらの
確認は行っていない。「登録の無い行が残っていたら落ちる」の実証は、
FKに守られていない`user`/`session`/`account`側で行った）

### 3. 表ごと免除だと検知漏れになる（表名免除と条件免除の違いの証明）

上のフォールト2（`user`の削除を外した状態）を維持したまま、テスト側の
`ALLOWED_TO_REMAIN`を`user: "id <> ?1"`等の条件から`user: null`・
`session: null`・`account: null`（表ごと免除）に一時的に変更したところ、
**テストが誤って緑になった**:

```
Test Files  1 passed (1)
     Tests  1 passed | 38 skipped (39)
```

**自分のuser・session・accountが削除されずに残っていても、表ごと免除では
検知できないことを実際に確認した。** 条件免除（`id <> ?1`）に戻すと
フォールト2の状態のまま赤に戻ることも確認済み（上記）。これが3節
「表名での免除と条件での免除を分ける唯一の点」の実証である。
