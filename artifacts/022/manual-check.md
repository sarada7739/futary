## 確認してほしい項目

1. 時刻の選択（時・分の2列ホイール）が、スマホ幅で押しやすいか。**016の
   デプロイ後。**PCの細い幅で見えるのは並びだけで、押しやすさは指でしか
   分からない
2. **iPhoneのSafariでの操作感。016のデプロイ後。念のためであって、これを
   待って何も止めない**（タイマーでの確定をやめ、スクロール位置から毎回
   値を導く形にしたため、確定した値がずれる懸念自体が構造的に無くなった。
   iPhoneは開発サーバーに届かず016のデプロイ後までしか実機確認できないため、
   確認できないことを前提に設計を直した。Aの決定）
3. PCのChromeで同じ形（ホイールの見た目・上下のフェード）に見えるか。
   `<input type="time">`を採らず自前で作ったのはこのため
   - ~~PCのSafari~~ → **人間の環境では確かめられない**（Windowsに
     Safariは無い）。デスクトップSafariとiOS Safariは同じWebKitで、
     `scroll-snap`も`-webkit-mask`もそこで共通である。違うのは幅で、
     そちらはPCのChromeで見る。**「幅はChrome、エンジンはiPhone
     （016後）」で分けて担保する**（Aの決定）
4. 既存の予定を開いたとき、入っていた時刻がそのまま出るか。特に5分刻みに
   乗らない時刻（例: `12:07`）を持つ予定を開いたとき、その値が選択肢の
   1行として出て、選択状態になっているか
5. 4の予定を、時刻に触れずタイトルだけ変えて保存したとき、時刻が
   （`12:05`などに丸められず）`12:07`のまま残るか
6. 開始時刻を設定する前は「終了時刻を追加」ボタンが出ない
   （開始を選ぶ前に終了を選べない。押せてから断られる形にしていない）
7. 終了を空にしたまま保存できるか
8. 終了を開始より前・同じ時刻にしようとすると、保存できない旨が分かるか
9. 日付の8桁入力（マイページの付き合った日・結婚した日、カレンダーの
   予定の日付）で、8桁を打つ途中で表示が壊れて見えないか
   （8桁そろうまではハイフンを入れない実装にしている）
10. 存在しない日付（`20240230`等）を打つと、保存できないと分かるか
11. カレンダーの一覧で、開始・終了の両方がある予定は「12:00〜13:00」の
    形で、開始だけの予定は「12:00」のまま読めるか

## 結果（2026-08-31）

リモートD1へ0011適用後、人間が**PCのChrome**で実機確認。1回目の確認で
2件の不具合が見つかり、Bが修正後の再確認で**「すべてOK。問題なし」**との
回答。**この「OK」はPCのChromeで確認できた範囲についてのものであり、
以下の項目ごとの表がすべて確認済みという意味ではない**（Rレビュー指摘:
「0件」「OK」は範囲とセットでしか意味を持たない。範囲を書かないと見た
範囲が広いほど正しく見えてしまう）。

見つかった不具合（Claude in Chrome経由で人間の実際のブラウザを見て診断）:

1. **ホイールの選択帯（ピンクの背景）が数字を完全に覆い隠していた。**
   `WheelColumn`で選択帯の`View`をScrollViewの後に配置していたため、DOM順で
   前面に来てテキストを隠していた。選択帯をScrollViewより先（背景側）に
   配置する順序へ修正
2. **時刻ホイールを2つ足したことでモーダルの高さが画面を超え、下部の
   保存ボタンが押せなかった。**モーダル内をScrollView化してスクロール
   可能にした
3. （あわせて）**必須項目（タイトル・日付）が未入力のまま保存を押しても
   何も反応がなかった。**保存ボタンを常に押せる形にし、押した時点で
   足りない項目のメッセージを表示するよう変更（020「押しても何も起きない、
   にしない」と同じ判断）

日付8桁入力自体（PCのChromeで日付選択できない、という当初の報告）は
再現手順を確定できなかったが、上記の修正後の確認では問題として挙がらな
かった。

### 項目ごとの確認状況（環境つき）

| 項目 | 確認環境 | 状況 |
|---|---|---|
| 1. スマホ幅での押しやすさ | **016のデプロイ後** | 指の感触が要るため、PCの操作では代われない |
| 2. iPhone Safariでの操作感 | **016のデプロイ後。念のため** | 当初はタイマー確定（300ms）だったため「止まって見える数字と保存された数字が一致するか」を実機で見る必要があった。**タイマーでの確定自体を撤去**し、スクロール位置から毎回値を導く形に直した（`WheelColumn`。PR #156）が、Rのレビューで「毎回`onChange`を呼ぶと、位置合わせの`scrollTo`が利用者のスクロール中（慣性の途中・刻み外れ値が選択肢から消えてindexが繰り上がる瞬間）に走り、実際の物理位置と衝突する」不具合3件・「タップ時点のindexで飛び先を決めると、確定後にoptionsが縮んで違う値に着地する」不具合1件、計4件を指摘された。いずれも実機・タイマーを要らず決定的に再現するため、`apps/app/test/wheel-column.test.tsx`にonScroll/contentOffsetを直接与える回帰テストを追加し、「自分のスクロール起因の変更では位置合わせの`scrollTo`を走らせない（外からvalueが変わったときだけ走らせる）」設計に修正した（Rの指摘・Aの決定）。これによりPC Chromeで決定的に確認できる範囲は担保したが、**iPhoneでの実際の慣性スクロールの感触そのものは未確認のまま**であり、016のデプロイ後に念のため確認する |
| 3. 幅（PC Chrome） | PC Chrome | 修正後確認OK |
| 3. エンジン（Safari系） | **016のデプロイ後** | 人間の環境にSafariが無いため確かめられない。iPhoneのSafariで見ればデスクトップSafariと同じWebKitを見たことになる（Aの決定） |
| 4. 既存の刻み外時刻がそのまま出る | PC Chrome | 修正後確認OK |
| 5. タイトルのみ変更保存で時刻が書き換わらない | PC Chrome | 修正後確認OK（自動テストでも固定済み） |
| 6. 開始前は終了ボタンが出ない | PC Chrome | 修正後確認OK |
| 7. 終了を空のまま保存できる | PC Chrome | 修正後確認OK |
| 8. 終了が開始より前・同じで拒否 | PC Chrome | 修正後確認OK |
| 9. 8桁入力途中の表示崩れなし | PC Chrome | 修正後確認OK |
| 10. 存在しない日付を拒む | 未確認 | 人間からの明示的な言及なし（自動テストでは確認済み） |
| 11. カレンダー一覧の時刻表示 | 未確認 | 人間からの明示的な言及なし |

**いま人間に頼む項目**（「確かめられないもの」と「まだ確かめていないもの」
を混ぜない。Aの指摘）:
- **項目10・11は、人間がログイン済みのブラウザを開いてくれれば、
  BがClaude in Chrome経由で画面を見て診断を報告できる**（見た目の一次
  報告をBが用意できるため、人間に見た目を言葉で説明してもらう手間は
  減らせる。ただし「確認OK」の最終判定は人間またはRが行う）
- **項目1（スマホ幅での押しやすさ）・2（iPhone Safariの操作感）・
  3のエンジン部分（Safari系）はいま依頼しない。**いずれも人間の手元の
  Windows環境では確かめようがなく、016のデプロイ後にiPhoneのSafariで
  まとめて確認する（これを待って022を止めない）
