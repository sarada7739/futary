# 068 追補 3: スクロールで斜めから正面へ

`docs/tasks/068-phone-3d-tilt.md` の「追補 3」。画面は `artifacts/068/stage4/`（定義の `stage3/` は追補 2 で使ったので、分けた）。#471（追補 2）のマージ（main e65ace0）の記録もこの PR に含める。

## 実装

`apps/landing/js/tilt.mjs`（純粋な関数）:

- `scrollProgress(top, stageHeight, viewportHeight)`: ステージの上端がビューポートの下端で 0、スマホの中心がビューポートの中心で 1。外は 0 と 1 で止める（中心を過ぎたら正面のまま）
- `angleForScroll(progress)`: 0 で `ENTRY_TILT`、1 で正面。間は `easeOutCubic`。**残りの割合が `SNAP_REMAINING`（0.005）未満なら正面ちょうど**（後述）
- `decayTilt(tilt, dt, target)`・`isAtRest(tilt, target)`: 戻る先を指定できるようにした（既定は正面）

`apps/landing/js/phone3d.mjs`:

- `scroll` は `passive`。1 フレームに 1 回だけ角度を出し直す（rAF でまとめる）。節が見えている間だけ
- 止まっていればその角度で描き、ドラッグの後に戻っている途中なら戻る先だけを変える。ドラッグの間はスクロールの角度を使わない
- 離したら、正面ではなく**スクロールの位置で決まる角度へ**戻る
- 動きを減らす設定なら、戻る先はいつも正面（最初から正面・スクロールに合わせて動かさない）
- 本体が読めた時点の角度もスクロールの位置から（節の手前なら斜めで始まる）

## 始めの角度の向き（0節 #1「向きは B が見て」）

**`ENTRY_TILT = { x: −0.14, y: +0.44 }`**（約 8°・約 25°）。y・x の符号の 4 通りを正面の位置でドラッグして撮って見比べた（`directions.png`。左から y+x−・y−x+・y+x+・y−x−）。**1 枚目（y +・x −）**にした: 画面が右の説明文の方を向き、左の側面と音量のボタンが見え、上の縁が少し奥へ倒れる。定義の文面の「rotateY −0.44・rotateX 0.14」とは符号が逆になる（この実装では y が正のとき右の縁が奥へ行く）。

## 正面ちょうどに丸める理由

スマホの中心がビューポートの中心の位置（上端 54.5px）は、画素に丸めると 55px になり、進み具合がわずかに 1 に届かない。easeOutCubic の終わりは平らなので角度はほぼ 0 だが、0 でないと iframe が 3D の変形のままになり、追補 2 の画質の対応（正面で止まっている間は 2D の変形）が効かずに文字がにじんだ。残りが 0.5% 未満（0.13° 未満。見た目では区別できない）なら正面ちょうどにした。

## 気になる点（A の判断）: easeOutCubic だと、斜めが見えるのは入ってくる最初の短い間だけ

ステージの高さ（791px）がビューポート（900px）に近いので、「全体が見えた位置」（上端 109px）と「中心が中央」（上端 54.5px）は 55px しか違わない。easeOutCubic は最初に大きく戻るので、y の角度は次のようになる（1280×900）:

| ステージの上端（ビューポートの上から） | 見えている量 | easeOutCubic（今） | 直線 | easeInCubic |
|---|---|---|---|---|
| 820px | 上の 80px | 18.7° | 22.8° | 25.2° |
| 600px | 上の 300px | **6.8°** | 16.3° | 24.1° |
| 300px | 600px | **0.6°** | 7.3° | 16.2° |
| 109px | 全部 | 0.0° | 1.6° | 4.5° |

半分ほど見えた頃にはほぼ正面なので、人間の言う「3D だと分かる」斜めは、スマホの上の方しか見えていない間にしか見えない（`halfway-1280.png` はほぼ正面に見える）。**easeInCubic（または直線）にすると、見えている間はっきり斜めで、中央に近づいてから正面へ向く**。曲線を変えるのは `angleForScroll` の 1 行。定義どおり easeOutCubic で出し、A に相談する。
